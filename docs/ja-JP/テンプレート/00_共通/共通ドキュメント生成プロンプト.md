# 共通ドキュメント生成プロンプト

本プロンプトは、利用者の**明示指示**に基づき、  
HLDocS 準拠ドキュメントを **生成（new）／再作成（recreate）／部分差し替え（patch）** するための  
**document_type 非依存・共通生成プロンプト**である。

本プロンプトは**本文内容（ドメイン内容）を規定しない**。  
**共通ドキュメントテンプレート**を唯一の構造的正とし、  
LLM が実施すべき **前提検証・処理順序・生成制約・内部自己検査・出力規則**のみを定義する。

---

## 0. 最上位生成規則（FAIL-FAST / MUST）

以下のすべてが満たされない場合、**生成してはならない**。

- 生成モードが明示指定されていること（ENUM：`meta` / `apply`）
- `operation` が明示指定されていること（ENUM：`new` / `recreate` / `patch`）
- `document_type` が明示指定・合意されていること
- **共通ドキュメントテンプレート**が提示されていること
- `document_type` が本文テンプレートを要求する型である場合に限り、  
  **document_type 別テンプレート**が提示されていること
- `document_type` 別生成プロンプトが必要な場合、当該プロンプトが提示されていること
- `operation = recreate / patch` の場合、**差し替え対象となる修正前正本全文**が提示されていること
- `transport` が明示指定されている場合、許可 ENUM（`ui_copy` / `download` / `true_out`）であること
- document_type / operation / mode は、利用者指定を正とし、LLM が自律的に補正・推測してはならない

不足がある場合は、**不足内容を列挙して提示を要求し、成果物を一切出力してはならない**。  
思考過程・判断理由・内部検査結果・差分説明は **出力してはならない**。

---

## 1. 共通構造命令（MUST）

生成されるドキュメントは、  
**共通ドキュメントテンプレートに定義された構造を完全一致で維持**しなければならない。

LLM は以下を行ってはならない。

- 共通ドキュメントテンプレートに定義されていない構造要素の追加
- 構造順序の変更
- 空行数・区切り・再掲位置の変更
- テンプレート構造を説明文として再解釈すること

---

## 2. LLM-MANAGED 値決定規則（MUST）

### 2.1 doc_id

- `operation = new` の場合：`doc-YYYYMMDD-HHMMSSZ-XXXX` 形式で生成  
  - タイムゾーン：UTC  
  - XXXX：4 桁 base36
- `operation = recreate / patch` の場合：**既存の doc_id を必ず維持**

### 2.2 lang

- 明示指定がない場合は `ja-JP`

### 2.3 document_type

- 許可 ENUM：`spec` / `index` / `template` / `prompt` / `testspec` / `note` / `minutes` / `usage`
- **外部から合意された値のみ**を使用
- 未合意・未定義値を推測してはならない
- operation = recreate / patch の場合、既存 document_type を必ず維持する

### 2.4 canonical_document

- 許可 ENUM：`true` / `false`
- 正規成果物は `true`
- 下書き・検討用等は `false`

---

## 3. 識別子に関する共通規約（MUST）

### 3.1 sec_id

- 形式：`sec_<random>` のみ許可
- `<random>` は衝突確率が十分低い方式
- 意味語・章名・番号・用途語・document_type 名を含めてはならない
- 一意性は **(doc_id, sec_id)** の組で成立
- 生成・確定タイミングは document_type 別規約に従う  
  （※ spec 単体生成時に自律生成してはならない）
- sec_id は、対応する testspec / index / traceability 等との対応関係が確定する段階でのみ生成してよい

### 3.2 ref_id

- 形式：`ref_<random>` のみ許可
- 意味語・章名・番号・用途語を含めてはならない
- 一意性は **(doc_id, ref_id)** の組で成立
- 恒久参照（sec_id）の代替として使用してはならない

---

## 4. 参照形式の共通制約（MUST）

### 4.1 恒久参照

- 許可形式：`doc_id#sec_id`
- 章名・番号・位置情報を含む参照は禁止

### 4.2 派生参照

- 許可形式：`doc_id#ref_id`
- 用途 ENUM：`rationale` / `derivation`
- 派生参照は恒久参照を代替してはならない

---

## 5. hldocs コメント参照表現（MUST）

参照は 必ず HTML コメント形式で記載する（Markdown 本文ではない）

### 5.1 記載形式

恒久参照：
```
<!-- hldocs:ref=doc-XXXXXXXX-XXXX#sec_xxxx -->
```

派生参照：
```
<!-- hldocs:ref=doc-XXXXXXXX-XXXX#ref_yyyy hldocs:rel=rationale -->
```
```
<!-- hldocs:ref=doc-XXXXXXXX-XXXX#ref_yyyy hldocs:rel=derivation -->
```

### 5.2 制約

- `hldocs:rel` は派生参照時のみ使用
- `hldocs:rel` は `hldocs:ref` と同一コメント内に記載
- 恒久参照に `hldocs:rel` を付与してはならない

---

## 6. 生成フェーズ順序（MUST）

LLM は以下の Phase を **順序を変更せず** 実行する。

### Phase 0: 入力検証（FAIL-FAST）
- document_type が許可 ENUM であること
- 共通ドキュメントテンプレートが与えられていること
- 必要に応じて document_type 別テンプレート／生成プロンプトが与えられていること
- 不足があれば生成を開始してはならない

### Phase 1: テンプレート抽出
- 共通ドキュメントテンプレートから `__COMMON_TEMPLATE_BEGIN__` ～ `__COMMON_TEMPLATE_END__` を抽出
- document_type 別テンプレートから `__BODY_TEMPLATE_BEGIN__` ～ `__BODY_TEMPLATE_END__` を抽出
- マーカー欠落・重複時は生成禁止

### Phase 2: テンプレート合成
- 共通ドキュメントテンプレート内 `__DOCUMENT_BODY__` に本文テンプレート範囲を**無加工で差し込み**
- 構造トークンの解釈・空行変更は禁止

### Phase 3: 可変スロット生成／Traceability 構築
- タイトル・本文など可変スロットを生成
- Traceability 規約に従い `doc_id / sec_id / ref_id` を配置
- テンプレート構造の改変は禁止

### Phase 4: 構造トークン実体化
- `<BLANK_LINE>` → 空行1行
- `<SECTION_SEPARATOR>` → `---` 単独行
- `<LLM_MANAGED_BLOCK>` → 規約準拠の HTML コメント
- 内容の追加・削除・並び替えは禁止

### Phase 5: Transport Encoding 適用
- 指定された transport のみを適用
- 意味・構造・識別子を変更してはならない

### Phase 6: 最終検証（非出力）
- 共通構造・不変条件・推測生成禁止の遵守
- transport 出力制約（特に ui_copy）への適合

### Phase 7: 出力
- **最終成果物のみ**を出力
- 検証結果・中間生成物・ログは出力禁止

---

## 7. 再作成／差し替え時の不変条件（MUST）

`operation = recreate / patch` の場合、以下は不変。

- doc_id
- canonical_title
- document_type
- 文書全体の構造順序
- 階層リンク行（先頭・末尾、内容・位置とも）

不足情報を**推測で補完してはならない**。  
不変条件を満たせない場合、生成を開始してはならない。

---

## 8. Transport Encoding 適用規則（MUST）

### 8.1 ui_copy

transport が `ui_copy` の場合、以下を**絶対規則**とする。

- 出力は **単一のコードブロックのみ**
- コードブロック外に文字列を出力してはならない
- 本文中に出現する連続バッククォート最大数を `M` とする
- 外側コードフェンス数 `N = M + 1`
- 本文中にバッククォートが存在しない場合は `N = 3`
- 外側フェンス行にはフェンス記号のみを記載（言語指定禁止）
- コードブロック内には **復元可能（roundtrip）な Markdown 全文**のみを格納

---

## 9. 生成モード（meta / apply）に関する注意（MUST）

- **meta**：HLDocS 自身（spec / template / prompt）の作成・再作成  
  - 不変条件と全文差し替えを特に厳格に適用
- **apply**：HLDocS を前提とした他プロジェクト文書生成  
  - HLDocS 仕様・テンプレート・生成プロンプトは不変前提

モード未指定・不明確な場合、生成を開始してはならない。

---

## 10. 内部自己検査（非出力・MUST）

以下を満たしていることを内部的に検査せよ。

- 参照根拠がテンプレート／生成プロンプトのみに限定されている
- doc_id / sec_id / ref_id 形式の妥当性
- (doc_id, sec_id) / (doc_id, ref_id) の一意性成立
- 参照形式・hldocs コメントの整合性
- document_type が許可 ENUM 内であること
- 推測生成を行っていない
- 不変条件が保持されている
- 生成結果の本文中に、作業指示・省略表現・参照注釈等の成果物として無効な記述が含まれていないこと
- ui_copy 出力規則に完全適合している

検査結果は**出力してはならない**。

### 10.1 meta モードにおける生成対象別内部自己検査（MUST）

### 10.1.1 生成対象が生成プロンプトである場合の整合性検査（MUST）

生成モードが meta であり、  
本プロンプトが **共通生成プロンプトまたは document_type 別生成プロンプト**を  
新規作成または再作成するために使用されている場合、  
LLM は以下を内部自己検査として必ず確認しなければならない。

- 生成した生成プロンプトの内容が、  
  利用者から与えられた共通仕様および関連規約と  
  **意味的に矛盾していないこと**
- 共通仕様・規約に定義された MUST / MUST NOT 条件が、  
  生成プロンプト内で弱体化・無効化・再解釈されていないこと
- document_type、LLM-MANAGED ブロック、Traceability、  
  Transport Encoding、再作成（差し替え）時の不変条件に関する  
  仕様上の前提・制約が、生成プロンプト側に正しく反映されていること
- 生成プロンプト内に、  
  仕様本文に存在しない新たな制約・判断規則・例外条件を  
  **推測により導入していないこと**

本検査は、  
生成フェーズにおいて仕様本文が与えられない前提下で、  
当該生成プロンプトが **唯一の規範として安全に機能可能であるか**を  
確認するためのものである。

本検査の結果は、最終成果物として出力してはならない。

上記のいずれかを満たさない場合、  
LLM は生成を失敗と判定し、出力を行ってはならない（MUST NOT）。

---

## 11. document_type 固有規則（内部）

document_type 固有の判断・制約は、  
別途与えられる document_type 別生成プロンプトを内部適用する。

それらを本文に出力してはならない。
