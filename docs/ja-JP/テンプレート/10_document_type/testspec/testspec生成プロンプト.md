# document_type:testspec 生成プロンプト

本プロンプトは、HLDocS 規約に準拠した **testspec（テスト仕様）** を生成するための  
**正規かつ唯一の生成プロンプト**である。  
spec との traceability（追跡可能性）確立を最優先目的とする。

---

## 0. 最上位命令（MUST）

- document_type は **testspec 固定**。
- testspec は **必ず spec に従属**する。
- spec が添付・参照されていない場合、testspec を生成してはならない。
- 出力は **最終成果物のみ**とし、説明・理由・補足は出力しない。

---

## 1. sec_id に関する基本原則（最重要）

### 1.1 役割定義

- **sec_id は traceability を構成する検証単位キーである**
- sec_id は **testspec を起点として初出・確定**する
- spec は testspec により確定した sec_id を「受け取る」側である

### 1.2 一意性の考え方

- sec_id は **単体では一意性を持たない**
- 一意性は **(doc_id, sec_id)** の組で成立する
- sec_id をグローバル一意キーとして扱ってはならない

---

## 2. 生成規則（MUST）

- 各テストケースは **章（見出し）単位**で生成する
- 各章には **必ず sec_id を付与**する
- 各テストケースは **必ず spec 参照（doc_id#sec_id）を含める**
- sec_id は **当該 testspec 内で初めて定義されるもの**とする

---

## 3. sec_id の付与ルール

### 3.1 新規 testspec 作成時

- LLM は **検証観点単位**で sec_id を生成してよい
- sec_id は **意味語に依存しない安定識別子**とする
- 人間可読性は要求しない

### 3.2 既存 testspec の再作成（HLDocS 非準拠 → 準拠）

- 既存テストケースに sec_id が存在しない場合、付与してよい
- 既存 sec_id がある場合は **変更してはならない**
- 再構成・整形を理由に sec_id を再生成してはならない

### 3.3 禁止事項（sec_id 関連）

- spec を参照せずに sec_id を定義すること
- spec 側の都合で sec_id を推測・変更すること
- sec_id を進捗管理・装飾・履歴管理など traceability 以外の目的で使用すること

---

## 4. spec 参照ルール（MUST）

- 各テストケースは、対応する spec の **sec_id を参照**しなければならない
- 恒久参照形式は以下のみを使用する

例（表記例）：

```
doc_id#sec_id
```

---

## 5. 暫定参照（TEMP_REF）の扱い（重要）

### 5.1 使用条件

- TEMP_REF は **入力（添付 spec / 指示文）に含まれている場合のみ使用可**
- LLM が **新たに TEMP_REF を生成してはならない**

### 5.2 許可される形式（完全一致）

```
[TEMP_REF: doc_id#章名]
[TEMP_REF: doc_id#節タイトル]
```

### 5.3 testspec 側での扱い

- TEMP_REF は **testspec 内に恒久的に残してはならない**
- testspec 生成時に sec_id を確定し、**恒久参照へ置き換える**
- TEMP_REF をそのまま traceability キーとして扱ってはならない

---

## 6. テスト番号の扱い

### 6.1 位置付け

- テスト番号は **管理・運用ラベル**であり、恒久キーではない
- traceability は **テスト番号ではなく sec_id により行う**

### 6.2 デフォルト動作

- 既存のテスト番号がある場合は **保持する**
- 再採番を目的としない限り、新規採番は最小限とする

### 6.3 再採番の条件付き許可

以下のような **明示的指示がある場合に限り**、テスト番号の再採番を許可する。

- 「テスト番号を振り直す」
- 「テスト番号を変更する」
- 「テスト番号を推奨形式に変換する」

この場合でも、

- sec_id は **絶対に変更してはならない**
- spec 参照は **変更してはならない**

---

## 7. テスト番号の推奨フォーマット

### 7.1 基本形式（参考）

```
<TARGET>-<LEVEL>-<PURPOSE>-<NNN>
```

### 7.2 推奨（拡張）形式（既定）

長文化・分割を防ぐため、**既定では以下の拡張形式を推奨**する。

```
<TARGET>-<LEVEL>-<PURPOSE>-<MM>-<NNN>
```

- <MM> は **テストモジュール番号**等を表す短い識別子
- 数字 2〜3 桁を推奨（例：01, 02, 10, 120）

### 7.3 解釈ルール

- 「テスト番号は推奨形式に変換して」と指示された場合  
  → **拡張形式（MMあり）を使用する**
- 基本形式（MMなし）を使用する場合は、**明示的指示が必要**

---

## 8. 禁止事項（MUST NOT）

- 実装方法・コードの記述
- テスト実行手順の詳細化
- spec の再解釈・拡張・補完
- spec 側の sec_id を新規に定義・変更すること

---

## 9. 内部自己検査（非出力）

生成前に以下を必ず満たしていることを確認する。

- spec が参照・添付されている
- 各テストケースに sec_id が付与されている
- spec 参照（doc_id#sec_id）が欠けていない
- TEMP_REF が残存していない
- sec_id をテスト番号の代替として扱っていない
- 再採番時も sec_id を変更していない
