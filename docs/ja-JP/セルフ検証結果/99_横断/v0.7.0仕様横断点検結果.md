## 3. CA-01 Capability ProviderとSubFlow

点検時、次の依存が許可されていた。

```text
Execution Capability
 ↓ provided_by
SubFlow
 ↓
Execution Capability
```

SubFlowはExecution Capabilityを利用して処理を構成する層であるため、Providerとしても扱うと循環依存を形成できる。

修正後:

```text
Practical Capability
 ↓
Execution Capability
 ↓
Capability Provider
 ├─ ENVIRONMENT_TOOL
 └─ HLDOCS_TOOL

Workflow
 ↓
SubFlow
 ↓ uses
Execution Capability
```

SubFlowをExecution CapabilityのCapability Providerから除外した。

これはSubFlowの再利用やPractical Capabilityの実現への利用を禁止するものではない。SubFlowは複数のExecution Capabilityを組み合わせた再利用可能処理を表現でき、その実行可能性は依存Execution Capabilityその他の開始条件から評価する。

## 4. CA-02 正本競合

再構成中、新`00_Core/01_HLDocSとは.md`と旧`00_共通/01_HLDocSとは.md`の双方が`canonical_document: true`であることを確認した。

当初は旧仕様群を一律に非正本化する案を検討したが、Version Up(バージョン更新)、移行、再構成、比較では新旧の正本候補が同時に存在することが通常運用として発生する。

このため、複数候補の存在そのものを異常とせず、現在採用する正本を一意に決定できない状態をCanonical Conflict(正本競合)としてCore仕様へ一般化した。

```text
複数の正本候補
 ↓
明示的な選択根拠あり？
 ├─ YES → 現在の正本を一意に確定して継続
 └─ NO  → Canonical Conflict
           ↓
         推測統合・暗黙選択禁止
           ↓
         現在処理に必要なら利用者判断
```

明示的な選択根拠には、利用者指定、対象版、ブランチ、配置先、登録情報その他の意味上の根拠を利用できる。

`canonical_document: true`は正本候補を示す情報であり、同一対象に複数存在した場合の自動優先順位そのものとはしない。

したがって、Version Up中の旧版を比較資料として残すためだけに、物理削除または`canonical_document: false`への変更を一律要求しない。

今回の再構成作業では、利用者が`develop`上の`docs/ja-JP/再構成ワーク/仕様/`を再構成対象として明示しているため、この作業中の新仕様と旧比較資料を区別する根拠が存在する。

## 5. CA-03〜05 未再構成層

新仕様が参照する後続層のうち、SubFlow(サブフロー)は新構造側の共通仕様がまだ存在しない。

Tool(ツール)は共通仕様を再構成済みである。Restriction Set(制限セット)は共通仕様と登録簿を再構成済みであり、個別Setは実際の参照が確定したものから追加する。

これは現時点では「循環依存」ではなく、再構成途中の未定義参照として扱う。

旧`00_共通`仕様をそのまま新仕様の不足部分として暗黙利用してはならない。

再構成時は旧仕様から必要事項を調査し、新Core/Capability/Restrictionモデルと整合する形で新仕様へ移す。

## 7. 次の再構成順序

未定義参照を減らすため、次の順序を基本とする。

1. Coreまでの確定区間を維持し、後続層からCore境界を変更する必要が生じた場合のみCoreを再点検する。
2. SubFlow共通仕様をExecution Capability利用側として再構成する。
3. 実際に参照されるRestriction Setを確認し、必要な個別Setだけを登録する。
4. Restriction / Tool / SubFlowを使う最小E2Eを実施する。
5. 旧仕様との差分を再点検する。

Toolより先にSubFlowを確定すると、Capability利用境界が再び曖昧になる可能性があるため、Provider/Tool側を先に固定する。

## 8. 判定

Core仕様群は別途横断確認を実施し、現時点で未解決の責務境界がないことを確認した。State Machine、State、Work、Interaction、Workflow、Capabilityの再構成済み範囲も主要責務境界について基本整合している。

正本候補の併存はCore仕様で扱える。Tool共通仕様、Restriction Set共通仕様および登録簿も再構成済みである。SubFlow共通仕様と、必要な個別Restriction Setの確定が残るため、全体再構成完了とはまだ判定しない。
