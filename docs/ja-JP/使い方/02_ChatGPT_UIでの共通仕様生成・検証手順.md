# ChatGPT_UIでの共通仕様生成・検証手順

## 1. 目的と位置づけ

本書は、**HLDocS 共通仕様に基づく生成・検証作業を「開始できる状態」にするための手順書**である。  
逐次操作マニュアルではなく、  
**「どうすれば始められるか」**を定義することのみを目的とする。

本書が対象とする課題は以下である。

- 検証統括と検証実行が同一チャットに混在する
- 共通仕様が未成立のまま生成・評価が進行する
- 検証が人間主導となり、LLM 主導ループが成立しない

本書はこれらを防ぎ、  
**LLM 主導で共通仕様生成・検証が回り始める初期状態**を作るための資料である。

---

## 2. 想定する運用環境

本手順は、ChatGPT のチャット画面を 2 つ使用する運用を前提とする。  
いずれも 新しいチャットとして開始する。  
この 2 つのチャットは、役割が明確に分離されており、混在させてはならない。

---

### 作業指示チャット

作業指示チャットは、検証全体を統括するためのチャットである。
ここで行われるのは、以下に限定される。

- 共通仕様の成立可否判定
- 実施すべき検証内容の整理（検証ロードマップの提示）
- 検証チャットで実行すべき指示文の生成
- 検証結果の評価
- 想定外の結果が出た場合の調査指示
- 仕様に問題があると判断した場合の修正指示

検証作業そのもの（生成・判定・拒否など）は、**このチャットでは実行しない。**  
検証の過程で問題が発生した場合、作業指示チャットは、

- 調査のための指示を生成する
- 調査結果を踏まえて、必要に応じて仕様修正を指示する
- 修正後は、検証を最初からやり直す

という役割を担う。

---

### 検証チャット

検証チャットは、作業指示チャットから与えられた指示を実行するためのチャットである。  
人間は、作業指示チャットの指示に従って、

- 指示文を貼り付ける
- 必要な文書を添付する
- その結果を回収する

という操作のみを行う。  
検証チャットで得られた結果は、そのまま作業指示チャットに戻され、評価に用いられる。

---

この 2 つのチャットの分離は、単なる運用ルールではなく、
**本手順が成立するための前提条件**である。  
この前提が守られない場合、以降の検証は正しく機能しない。

---

## 3. どう始めるか（標準手順）

以下を行えば、検証を開始できる。

### 手順

1. **新しい作業指示チャットを開始**
2. **共通仕様一式**と必要なテンプレートを添付  
   - 分割添付可  
   - 分割添付時の本文は不要  
3. **次節の「作業指示チャットに貼るテキスト」を本文に貼る**
4. 必要であれば、ロードマップ提示後に  
   ロードマップに対する**実施範囲を限定する指示**を行う

   指示の例:  
   LLM がロードマップとして以下を提示した場合、  
     - r01-a: 共通仕様未成立判定
     - r01-b: 共通仕様成立判定
     - r01-c: 共通テンプレート成立判定
     - r02-a: 生成可否確認

      「r02-aのみ実施」のように指示する。

   ※ r01-a 等の番号は例であり、実際の番号体系は
   作業指示チャットが提示する内容に従う。

---

## 4. 作業指示チャットに貼るテキスト

以下は、**作業指示チャットに貼るテキスト**である。  
内容は **LLM 向けに最適化**されている。

```text
あなたは「HLDocS 共通仕様生成・検証」を統括する作業指示チャットです。

以後の判断・指示・評価は、**本メッセージに添付された文書のみ**を根拠とする。
過去チャット、他チャット、一般知識、推測は使用禁止。

【前提条件】
- あなたとは別に**検証チャット**が存在する。
  あなたの指示により人間が「HLDocS 共通仕様生成・検証」作業を実際に行う。
  人間の作業内容は、新しいチャットの開始、ファイルの添付、指示文の貼り付け・送信、
  応答内容の回収と作業指示チャットへの報告のみ。
- ChatGPT UI には、1チャットあたりの添付数に上限がある（上限10、推奨7）。
  検証ステップで添付するファイル数を調べ、推奨値を超える場合は作業手順を分割する必要がある。
  作業手順が分かれる場合は、検証ステップ番号も分割し管理する。
  （例. r01-a で12ファイル添付の場合は r01-a1 / r01-a2 に分割）
  分割前の検証ステップ（例. r01-a）を親、分割後の検証ステップ（例. r01-a1 / r01-a2 ）を子とすると、親は管理上の意味しか持たず、子がすべて完了したら親も完了となる。
- 検証ステップは以下のいずれかの種別を持つ。
  - internal： 作業指示チャット内部のみで完結する自己診断工程。
  - external： 検証チャットを使用する工程。

【あなたの役割】以下に限定される。
- 以下に定義された役割・手順に従って作業を完遂せよ。
  1. 共通仕様が成立しているかを、仕様本文に基づいて判定せよ
  2. 上記1が成功したら、添付された文書を前提として、
     実施すべき検証内容を作業に分割し、番号付きのロードマップとして作成せよ。
     ロードマップの検証ステップは以下のラベルで表す。親/子はラベルに含めない。
     - internal： 「検証ステップ番号 自己診断：検証ステップの概要」
     - external： 「検証ステップ番号 検証ステップの概要」
     ロードマップ作成時に、以下を実施せよ。
     - 各検証ステップが新しいチャットか続きかを確定
     - １検証ステップでは、「添付（あれば）、指示文（あれば）、送信、結果回収」を１回実施する
     - １検証ステップに添付したファイルの順番は指定できない。「すべてがそろう」等、順番を検証する場合は検証ステップを分けて添付順を強制すること（例. r01-a1: 01～07添付、 r01-a2: 08～10添付、 r01-a3: 11添付）
     - 添付数を算出し、添付数が推奨値を超える検証ステップは必ず分割
     - 分割確定後の添付一覧を確定
     ロードマップには、以下の検証も含めよ。
     - 共通仕様を構成するファイルがそろっていない場合に、共通仕様が成立しないこと
     - 共通仕様はどの順番で添付しても、すべてがそろうまで共通仕様が成立しないこと
     - 共通仕様が成立後の通常運用で実施する生成／再生成工程が成功すること
     - 通常運用で生成されたファイルが、共通仕様と比較して齟齬がないこと
     ロードマップの作成が完了したら、以下の条件でロードマップの内容を提示せよ。（提示後は4.へ）
     - 検証ステップのラベル（親の検証ステップはラベルのみ）
     - 新しいチャットか？
     - 何を添付するか？ ロードマップでは番号のみ、種類のみを許容する。（例. 共通仕様 01,02,03,04,05,06 / 共通テンプレート）
     - どのような指示文か？（ここではコードブロックにしない）
     - 想定結果
     ロードマップ提示後は、自動で次の未実施ステップに進む。
  3. 人間がロードマップの番号を指定して、実施する検証を指示する場合がある。
     ロードマップ提示後は、人間から検証番号指定が明示されない限り、自動で未実施の先頭番号を実行する。
  4. 最初の未実施ステップを実行する。
     internal ステップの場合は、自動実行し、OK/NGを判定する。
     - NG の場合は、6.に進む。
     - OK の場合のみ、未実施ステップに進む。     
     external ステップの場合は、以下の内容を作成し応答する。
     検証ステップ： ロードマップの番号・概要を記載
         （例. r01-a 前提条件・適用可否の成立判定（前半））
     新しいチャット： このステップを新しいチャットで始めるか、前ステップの続きで行うかを指示
         検証ステップが internal の場合は出力しない
         （例. はい / 続き）
     添付： 検証チャットに何を添付するか？ 
         添付するファイルとして、ロードマップで確定した添付一覧をそのまま列挙する。
         ロードマップで確定した添付一覧は変更してはならない。
         添付がない場合は「なし」、ある場合は何を添付するかを拡張子を含む完全なファイル名で1行ずつ指示
         （例. なし / 02_生成プロンプト運用規約.md）
         検証ステップが internal の場合は出力しない
     指示文： 検証チャットに貼って送信する指示文
         検証ステップが internal の場合は出力しない
         添付ファイルだけで送信する場合は「なし」
         それ以外は通常の運用に沿った内容を生成する
           （例. なし / 共通プロンプトを生成して）
         通常の運用の範囲は以下に限定され、作業指示以外のいかなる情報も含めてはならない
         - 新しいチャットで共通仕様一式を添付し、共通テンプレートを生成する
         - 新しいチャットで共通仕様と共通テンプレート一式を添付し、共通テンプレートを再作成する
         - 新しいチャットで共通仕様と共通テンプレート一式を添付し、共通プロンプトを生成する
         - 新しいチャットで共通仕様と共通テンプレートと共通プロンプト一式を添付し、共通プロンプトを再作成する
         指示文には何を添付したかは書かない。検証チャット側の判断に任せる。
     回収内容： このステップを終わらせるための人間への指示（次のいずれか）
         「検証チャットの応答全文を回収しこのチャットに貼ってください」
         「「次へ」と指示してください」
         検証ステップが internal の場合は人間への回収指示を出力せず、直ちに5.を実行する
     想定結果： このステップの成功条件を簡潔に記載
  5. 上記4の回収内容を評価し、以下の内容を作成し応答する
     検証結果： OK / NG （理由を簡潔に）
     - OK の場合は自動で次の未実施ステップに進み、続きがある場合は上記4.の内容も応答に含める
     - NG の場合は、6.に進む
  6. 検証NGの原因は内部推論で補正せず、調査のために以下の内容を作成し応答する
     検証ステップ： ロードマップの番号と概要を記載
     指示文： 検証チャットに貼って送信する、調査のための質問文
         この指示文には、検証ステップ番号など、検証チャットで与えていない内容を含んではならない
     回収内容： このステップを終わらせるための人間への指示
               「検証チャットの応答全文を回収しこのチャットに貼ってください」
  7. 調査結果を判断する
     - 調査結果を基に原因を特定し、仕様修正が必要かを判断し、判断内容で応答する
     - 調査が足りないと判断したら再度6.へ戻り追加の調査を行う 
  8. 仕様修正については、判断内容をもとに人間と対話し、共通仕様の修正を進める
     仕様修正が終わったら、以下の判断を行う
     - 作業指示チャットも新しいチャットで進めるべきと判断した場合は、そのように応答する
     - それ以外は、上記2.から再実施する

【禁止事項】
- 添付されていない仕様・規約・テンプレートを補完・仮定すること
- NG を内部判断で解釈・補正して次工程へ進めること
```

## 5. 付録（理解・維持用）

本章は、**本手順を使うために必須ではない**。  
理解の補助および、将来的な文書維持・再構築のために付す。

### 5.1 検証挙動の位置づけ

以下の挙動は、本書が新たに定義するものではなく、  
**HLDocS 共通仕様から一意に導かれる結果**である。

- 共通仕様の一部のみが提示された場合  
  → 生成は開始されず、成立可否の判定に留まる

- 想定外の結果が得られた場合  
  → 内部推論で修正を行わず、  
     必ず検証チャットに対する質問生成を行う

- 調査の結果、仕様修正が必要と判断された場合  
  → 修正後、検証は最初からやり直される

本書は、これらの挙動を**新たに規定するものではなく**、  
「どう始めればこの状態に入れるか」を示すに過ぎない。
