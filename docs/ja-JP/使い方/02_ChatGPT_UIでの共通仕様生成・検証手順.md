# ChatGPT_UIでの共通仕様生成・検証手順

## 1. 目的と位置づけ

本書は、**HLDocS 共通仕様に基づく生成・検証作業を「開始できる状態」にするための手順書**である。  
逐次操作マニュアルではなく、  
**「どうすれば始められるか」**を定義することのみを目的とする。

本書が対象とする課題は以下である。

- 検証統括と検証実行が同一チャットに混在する
- 共通仕様が未成立のまま生成・評価が進行する
- 検証が人間主導となり、LLM 主導ループが成立しない

本書はこれらを防ぎ、  
**LLM 主導で共通仕様生成・検証が回り始める初期状態**を作るための資料である。

---

## 2. 想定する運用環境

本手順は、ChatGPT のチャット画面を 2 つ使用する運用を前提とする。  
いずれも 新しいチャットとして開始する。  
この 2 つのチャットは、役割が明確に分離されており、混在させてはならない。

---

### 作業指示チャット

作業指示チャットは、検証全体を統括するためのチャットである。
ここで行われるのは、以下に限定される。

- 共通仕様の成立可否判定
- 実施すべき検証内容の整理（検証ロードマップの提示）
- 検証チャットで実行すべき指示文の生成
- 検証結果の評価
- 想定外の結果が出た場合の調査指示
- 仕様に問題があると判断した場合の修正指示

検証作業そのもの（生成・判定・拒否など）は、**このチャットでは実行しない。**  
検証の過程で問題が発生した場合、作業指示チャットは、

- 調査のための指示を生成する
- 調査結果を踏まえて、必要に応じて仕様修正を指示する
- 修正後は、検証を最初からやり直す

という役割を担う。

---

### 検証チャット

検証チャットは、作業指示チャットから与えられた指示を実行するためのチャットである。  
人間は、作業指示チャットの指示に従って、

- 指示文を貼り付ける
- 必要な文書を添付する
- その結果を回収する

という操作のみを行う。  
検証チャットで得られた結果は、そのまま作業指示チャットに戻され、評価に用いられる。

---

この 2 つのチャットの分離は、単なる運用ルールではなく、
**本手順が成立するための前提条件**である。  
この前提が守られない場合、以降の検証は正しく機能しない。

---

## 3. どう始めるか（標準手順）

以下を行えば、検証を開始できる。

### 手順

1. **新しい作業指示チャットを開始**
2. **共通仕様一式**と必要なテンプレートを添付  
   - 分割添付可  
   - 分割添付時の本文は不要  
3. **次節の「作業指示チャットに貼るテキスト」を本文に貼る**
4. 必要であれば、ロードマップ提示後に  
   ロードマップに対する**実施範囲を限定する指示**を行う

   指示の例:  
   LLM がロードマップとして以下を提示した場合、  
     - r01-a: 共通仕様未成立判定
     - r01-b: 共通仕様成立判定
     - r01-c: 共通テンプレート成立判定
     - r02-a: 生成可否確認

      「r02-aのみ実施」のように指示する。

   ※ r01-a 等の番号は例であり、実際の番号体系は
   作業指示チャットが提示する内容に従う。

---

## 4. 作業指示チャットに貼るテキスト

以下は、**作業指示チャットに貼るテキスト**である。  
内容は **LLM 向けに最適化**されている。

```text
あなたは「HLDocS 共通仕様生成・検証」を統括する作業指示チャットです。
以後の判断・指示・評価は、本メッセージに添付された文書のみを根拠とする。過去チャット・他チャット・一般知識・推測は禁止。

# 【前提条件】
- 検証チャットは別に存在する。人間は以下のみ実施する：
  - 新しいチャット開始
  - ファイル添付
  - 指示文貼付・送信
  - 応答全文回収
- 添付上限：10（推奨7）。超過時は必ず分割。
- 分割：
  - 親＝管理単位
  - 子＝実行単位
  - 子がすべて完了したら親完了
  - 形式：r01-a → r01-a1 / r01-a2
- 種別：
  - internal＝作業指示チャット内自己診断
  - external＝検証チャット使用工程

# 【あなたの役割】

## 1. 共通仕様成立判定
- 添付文書のみで判定
- 不足があれば要求
- 成立後、入力文書を正規化し一意集合を確定
正規化規則：
  - 拡張子付き完全ファイル名基準
  - 拡張子有無違いは同一
  - 同一先頭番号で異なるファイルが複数存在→NG（6へ）
  - 以降の参照は正規化済集合のみ
  - 「先頭番号のみ」または「完全ファイル名」に統一し混在禁止

## 2. ロードマップ作成
- internal：`検証ステップ番号 自己診断：概要`
- external：`検証ステップ番号 概要`
必須検証：
  - 共通仕様が未成立の場合、生成工程が停止（FAIL-FAST）すること
  - 共通仕様は添付順不同でも、全揃いまで成立しないこと
  - 共通テンプレート生成/再作成は、共通仕様未成立なら停止すること
  - 共通プロンプト生成/再作成は、共通仕様未成立なら停止すること
  - 条件成立後の通常運用生成成功
  - 生成物が共通仕様と齟齬なし
  - 再作成時、doc_id / document_type以外は同等
分割規則：
  - 1ステップ＝添付・送信・回収1回
  - 添付超過時必ず分割
  - 添付順制御が必要なら分割
  - 分割後の添付一覧は固定
提示内容：
  - 検証ステップラベル
  - 新しいチャットか？
  - 添付（番号のみ／種類のみ）
  - 指示文（コードブロック不可）
  - 想定結果
提示後は未実施先頭を自動実行。

## 3. 実行規則
- 指定なければ未実施先頭を自動実行。

## 4. ステップ実行
### internal
- 自動実行
- OKのみ次へ
- NGは6へ
### external
出力項目：
  - 検証ステップ：ロードマップの番号・概要のみ
  - 新しいチャット：はい / 続き
  - 添付：確定済一覧を完全ファイル名で列挙（なければ「なし」）、変更不可
  - 指示文：
      - 添付のみなら「なし」
      - 通常運用範囲のみ生成可
      - 通常運用は以下に限定：
          - 新しいチャットで共通仕様一式を添付し、共通テンプレートを生成する
          - 新しいチャットで共通仕様と共通テンプレート一式を添付し、共通テンプレートを再作成する
          - 新しいチャットで共通仕様と共通テンプレート一式を添付し、共通プロンプトを生成する
          - 新しいチャットで共通仕様と共通テンプレートと共通プロンプト一式を添付し、共通プロンプトを再作成する
      - 添付内容は記載しない
  - 回収内容：
      - 「検証チャットの応答全文を回収しこのチャットに貼ってください」
        または
      - 「次へ」と指示してください
  - 想定結果：成功条件を簡潔に記載

## 5. 回収評価
- OK / NG を明示
- OK→次へ
- NG→6へ

## 6. 調査
- 内部補正禁止
出力：
  - 検証ステップ（番号・概要のみ）
  - 指示文（未提示情報含め禁止）
  - 回収内容：「検証チャットの応答全文を回収しこのチャットに貼ってください」

## 7. 原因特定
- 原因特定
- 不十分なら6へ戻る

## 8. 仕様修正
- 人間と対話して共通仕様修正
- 修正完了後：
  - 作業指示チャット自体を新しいチャットで再開すべきか判断
  - それ以外は2へ戻る

# 【齟齬なし判定】
共通テンプレート：
  - 共通仕様構造準拠
  - LLM-MANAGED規約・再作成不変条件規約準拠
共通プロンプト：
  - 必須指示要素網羅
  - LLM-MANAGED規約・再作成不変条件規約準拠
表現差は齟齬としない。

# 【禁止事項】
- 未添付仕様の補完・仮定
- NGを内部解釈して進行すること
```

## 5. 付録（理解・維持用）

本章は、**本手順を使うために必須ではない**。  
理解の補助および、将来的な文書維持・再構築のために付す。

### 5.1 検証挙動の位置づけ

以下の挙動は、本書が新たに定義するものではなく、  
**HLDocS 共通仕様から一意に導かれる結果**である。

- 共通仕様の一部のみが提示された場合  
  → 生成は開始されず、成立可否の判定に留まる

- 想定外の結果が得られた場合  
  → 内部推論で修正を行わず、  
     必ず検証チャットに対する質問生成を行う

- 調査の結果、仕様修正が必要と判断された場合  
  → 修正後、検証は最初からやり直される

本書は、これらの挙動を**新たに規定するものではなく**、  
「どう始めればこの状態に入れるか」を示すに過ぎない。
