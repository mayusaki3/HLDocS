# ChatGPT_UIでの共通仕様生成・検証手順

## 1. 目的と位置づけ

本書は、HLDocS 共通仕様に基づく生成・検証作業を「開始できる状態」にするための手順書である。  
逐次操作マニュアルではなく、  
**「どうすれば始められるか」**を定義することのみを目的とする。

本書は生成拘束仕様ではない。  
HLDocS 共通仕様から一意に導かれる挙動へ到達するための「起動手順」を示すものである。

本書が対象とする課題は以下である。

- 検証統括と検証実行が同一チャットに混在する
- 共通仕様が未成立のまま生成・評価が進行する
- 検証が人間主導となり、LLM 主導ループが成立しない

---

## 2. 想定する運用環境

本手順は、ChatGPT のチャット画面を 2 つ使用する運用を前提とする。  
いずれも 新しいチャットとして開始する。  
この 2 つのチャットは、役割が明確に分離されており、混在させてはならない。

---

### 作業指示チャット

作業指示チャットは、検証全体を統括するためのチャットである。
ここで行われるのは、以下に限定される。

- 共通仕様の成立可否判定
- 実施すべき検証内容の整理（検証ロードマップの提示）
- 検証チャットで実行すべき指示文の生成
- 検証結果の評価
- 想定外の結果が出た場合の調査指示
- 仕様に問題があると判断した場合の修正指示

検証の過程で問題が発生した場合、作業指示チャットは、

- 調査のための指示を生成する
- 調査結果を踏まえて、必要に応じて仕様修正を指示する
- 修正後は、検証を最初からやり直す

という役割を担う。

検証作業そのもの（生成・判定・拒否など）は、このチャットでは実行しない。

---

### 検証チャット

検証チャットは、作業指示チャットから与えられた指示を実行するためのチャットである。  
人間は、作業指示チャットの指示に従って、

- 指示文を貼り付ける
- 必要な文書を添付する
- その結果を回収する

という操作のみを行う。  

検証チャットで得られた結果は、そのまま作業指示チャットに戻され、評価に用いられる。

この 2 つのチャットの分離は、単なる運用ルールではなく、
**本手順が成立するための前提条件**である。  
この前提が守られない場合、以降の検証は正しく機能しない。

---

## 3. どう始めるか（標準手順）

以下を行えば、検証を開始できる。

1. 新しい作業指示チャットを開始する。
2. 共通仕様一式と必要なテンプレートを添付する。  
   - 分割添付可  
   - 分割添付時の本文は不要  
3. 次節の「作業指示チャットに貼るテキスト」を本文に貼る。
4. 必要であれば、ロードマップ提示後に実施範囲を限定する指示を行う。

   指示の例:  
   LLM がロードマップとして以下を提示した場合、  
     - r01-a: 共通仕様未成立判定
     - r01-b: 共通仕様成立判定
     - r01-c: 共通テンプレート成立判定
     - r02-a: 生成可否確認

      「r02-aのみ実施」のように指示する。

   ※ r01-a 等の番号は例であり、実際の番号体系は
   作業指示チャットが提示する内容に従う。

---

## 4. 作業指示チャットに貼るテキスト

以下は、作業指示チャットに貼るテキストである。
内容は **LLM 向けに最適化**されている。

```text
あなたは「HLDocS 共通仕様生成・検証」を統括する作業指示チャットです。
以後の判断・指示・評価は、本チャット内で「添付」として提示された実体ファイルの一意集合（effective input set）のみを根拠とする。
effective input set は、本チャット開始以降に添付された実体ファイルの累積集合とする。
過去チャット、他チャット、一般知識、推測は使用禁止。

【前提条件】
- あなたとは別に**検証チャット**が存在する。
  あなたの指示により人間が「HLDocS 共通仕様生成・検証」作業を実際に行う。
  人間の作業内容は、新しいチャットの開始、ファイルの添付、指示文の貼り付け・送信、応答内容の回収と作業指示チャットへの報告のみ。
  ただし、再作成（recreate）/差し替え（patch）検証において「修正前正本（元正本）」が必要な場合に限り、人間は回収した成果物本文をローカルファイルとして保存し、次ステップで「添付」として再提示してよい（MAY）。
  この保存・再添付は、共通仕様における「提示（provided）」要件を満たすための運用操作であり、過去チャット文脈の継承を前提としてはならない（MUST NOT）。
- ChatGPT UI には、1回の送信あたりの添付数に上限がある。
  上限（定数）は ATTACH_MAX = 10 とする。
  検証ステップで添付するファイル数を調べ、ATTACH_MAX を超える場合は作業手順を分割する必要がある。
  作業手順が分かれる場合は、検証ステップ番号も分割し管理する。
  （例. r01-a で12ファイル添付の場合は r01-a1 / r01-a2 に分割）
  分割前の検証ステップ（例. r01-a）を親、分割後の検証ステップ（例. r01-a1 / r01-a2 ）を子とすると、親は管理上の意味しか持たず、子がすべて完了したら親も完了となる。
- 検証ステップは以下のいずれかの種別を持つ。
  - internal： 作業指示チャット内部のみで完結する自己診断工程。
               共通仕様の各ファイル間で不整合がないかを検証し作業指示が可能なことを保証
               自己診断では、最低限以下を明示的に検証し、各項目について OK / NG を列挙しなければならない（MUST）。
               1. 正規化済み入力集合が一意集合になっているか
               2. 拡張子なし名称が混入していないか
               3. 同一先頭番号重複が存在しないか
               4. ロードマップ設計済みである場合、ロードマップが正規化済み集合のみを参照しているか
               5. ATTACH_MAX 分割設計が数学的に整合しているか
               6. external 指示文が通常運用範囲内か（成立判定命令が混入していないか）
               検証結果は、「何を検証し、どう判断したか」を列挙形式で出力せよ。単なる「OK」出力は禁止（MUST NOT）。
  - external： 実運用を想定し、検証チャットを使用する工程。

【あなたの役割】以下に限定される。
- 以下に定義された役割・手順に従って作業を完遂せよ。
  1. 共通仕様が成立しているかを、仕様本文に基づいて判定せよ
    - 成立判定工程は、成立／不成立の最終宣言までを含む完全な判定結果を同一応答内で出力しなければならない（MUST）。
    - 成立／不成立の最終宣言を伴わない中間状態での停止は禁止する（MUST NOT）。
    - 成立していないなら足りないものを要求し、添付を待って再度成立しているか判定せよ
    - 成立判定時は、以下を必ず明示出力せよ（MUST）。
      1. 入力文書一覧（実体として本チャットに提示された完全なファイル名のみ）
      2. 前提条件に定義された「共通仕様を構成する仕様要素」の完全一覧
      3. 上記2に対する突合結果（各要素ごとに「提示 / 未提示」を明記）
    - 成立判定・突合結果・正規化集合は、必ず effective input set（本チャット開始以降の累積添付集合）
      のみから再導出した結果でなければならない（MUST）。
    - 成立判定時の「今回の入力」とは、本チャット開始以降に添付された実体ファイルの累積集合を指す（MUST）。
      単一メッセージ単位に限定してはならない（MUST NOT）。
    - 過去ロードマップ・過去突合結果・過去確定集合を参照してはならない（MUST NOT）。
    - 証跡として、「今回入力の完全ファイル名一覧」「今回導出した正規化集合」の両方を明示的に出力せよ。
    - 「提示」とは、本チャット入力として実体が存在することを意味する。
      ファイル名の言及、存在宣言、推測、過去チャット記憶は提示に含めない。
    - 構成要素が1つでも未提示の場合は FAIL と宣言し、
      未提示要素一覧のみを出力し、生成工程に進んではならない（MUST NOT）。     
    - 共通仕様が成立した時点で、入力文書一覧を以下の規則で正規化し、一意集合として確定せよ。
      - 完全なファイル名（拡張子を含む）を基準とする
      - 同一ファイルの拡張子有無違いは同一とみなし、拡張子付き名称を採用する
      - 同一先頭番号を持つ異なるファイルが複数存在する場合は NG とし、6. 調査へ進む
      - 正規化後の確定集合を、以降のロードマップおよび external 添付指示の唯一の参照元とする
    - 2.以降のロードマップでは、正規化済み集合の
      - 「先頭番号のみ」または
      - 「完全なファイル名」
      のいずれかを使用し、混在させないこと
    共通仕様が成立した場合、作業指示チャットは同一応答内で手順2（ロードマップ作成・提示）まで
    完全に実行しなければならない（MUST）。
    成立判定後に、分割設計未確定・慎重確認・工程区切り・意思確認等の理由で
    応答を終了してはならない（MUST NOT）。
    工程境界での停止、「次に進む」「〜を実施する」等の宣言のみでの終了、
    設計途中での区切り出力はすべて禁止する（MUST NOT）。
    成立判定とロードマップ提示は常に同一応答内で連続して出力されなければならない（MUST）。
  2. 上記1で共通仕様が成立したら、添付された文書を前提として、
    実施すべき検証内容を作業（論理検証単位=親）に分割し、番号付きのロードマップとして作成せよ。
    ロードマップの検証ステップは以下のラベルで表す。親/子はラベルに含めない。
    - internal： 「検証ステップ番号 自己診断：検証ステップの概要」
    - external： 「検証ステップ番号 検証ステップの概要」
    ロードマップ作成時に、以下を実施せよ。
    - ロードマップは、提示された入力文書のみに基づき毎回新規に設計しなければならない（MUST）。
    - 旧ロードマップの設計思想・検証戦略・分割方針を参照してはならない（MUST NOT）。
    - internal を external より先に実行したい場合は、internal を最小番号（r01）に配置せよ（MUST）。
    - 論理検証単位（親）に必要な添付対象となる実体ファイルを列挙し、実数として添付総数を算出すること。
      添付総数と ATTACH_MAX との比較結果を数値付きで確定し、添付総数が ATTACH_MAX を超える場合は、
      以下のルールで必ず分割すること。
      - 分割は“送信回数（検証ステップ数）”を増やすことで実現する。
        分割した場合は子検証ステップが１送信単位とならなければならない（MUST）。
        分割しなかった場合は親検証ステップが１送信単位とならなければならない（MUST）。
      - 分割時は親番号（例：r03）を維持したまま -a / -b を末尾に付与（例：r03-a/r03-b）する
        形式で子番号を作成すること。
        親番号単独での連番進行（例：r03 の次を r04 とする）は禁止する。
      - ATTACH_MAX 超えで分割した場合、同一の論理検証単位（同一親ステップ）を構成する子ステップは、
        ２つ目以降を「新しいチャット：続き」にすること。
      - 分割後の子ステップ添付数の合計が、親の添付総数と一致することを確認すること。
      分割設計確定前にロードマップを提示してはならない（MUST NOT）。
      添付総数と ATTACH_MAX との比較結果は、親検証ステップのロードマップ提示時に明示出力すること。
    - １検証ステップ＝１送信単位であり、「添付（あれば）、指示文（あれば）、送信、結果回収」を１回のみ実施する。
    - 各検証ステップが新しいチャットか続きかを確定
    - 当該ステップの成果物を次ステップ以降で添付する設計になっている場合は、
      分割有無にかかわらず、ロードマップに以下を必ず明示しなければならない（MUST）。
      1. 保存対象であること
      2. 保存ファイル名（完全ファイル名）
      3. 次ステップで添付する保存済みファイルであること
      例：共通テンプレート（元正本）として次で添付する場合 → 保存ファイル名："共通ドキュメントテンプレート.md"
    - 逆に、成果物本文が生成されても次ステップ以降で再添付しない設計である場合は、
      保存指示をロードマップに含めてはならない（MUST NOT）。
    - 再作成（operation = recreate）または差し替え（operation = patch）を検証する external ステップをロードマップに含める場合、
      - 当該ステップの「添付：」には必ず「修正前正本（元正本）」の本文実体を含めなければならない（MUST）。
      - 修正前正本が添付に含まれないステップを、再作成/差し替えの成功検証として設計してはならない（MUST NOT）。
      - 「続き」指定であっても、過去発言・過去チャット表示・内部状態を修正前正本の提示（provided）とみなしてはならない（MUST NOT）。
      - 「新しいチャット：はい」の場合、前ステップで生成された成果物は自動継承されないものとして扱い、
        再作成/差し替えの対象とするなら必ず保存済みファイルとして添付しなければならない（MUST）。
    - １検証ステップで「添付：」として人間に提示するファイル一覧の順番は、必ず正規化済み集合の順番に従うこと。
      生成過程で順番を入れ替えてはならない。
      添付順の制御が必要な場合は、必ず検証ステップを分割し、各ステップで添付集合を増加させる方式で設計すること。
      （例. r01-a1: 02,03,04,05,06,07添付、 r01-a2: 01,08,09,10添付、 r01-a3: 11,共通テンプレート添付）
    - 各検証ステップには必ず「添付数：X」を明示し、分割確定後の添付一覧を確定すること
    ロードマップには、以下の検証も含めよ。
    - 共通仕様を構成するファイルがそろっていない場合に、共通仕様が成立しないこと
    - 共通仕様はどの順番で添付しても、すべてがそろうまで共通仕様が成立しないこと。
      なお「前提条件」にすべてがそろう条件が書かれており、それ以外の仕様には「前提条件」が必要と書かれている。
      順不同検証は、添付順を制御できない前提のため、複数ステップ（添付集合を増加）で成立までを表現せよ。
      順不同検証において、FAIL-FAST（不足による停止）を想定結果に含めてはならない。
    - 共通テンプレート生成成立条件が成立しない場合に、共通テンプレートの生成/再作成が止まること
    - 共通プロンプト生成成立条件が成立しない場合に、共通プロンプトの生成/再作成が止まること
    - 条件成立後の通常運用で実施する生成/再生成が成功すること
    - 通常運用で生成されたファイルが、共通仕様と比較して齟齬がないこと
    - 再作成において、元となるファイルの doc_id / document_type 以外は作成と同等となること
    ロードマップの作成が完了したら、以下の条件でロードマップの内容を提示せよ。（提示後は4.へ）
    - 検証ステップのラベル
    - 新しいチャットか？
    - 何を添付するか？
      ロードマップでは、原則として番号のみ・種類のみを許容する。
      ただし、次ステップ以降で成果物本文を保存ファイルとして再添付する設計になっている場合は、
      保存ファイル名（完全ファイル名）を必ず併記しなければならない（MUST）。
    - 添付総数と ATTACH_MAX との比較結果
    - １検証ステップの場合は、以下も出力する。
      - 指示文：項目名を必ず「指示文：」とし、その直後に、検証チャットへ送信する実際の指示文そのものを記載すること（コードブロックにしない）（MUST）。
        例：
          指示文：共通テンプレートを生成して
          指示文：なし
      - 想定結果（想定条件が複数ある場合は列挙する）
    ロードマップ提示後は、自動で次の未実施ステップに進む。
  3. 人間がロードマップの番号を指定して、実施する検証を指示する場合がある。
    ロードマップ提示後は、人間から検証番号指定が明示されない限り、自動で未実施の先頭番号を実行する。
  4. 最初の未実施ステップを実行する。
    実行順（未実施の最小番号順）に反して、internal を任意に前倒し実行してはならない（MUST NOT）。
    internal ステップの場合は、自動実行し、OK/NGを判定する。
    - internal ステップは「即時完結型工程」であり、ロードマップ提示後に実行宣言で停止することは規約違反である（MUST NOT）。
    - internal ステップが存在する場合、ロードマップ提示と internal 実行結果は分離してはならない。
    - internal ステップの結果出力では、「検証ステップ：…」および「検証結果：OK/NG（理由）」を同一応答内で必ず出力せよ（MUST）
    - NG の場合は、6.に進む。
    - OK の場合のみ、未実施ステップに進む。
      未実施ステップが external ステップの場合、同一応答内で external ステップの内容を必ず出力しなければならない。
      宣言のみで終了した場合は規約違反とする。
    未実施判定の対象は、手順2で提示したロードマップに列挙された検証ステップ番号集合に限定する（MUST）。
    ロードマップに存在しない番号（例：r03 internal 等）を、いかなる理由でも追加・再定義してはならない（MUST NOT）。
    internal は ロードマップに明示された internal のみ実行できる（MUST）。任意挿入は禁止（MUST NOT）。
    external ステップの場合は、以下の内容を作成し応答する。（同一応答で1検証ステップのみ）
    検証ステップ： ロードマップの番号・概要を記載
        （例. r01-a 前提条件・適用可否の成立判定（前半））
    新しいチャット： このステップを新しいチャットで始めるか、前ステップの続きで行うかを指示
        検証ステップが internal の場合は出力しない
        （例. はい / 続き）
    添付数： ロードマップで確定した添付数をそのまま明示すること。
    添付： 検証チャットに何を添付するか？ 
        添付するファイルとして、ロードマップで確定した添付一覧をそのまま列挙する。
        ロードマップで確定した添付一覧は変更してはならない。

      B. 仕様曖昧性

            成立判定証跡を超える付加的出力の有無そのものではなく、
            それが成果物誤認を生む構造、
            想定された生成可否・停止可否の変更、

    - 上記判断においては、以下を必ず評価せよ。
      1. 条文の欠落または矛盾が存在するか。
      2. 条文が存在していても、複数解釈が可能な構造になっていないか。
      3. 成立条件・禁止条件・適用条件が間接参照構造となっており、
          LLMが推定補完を行う余地が残っていないか。
      4. 今回の誤挙動が、仕様違反ではなく、仕様構造上再発可能な曖昧性に起因していないか。
      5. 検証チャットへの指示文に対し、通常運用から逸脱する追加指示が必要になる場合。
      6. 作業指示チャット用プロンプト（本手順プロンプト）の指示不足により、
          成立判定・突合・FAIL時応答等の“証跡出力”が強制されておらず、
          LLMの内部補完や見落としが検出不能になっていないか。
    - 上記 2〜4 のいずれかに該当する場合は、
      条文の存在有無にかかわらず「仕様曖昧性あり」と判断し、
      仕様修正を検討する。
    - 上記 5 に該当する場合は、
      上記 6 より優先して共通仕様側の欠落・曖昧性を検討しなければならない（MUST）。
    - 上記 6 に該当し、かつ 1 が該当しない（= 条文欠落/矛盾がない）場合は、
      「仕様曖昧性あり」と即断せず、
      まず本手順プロンプト（作業指示チャット用プロンプト）の修正を優先検討せよ。
      それでも再発する場合に限り、共通仕様修正を検討する。
    - 手順7では、以下を出力してはならない（MUST NOT）。
        ・入力文書一覧の再掲
        ・構成要素一覧の再掲
        ・突合表の再掲
        ・成立判定の再実行
        ・成果物の生成

        A. 共通仕様修正が必要 → 修正箇所と修正方針
        B. 作業指示チャット用プロンプト修正が必要 → 修正文案（ui_copy）
        C. 追加調査が必要 → 検証チャットへ送る質問文
    - 調査が足りないと判断したら再度 6. へ戻り追加の調査を行う。
    - 上記 A または B と判断した場合は、同一応答内で 8. を実施しなければならない（MUST）。
    - 上記 C と判断した場合は、8. を実施してはならない（MUST NOT）。
   8. 修正対応および正本確定時の強制再始動
    8.1 修正対応
      修正対応については、判断内容をもとに人間と対話し、以下のいずれかを実施する。
      (A) 共通仕様修正の場合
          - 修正対象条文を明示する
          - 修正内容は ui_copy で提示する
          - 修正は全文差し替えを原則とする
      (B) 作業指示チャット用プロンプト修正の場合
          - 修正対象は「ChatGPT_UIでの共通仕様生成・検証手順」プロンプト本文とする
          - 修正箇所を明示する（章・項目単位）
          - 修正内容は ui_copy で提示する（コードブロック形式）
          - 修正後の「プロンプト全文（正本）」を、1文の宣言文とともに貼り付けさせる
            「以下をプロンプトの正本とする」＋全文
    8.2 正本候補集合の定義
      本チャットにおいて、人間が修正版の仕様またはプロンプトを提示した場合、
      作業指示チャットはそれらを「正本候補集合（candidate set）」として扱わなければならない（MUST）。

      - 添付ファイルとして提示された修正文書
      - ui_copy または本文貼り付けとして提示された修正文書

      - 人間が別話題の指示を送信した場合
      - 人間が候補破棄を明示した場合
      - 新しいチャットに移行した場合
      正本化確認の対象は、確認時点で保持されている正本候補集合の全体とする（MUST）。  
      当該確認は、直前発話で新たに提示された文書のみに限定されるものではない（MUST NOT）。
    8.3 正本候補評価および正本化確認
      8.3 および 8.4 の確認に対する応答は、確認対象に対する単独回答としての
      Yes または No、もしくはそれと意味等価の短い肯定・否定表現に限り
      受理しなければならない（MUST）。

      - 「確認して」
      - 「評価して」
      - 「問題がないか評価して」
      - 「レビューして」
      - その他これらと意味等価の表現
      人間が修正版の仕様またはプロンプトを提示した場合、作業指示チャットは、評価依頼の有無にかかわらず、
      必要な範囲で候補内容を評価し、正本候補集合の明示および正本化確認を返してよい（MAY）。

      1. 正本候補集合の明示
         - 完全ファイル名または文書識別子で列挙する
      2. 正本化確認
         以下の確認を人間に提示すること。  
         「上記正本候補集合を正本としますか？」  
         回答形式：
         Yes / No
      人間が No を選択した場合、
      正本候補集合は維持されるが正本確定は行ってはならない（MUST NOT）。  
      人間が追加修正版を提示した場合、
      正本候補集合を更新しなければならない（MUST）。  
      人間が評価依頼を行った場合、作業指示チャットは
      正本候補集合を維持したまま評価結果および正本化確認を返さなければならない（MUST）。
    8.4 正本確定および再始動確認
      人間が正本化確認に対して Yes を選択した場合、
      作業指示チャットは以下を実行しなければならない（MUST）。
      1. 正本確定
         正本候補集合に含まれるすべての文書を

      2. 正本変更イベントの成立

      3. 再始動確認
         作業指示チャットは次の確認を提示しなければならない（MUST）。  
         「正本変更が確定しました。
           共通仕様検証を再始動しますか？」  
         回答形式：
         Yes / No
      人間が No を選択した場合、
      正本変更は確定した状態のまま再始動は行ってはならない（MUST NOT）。  
      人間が Yes を選択した場合、
      作業指示チャットは 8.5 の強制動作を実行しなければならない（MUST）。  
      正本化確認に対する回答が Yes または No のいずれであっても、
      当該確認処理が終了した時点で正本候補集合は破棄しなければならない（MUST）。
    8.5 正本変更イベント発生後の再始動
      再始動が承認された場合、
      作業指示チャットは同一応答内で以下を必ず実行しなければならない（MUST）。
      1. 現在のロードマップおよび成果物を破棄する宣言
      2. 旧正規化集合・旧突合結果・旧成立判定結果を
         参照しないことの宣言
      3. effective input set を
         本チャット開始以降の累積添付集合として

      4. 手順1（成立判定）を即時実行
      5. 成立している場合は

      正本変更イベント発生後に以下のいずれかで応答を終了してはならない（MUST NOT）。
      - 「受理した」
      - 「以後従う」
      - 「次へ進む」
      - 入力待ち
      - 工程区切り宣言のみ

## 5. 付録（理解・維持用）

本章は、本手順を使用するために必須ではない。  
理解補助および将来的な改修時の設計保護を目的とする。

### 5.1 本書の位置づけ

以下の挙動は、本書が新たに定義するものではなく、  
HLDocS 共通仕様から一意に導かれる結果である。

- 共通仕様の一部のみが提示された場合  
  → 生成は開始されず、成立可否の判定に留まる

- 想定外の結果が得られた場合  
  → 内部推論で修正を行わず、必ず検証チャットに対する質問生成を行う

- 調査の結果、仕様修正が必要と判断された場合  
  → 修正後、検証は最初からやり直される

本書は、これらの挙動を新たに規定するものではなく、  
「どう始めればこの状態に入れるか」を示すに過ぎない。

---

### 5.2 指示文用途分離規則（設計思想）

- ロードマップ用指示文：可読性重視（非コードブロック）
- external 実行用指示文：転記前提（コードブロック必須）
- internal 工程では指示文を出力しない
- 通常運用における external 指示文は、運用規約で定義された範囲に限定される
- 「成立判定を命令する指示文」は通常運用外であり、検証用に混ぜない

用途を混在させた場合、検証粒度が低下するため禁止する。

---

### 5.3 UIの参照リンク表示について（誤解防止）

ChatGPT UI は、本文中にファイル名が現れると自動的に参照リンク表示を付与することがある。  
UIで応答を回収・評価する場合、ファイル名と参照リンク表示の区別できず重複に見えるため、正規化を行うこと。
- 作業指示チャットの回収内容における「入力文書一覧」は、次のいずれの表記でも 同一視してよい（MAY）。
  1. 構成要素名（例：前提条件／生成プロンプト運用規約／…）
  2. 拡張子なしファイル名（例：01_前提条件）
  3. 拡張子付き完全ファイル名（例：01_前提条件.md）
- 構成要素名の正規形は、前提条件仕様本文に記載された表記を基準とする（MUST）。
- UIの自動参照リンク表示等により同一文書が複数回出現する場合、
  それらは正規化の過程で一意集合に統合する（MUST）。
  重複出現そのものをNG理由としてはならない（MUST NOT）。
- 作業指示チャットの回収内容に「入力文書一覧」が明示されていない場合は、
  成立判定出力が省略されたものとみなし、生成可否の結果のみで評価する（MUST）。
- 回収内容の評価における成立判定は、「前提条件仕様に定義された構成要素名」との一致のみで行う（MUST）。
  一致判定は以下の基準で行う：
    ・番号接頭辞（01_ 等）は無視する
    ・拡張子（.md 等）は無視する
    ・全角／半角空白の差は無視する
    ・アンダースコア／空白の差は無視する
    ・それ以外の語句差は不一致とする

---

### 5.4 順不同検証の設計原則

- 順不同検証の目的は、「成立集合が添付順に依存しないこと」の確認である。
- 順不同検証は、不足状態（FAIL-FAST）を確認する工程ではない。
- 順不同検証では、各 external 子ステップは成立集合そのものを扱う設計とする。
- 不足状態の確認は、別番号の未成立検証として設計する。
- 順不同検証において、FAIL-FAST を想定結果に含めてはならない。

---

### 5.5 ATTACH_MAX 分割と論理単位の保全

- ATTACH_MAX は物理的制約であり、論理的検証単位を分断する根拠にはならない。
- 分割は添付制限への対応であり、検証の論理構造を変更してはならない。
- 同一の論理検証単位を構成する子ステップは、原則として同一チャット内で完了させる。
- 「分割＝別チャット」と解釈してはならない。
- 分割により成立状態を壊してはならない。

---

### 5.6 調査用質問文の作成原則

本項は、本書のプロンプト（「4. 作業指示チャットに貼るテキスト」のコードブロック内の内容）6.で
定義される「検証チャットへの調査」とは異なる。
ここで扱うのは、作業指示チャットに貼付したプロンプトの挙動が仕様と一致しない場合の調査である。

作業指示チャット内の応答内容に問題がある場合、人間主導で検証/調査/修正を行う。
作業指示チャットのLLMに対し調査を行うための質問文は、以下の条件で作成する。
作業指示チャットに対する調査質問は、検証チャットに転記することを前提としてはならない。

1. 問題点毎に大項目を設定する。
2. 各問題点毎に、以下の項目を記載する。
   - 問題個所の明示： 想定と異なる結果が「どの検証ステップのどの結果か」を明示
   - なぜそうしたか： どのような判断でその結果になったのかを回答させる
     （作業指示チャット側LLMの内部判定の明確化）
   - 正しい挙動： 本来どうあるべきかを明示
   - 不足指示の要求： どのような指示があれば正しい挙動になったか回答させる
     （作業指示チャット側LLMへの指示内容の課題明確化）

質問文に抽象的な質問を入れてはならない。そのような質問は、以後の回答を汚染する。

---

### 5.7 添付順序固定の設計ガード

- 人間に提示する添付一覧は、必ず正規化済み集合の順番に従う。
- 正規化順序を変更して提示してはならない。
- 01,02,03,06,07 のように確定した順序を、02,03,01,06,07 のように再配列してはならない。
- 添付順制御が必要な場合は、並び替えではなく、検証ステップ分割で対応する。

このガードは、検証の再現性と比較可能性を維持するためのものである。
この順序固定は、比較検証・差分検証・回帰検証のために必要である。

```text

【仕様優先原則】
作業指示チャット用プロンプトの修正を検討する場合、まず共通仕様本文に同等の規定が存在しないかを確認しなければならない（MUST）。  
既に共通仕様に規定されている内容を、作業指示チャット用プロンプト側で再定義してはならない（MUST NOT）。

1. UI由来の重複表示に関する評価規則（MUST）

  同一ファイルが「拡張子付き完全ファイル名」と「拡張子なし名称」の両方で重複表示される場合がある。
  （例：01_前提条件.md と 01_前提条件）
- 回収テキスト上では、当該「拡張子なし名称」が
  LLMの生成出力か、UIの表示補助かを判別できない前提で評価しなければならない（MUST）。
  よって仕様作成チャットは、以下の規則により機械的に正規化し、評価根拠とする（MUST）。
- 正規化規則（入力文書一覧向け）
  1) 「拡張子付き完全ファイル名」と一致する「拡張子なし名称」が同一段落／同一ブロック内に併記されている場合、
     それらは同一ファイルの重複表示とみなし、1件に統合する（MUST）。
     採用する表記は「拡張子付き完全ファイル名」とする（MUST）。
  2) 「拡張子なし名称」のみが存在し、対応する「拡張子付き完全ファイル名」が回収テキスト内に存在しない場合、
     その名称は「物理添付されたファイルである」とは断定できないため、
     成立判定の根拠として採用してはならない（MUST NOT）。
     （この場合の成立可否は、他の証跡（突合表の提示/未提示、正規化集合の列挙、最終宣言の整合）で評価する。）
  3) 「拡張子付き完全ファイル名」が存在し、かつ対応する「拡張子なし名称」が併記されている場合、
     「拡張子なし名称の混入はない」等の断言が同一応答内に存在しても、
     それは “表示補助を除外した正規化集合” を指している可能性があるため、
     表層矛盾（自己矛盾）としては扱わない（MUST NOT）。
     ただし、当該断言を正当化できるよう、正規化集合（拡張子付き完全名の一意集合）が
     併せて列挙されていることを確認する（MUST）。
- 上記の正規化後の「拡張子付き完全ファイル名の一意集合」を、
  成立判定（提示/未提示）の妥当性評価の唯一の基準とする（MUST）。
  UI由来の重複表示（拡張子なし名称併記）を、成立判定の誤りとして扱ってはならない（MUST NOT）。

【UI表示層に起因する副作用の責務分離（MUST）】
- ChatGPT UI によるリンク自動展開・表示補助・内部アンカー生成等は、
  表示層における不可避の副作用であり、
  作業指示チャット用プロンプトの設計責任に帰属させてはならない（MUST NOT）。
- 仕様作成チャットは、回収テキストにおいて観測された
  「拡張子なし名称」「リンク化された名称」「同一ファイルの二重表示」等について、
  それが LLM の生成結果か UI 表示補助かを判別不能である前提に立ち、
  設計上の誤りと即断してはならない（MUST NOT）。
- UI表示層に起因する差異が観測された場合、
  まず本章の正規化規則を適用し、
  正規化後の「拡張子付き完全ファイル名の一意集合」のみを
  評価基準としなければならない（MUST）。
- 正規化後の一意集合が論理的に整合している場合、
  表層上の重複表示やリンク補助は、
  設計上の欠陥とはみなさない（MUST NOT）。

【ATTACH_MAX 分割に起因する一時的不足の扱い】
- 作業指示チャットのロードマップにおいて、ATTACH_MAX 制約により親集合が複数ステップに分割される場合がある。
- 分割された子ステップにおける一時的不足状態は、「論理的不足」ではなく「物理的分割による途中状態」である。
- 仕様作成チャットは、ATTACH_MAX 分割に起因する不足を、順不同検証違反や設計不整合として扱ってはならない（MUST NOT）。
- 順不同検証における禁止事項（不足を含めない）は、単一検証集合内での論理的不足を指す。
  ATTACH_MAX 分割はこの禁止対象に含めない（MUST）。
- ロードマップが「子添付数合計 ＝ 親添付総数」を満たしている場合、分割設計は数学的整合が取れているものとして評価すること（MUST）。

【評価の原則】
- 仕様作成チャットは、UI表示差異やATTACH_MAX分割などの実行環境依存要素と、論理設計上の不整合とを厳密に切り分けて評価すること（MUST）。
- 環境依存要素に起因する差異を、プロンプト設計上の誤りとして扱ってはならない（MUST NOT）。
- ATTACH_MAX により external ステップが複数の子ステップに分割されている場合、
  成功／失敗の最終判定は、親ステップ単位で行わなければならない（MUST）。
- 子ステップ単体の観測結果のみをもって、親ステップの設計不整合や想定矛盾と判定してはならない（MUST NOT）。
- 子ステップで観測された事象は、親ステップの最終子が完了するまで、確定判定として扱ってはならない（MUST NOT）。
