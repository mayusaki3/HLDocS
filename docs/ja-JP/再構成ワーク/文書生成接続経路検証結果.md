# 文書生成接続経路検証結果

## 1. 対象と方法

- 検証対象: developの文書生成接続仕様、変更対処Workflow、変更検証Workflow、情報参照Workflow、文書生成SubFlow仕様
- 検証開始SHA: `1049ff4a783e2ba9e96f9c14115ac920cdcf2495`
- 方法: GitHubから各正本文書を取得し、接続契約・禁止条件を静的に照合
- 限界: LLMの仕様解釈に基づく静的照合であり、実装されたSubFlowランタイムを起動したテストではない

## 3. 受入検証との区別

DGEN-01〜18は受入シナリオとして未実施。上記は仕様の存在と整合の確認であり、受入PASSを意味しない。実際のSubFlow呼出し、State/Plan実行、権限拒否の動作、文書生成・保存・再取得は未実施である。

本結果ファイルをGitHubに保存し再取得できた場合、その事実はGitHubファイル操作の疎通確認に限定する。HLDocS文書生成SubFlow経由の保存を証明しない。

## 4. 次の検証条件

- Work PurposeとTarget List、State/Planの初期状態、Restriction Contextを固定する
- 変更対処Workflowが4つの文書生成SubFlowを順に呼ぶ実行証跡を取得する
- 変更検証Workflowが保存済み成果物を独立に再取得し、差分と構造を照合する
- 情報参照Workでは保存要求が拒否されることを実行確認する
- 対象SHAと終了SHA、入力・実結果・判定・Issue・再実行を記録する

## 5. State/Planの静的到達性と実行境界（追加）

- 照合対象SHA: `47c3af71d1ce0f46b0cfa645b56a13761cf49cc5`。
- 変更Stateのavailable_workflowsとdefault_workflow_planは「変更調査 → 変更対処 → 変更検証」で一致。情報参照Stateは「情報参照」のみを登録する。
- State Machine定義は待機から変更・情報参照へのWork生成を規定し、Workflow共通仕様は開始時にState登録・Plan所属・PENDING・同時ACTIVE最大1件・Restriction適用を要求する。
- 文書生成SubFlowは独立Workflowとして登録せず、変更対処Workflowから必要に応じて呼び出す。情報参照Workflowでは確認用派生情報のみを扱う。
- Restriction Set登録簿には再構成済み個別Setが存在しない。これは制限検査の省略許可ではなく、実行時のRestriction ContextとCore検証を別途確認する必要がある。
- **判定**: State/Planの接続仕様は静的に整合。ただしExecution Context、Current Work、Target List、実行可能なSubFlowランタイムと呼出しログを取得していないため、実行時到達性は未検証。DGEN-14〜18の受入PASSにはしない。
- 実行可能な呼出し手段が存在しない場合は、実行テストを実施したと装わず、具体的な呼出しインターフェースまたはランタイムを確認してから再開する。
