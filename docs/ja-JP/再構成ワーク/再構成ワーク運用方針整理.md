# 再構成ワーク運用方針整理

本書は目次から退避した運用方針の検討記録である。内容は現行のCore仕様および関連する正本仕様と照合し、必要な規範は正本specへ移管する。**本書のみを根拠に規範が成立したとみなさない。**

## セルフ検証仕様

v0.7.0で再構成する各主要仕様領域は、確定前にその領域自身の仕様体系を再検証するためのSelf Validation Specification(セルフ検証仕様)を持つことを基本とする。

Self Validation Specificationは`document_type: spec`とする。HLDocSが生成した成果物に対する検証トレーサビリティを定義する`document_type:testspec`とは別の責務である。

各Self Validation Specificationは、その文書単独と現在のリポジトリ上の正本から、新しいLLMセッションでも検証を開始できなければならない。少なくとも次を各仕様自身に明記する。

- 検証対象となる現在の正本
- 検証に必要な前提および入力
- 既知の検証項目またはシナリオ
- 期待結果および判定方法
- 既知項目だけでなく未知の問題も探索すること
- 過去チャットへ依存しないこと
- LLM_WORKSPACEを検証根拠の正本として扱わないこと
- 不足情報を推測補完しないこと
- 再検証条件
- 検証結果として記録すべき内容

過去の検証結果は証跡および比較資料であり、現在のPASS判定を代替しない。

仕様領域を再構成ワークから本来の配置へ移行する場合、対応するSelf Validation Specificationも当該仕様領域とともに移行する。

## 再構成仕様の確定と移行方針

v0.7.0再構成中の仕様は、責務境界、横断整合性および必要な検証を確認した単位で確定してよい。

確定した仕様は`再構成ワーク/仕様/`へ恒久的に残さず、`develop`ブランチ上の本来の仕様配置へ移行する。再構成ワーク側には、必要な設計記録および移行記録を残す。セルフ検証結果は仕様と同階層の専用ディレクトリで管理する。

移行はコピーによる二重管理ではなく、現在採用する仕様の配置を本来の位置へ切り替えるものとする。

`main`ブランチはv0.6.1系の安定運用版として維持し、v0.7.0全体が完成するまで`develop`から`main`へマージしてはならない。

v0.7.0完成前に本来の位置へ移行した仕様は、`develop`上のCore(中核)機能および次期仕様の評価用であり、v0.7.0全体の完成または安定運用を示さない。

## v0.7.0リリース時の再構成ワーク整理

- v0.7.0のリリース準備までは`再構成ワーク/`を維持する。作業途中に名称変更しない。
- リリース時、確定した仕様およびセルフ検証仕様は`仕様/`へ、当該リリースの最終PASS結果は`セルフ検証結果/`へ配置する。
- `再構成ワーク/`にある確定済み仕様の複製、解決済みの検討資料、途中の検証結果は現行ツリーから除外する。履歴はGitで追跡する。
- 次版へ引き継ぐ情報のみ`docs/ja-JP/次版開発ワーク/引継ぎ.md`へ移し、`再構成ワーク/`は廃止する。
- 引継ぎには現行版・次版の識別、未対応事項、許容した既知の制約、次版の検討事項、関連するIssue・仕様・コミットSHAを記載する。未解決問題は必要に応じてIssueまたは仕様の未確定事項へ記録する。
- `次版開発ワーク/`は提案・検討・作業中の情報を扱い、現行仕様の正本やセルフ検証PASSの根拠として扱わない。
- 次版のリリース時にも同様に整理し、次々版へ必要な最小情報のみ残す。

## セルフ検証結果の管理とリリースゲート

- セルフ検証仕様は`docs/ja-JP/仕様/`に置き、結果は同階層の`docs/ja-JP/セルフ検証結果/`に置く。結果は対象リリースバージョン別・領域別に分類する。
- 仕様作成・変更・確認時の結果は開発途中の一時記録とし、最終リリース成果物には含めない。未解決問題は削除前にIssueまたは正本の未確定事項へ移す。
- `main`へのマージは、リリース候補の全必須セルフ検証がPASSであり、領域横断検証もPASSで、未解決のリリース阻害事項がない場合に限る。UNDEFINED/BLOCKED/FAILまたは結果欠落があれば禁止する。
- 各最終結果には、対象リリースバージョン、検証日時、対象ブランチ、**検証対象コミットSHA**、検証終了コミットSHA、セルフ検証仕様のパスと対象版、対象仕様、検証方式、項目別判定・根拠、未解決事項、修正コミット、再検証状況を記録する。
- 検証後にコミットが変わった場合は差分の影響分析を記録し、影響がある領域を再検証する。検証対象SHAとマージコミットSHAの機械的一致は要求しない。
- リリース時には対象バージョンの最終PASS結果のみ残し、開発途中の結果と別バージョンの結果を現行ツリーから除く。過去リリースの証跡はGitタグ・履歴で参照する。
- 過去結果の未記録SHAを推測補完したり、旧PASSを現行PASSへ流用したりしない。
- この規則の適用前に作成した既存結果は履歴資料として保持できるが、リリース判定には再検証が必要である。
