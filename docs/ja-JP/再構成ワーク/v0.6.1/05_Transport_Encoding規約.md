# Transport Encoding 規約

本書は、LLM が提供する UI 上で **安全に提示・回収**できる形でドキュメントを扱うための  
**Transport Encoding（搬送・提示方式）** を定義する。

本規約は、ドキュメントの内容・意味・正規性を規定するものではなく、  
**UI や回収手段の制約下で「どう提示するか」だけを定義**する。

本書は、「HLDocS 前提条件」という仕様が参照可能である場合にのみ適用される。
- 「HLDocS 前提条件」が入力として与えられていない場合、  
または当該仕様に基づく適用可否が確定していない場合、  
本書に基づく判断・生成・再作成・工程実行を行ってはならない。
- この場合、許可されるのは、  
提示された文書の受理および存在確認、  
ならびに前提条件が未参照または未確定である旨の通知のみとする。
- 「HLDocS 前提条件」が入力文書一覧に含まれない場合、生成・再作成・成果物提示を一切行ってはならない。

---

## 1. 背景（Why）

### 1.1 何が問題か（Problem）

- UI 上でのコピー・貼り付け時に、Markdown が意図せず変形・欠落し、  
  回収対象となる内容が破損することがある。
- 特に、コードブロック・引用・箇条書きが混在する文書では、  
  UI の都合で構造が崩れる可能性が高い。

### 1.2 なぜ起きるか（Cause）

- UI は Markdown を「文字列」ではなく「レンダリング結果」として扱う局面がある。
- フェンス記号やインデントが UI 側で再解釈され、  
  **元の Markdown が保持されない**場合がある。
- 長文では、部分コピーによる回収失敗も起こり得る。

### 1.3 何が必要か（Requirement）

- UI 上で **成果物単位**として扱える提示方式
- 正規内容と提示用表現を分離できる仕組み
- 復元可能（roundtrip）であること

### 1.4 どう解決するか（Approach）

- 内容そのものは変更せず、提示方法のみを切り替える。
- UI 制約がある場合のみ Transport Encoding を適用する。
- 回収後は提示用表現を復元し、内容として保存する。
- Transport Encoding は **成果物単位**で適用される。

---

## 2. 定義

- Transport Encoding は **提示・回収のための表現上の取り決め**である。
- Transport Encoding は **ドキュメントの意味・構造を変更してはならない**。
- Transport Encoding は **復元可能（roundtrip）**でなければならない。
- 本規約における「成果物」とは、**1つの正本ドキュメント（1ファイル）**を指す。

### 2.1 成果物提示単位の原則（MUST）

- 成果物は、常に「1つの正本ドキュメント単位」で提示されなければならない（MUST）。
- 各成果物は、提示形式に依存せず、単独で完全に回収可能でなければならない（MUST）。
- 提示方式（true_out / ui_copy / download）に関係なく、
  成果物の開始位置・終了位置・境界が一意に識別可能でなければならない（MUST）。
- UIレンダリングや表示変換によって、
  成果物の構造・トークン・境界が失われる形式で提示してはならない（MUST NOT）。
- 成果物は、UIレンダリングを経ても内容が変化しない形式で提示されなければならない（MUST）。

---

## 3. 責務境界（Scope & Boundary）（MUST）

### 3.1 Transport Encoding の責務（MUST）

- Transport Encoding は、**生成済みの成果物内容**を  
  **どの形式で提示・回収するか**のみを定義する。
- Transport Encoding は、UI 制約下での **安全な提示・回収**を目的とする。
- Transport Encoding は、**成果物単位での提示と回収の成立**を保証する。
- Transport Encoding は、提示方式の選択に関わらず、
  成果物が単独で回収可能な提示単位であることを保証しなければならない（MUST）。

### 3.2 Transport Encoding が関与しない事項（MUST NOT）

Transport Encoding は、以下の事項に **一切関与してはならない**。

- document_type の意味論
- spec / template / prompt の責務・内容
- meta / apply を含む生成フロー
- LLM の判断・生成内容・正規性
- 成果物の生成個数や生成順序

### 3.3 他仕様との関係（MUST）

- Transport Encoding は、以下の仕様を **上書き・補完・再解釈してはならない**。
  - 前提条件
  - 生成プロンプト運用規約
  - 共通ドキュメント構造
  - document_type 別仕様
- transport の指定は、**提示方式の選択**にのみ影響し、  
  **ドキュメントの意味・構造・生成可否条件に影響を与えてはならない**。

## 4. 検証レイヤ定義（MUST）

成果物の検証は、以下の2つのレイヤで実施されなければならない（MUST）。

### 1. 生成検証（LLM出力）

- 対象：LLMが生成した生テキスト
- 検証内容：
  - 文書構造
  - 固定トークン
  - 境界
  - 完全一致

### 2. 表示検証（UIレンダリング後）

- 対象：UIにより表示された結果
- 検証内容：
  - 構造破壊の有無
  - トークン変形の有無
  - 回収可能性

### UIによる変形（抽象定義）

UIレンダリングにより、以下が発生し得る：

- Markdown構文の変換
- 装飾記号の除去または変形
- コメントの圧縮または非表示
- トークンの可視表現の変化

これにより、原文との一致が失われる可能性がある。

### UI変形の判定基準（MUST）

以下のいずれかが発生した場合、
当該提示は不正とみなさなければならない（MUST）。

- 固定トークンの文字列一致が失われている
- アンダースコア等の構造記号が除去または変形されている
- 階層リンクがリンク構文として再解釈されている
- HTMLコメントが非構造テキストとして扱われている

### 禁止事項

以下の状態を許容してはならない（MUST NOT）：

- UI表示において構造またはトークンが変形する形式で提示すること
- 回収不能または検証不能な形式で提示すること

### 検証責務（MUST）

本章で定義する検証レイヤは、
成果物の正当性を担保するために必ず実施されなければならない（MUST）。

- 生成検証は、生成された生テキストを対象とする。
- 表示検証は、提示後の表示結果を対象とする。

これらは異なる検証対象であり、
同一のものとして扱ってはならない（MUST NOT）。  
また、いずれか一方のみの検証結果をもって、
成果物の正当性を確定してはならない（MUST NOT）。  
UIレンダリングによる構造破壊の回避は、
Transport Encoding の選択責務により実現されなければならない（MUST）。  
したがって、表示検証で検出される破壊状態は、
Transport Encoding の選択誤りとして扱わなければならない（MUST）。

## 5. transport タグ一覧と意味（MUST）

本章は、Transport Encoding において使用可能な  
**transport 指定値（ENUM）**と、その意味・制約を定義する。

### transport = true_out

**意味**

- Transport Encoding を適用せず、内容をそのまま提示する。
- true_out は、構造・トークン・境界に影響を与えない単純テキストに限り使用される（MAY）。

**動作**

- Markdown を変換せず出力する。
- 単一成果物または複数成果物の提示において、補足説明が存在する場合も、
  成果物本文の外側に明確に分離して記載しなければならない（MUST）。
- 補足説明により、成果物本文の開始位置・終了位置・回収単位が不明瞭になってはならない（MUST NOT）。
- 成果物に 固定トークン、HTMLコメント、階層リンク、または構造的Markdownを含む場合は、
  true_out を使用してはならない（MUST NOT）。
- この場合は ui_copy または download を選択しなければならない（MUST）。

例：
プレーンテキストの短文回答、ログ出力、構造を持たない単純説明文などに使用できる。

---

### transport = ui_copy

**意味**

- UI 上での表示・コピーが安定するよう、**提示用の整形を行う**。
- ui_copy は、UIレンダリングによる構造破壊を回避し、
  成果物の回収可能性を保証するための推奨手段である（SHOULD）。
- 特に、Markdown構造・固定トークン・コメント・階層リンクを含む文書では、
  ui_copy を使用することが強く推奨される（SHOULD）。

**適用単位**

- ui_copy は **成果物単位**で適用される。
- 各成果物本文は、独立した ui_copy コードブロックとして提示しなければならない（MUST）。

**動作**

- UI 制約を考慮した提示を行う。
- 意味・構造の変更は禁止する。
- ui_copy の整形は、復元可能（roundtrip）でなければならない。

#### ui_copy 標準整形方式（MUST）

ui_copy が適用される成果物ごとに、LLM は以下の  
**標準整形方式を必ず使用**しなければならない。

- 各成果物本文は、単一のコードブロックとして出力すること。
- 各コードブロック内には、復元可能（roundtrip）な Markdown 全文
  （当該成果物のみ）を格納する。
- 補足説明が存在する場合も、当該成果物本文の外側に明確に分離して
  記載しなければならない（MUST）。
- 補足説明により、当該成果物の開始位置・終了位置・回収単位が
  不明瞭になってはならない（MUST NOT）。
- 見出し・箇条書き・区切り線・コメント等は、正規の内容を保持したまま記載する。
- 整形の目的は UI 上での安定したコピーであり、
  意味・構造・論理階層・成果物境界を変更してはならない。

#### ui_copy における複数成果物提示（MUST）

- 複数の成果物を提示する場合、
  各成果物本文は独立した ui_copy コードブロックとして提示しなければならない（MUST）。
- 各コードブロックは、1つの正本ドキュメントとして
  個別に回収可能でなければならない（MUST）。
- 補足説明が存在する場合も、各成果物コードブロックの外側に分離して
  記載しなければならない（MUST）。
- 補足説明により、成果物間の境界または各成果物の回収単位が
  不明瞭になってはならない（MUST NOT）。

#### ui_copy における外側フェンス決定規則（MUST）

各 ui_copy コードブロックの外側フェンスは、  
**当該成果物本文（格納する Markdown 全文）の内容**に基づいて  
個別に決定しなければならない。

- 本文中に出現する「連続バッククォートの最大連続数」を M とする。
- 外側フェンスのバッククォート連続数 N は **必ず M + 1** とする。
- 本文中にバッククォートが一切出現しない場合は M = 0 とみなし、N = 3 とする。
- 外側フェンスの開始行・終了行は **フェンス記号のみ**の1行とし、  
  言語指定や追加文字列を付けてはならない。

#### 禁止事項（MUST NOT）

- 本文に含まれるコードフェンスを、置換・削除・改変してはならない。
- 本文に含まれるコードフェンスを、インデント等へ変形してはならない。
- 外側フェンスに言語指定や追加文字列を付与してはならない。
- 異なる成果物の内容を、1つのコードブロックに混在させてはならない。

---

### transport = download

**意味**

- UI コピーを前提とせず、**ファイルとして回収**する。

**動作**

- 内容を成果物として生成する。
- zip や単体ファイル等、回収可能な形式を提供する。
- 複数成果物を同時に扱う場合にも使用できる。
- 補足説明が存在する場合も、成果物ファイル自体には混在させてはならない（MUST NOT）。
- 補足説明は、成果物ファイルとは別の提示要素として分離されなければならない（MUST）。

---

## 6. 禁止事項（MUST NOT）

- Transport Encoding により、ドキュメントの意味や構造を変更してはならない。
- 本規約で定義されていない transport 値を使用してはならない。
- ui_copy において、成果物境界を曖昧にする提示を行ってはならない。
- 成果物が UI 上での表示・コピー時に構造破壊される形式で提示してはならない。
- 成果物の回収単位が曖昧になる提示方法を使用してはならない。
- 提示形式の選択により、成果物の完全性が失われる状態を許容してはならない。

---

## 7. 提示方式選択ルール（MUST/SHOULD）

本章は、5章で定義された禁止条件および選択制約を前提とした補足規則であり、
5章に違反する選択を行ってはならない（MUST）。  
また、5章の制約は本章のすべての規則に優先する（MUST）。  
Transport Encoding の選択は、以下の順序で判定しなければならない（MUST）。

### 7.0 判定順序（MUST）

1. UIレンダリングにより構造・トークン・境界が破壊される可能性があるかを判定する
2. 上記に該当する場合は、ui_copy を選択しなければならない（MUST）
3. 上記に該当しない場合に限り、true_out または download を選択してよい（MAY）

本判定は、推奨ではなく強制的な選択規則である（MUST）。

### 7.1 ui_copy 適用条件（補足）

本節は、5章で定義された禁止条件を前提とした補足規則である。  
本節は、7.0 の判定結果を補足説明するものであり、
判定ロジック自体は 7.0 に従う（MUST）。  
ui_copy は、UIレンダリングによる構造破壊の恐れがある場合に適用される提示方式である。  
特に以下を含む成果物においては、ui_copy を使用することが強く推奨される（SHOULD）。

- Markdown構造（見出し、リスト、区切り線）
- 固定トークン（例：__COMMON_TEMPLATE_BEGIN__ 等）
- HTMLコメント（LLM-MANAGEDブロック）
- 階層リンク

この要件は、提示方式に関する技術制約として優先されるものであり、
生成プロンプト運用規約および各 document_type の仕様における
提示方式選択よりも優先される（MUST）。

例：
__COMMON_TEMPLATE_BEGIN__ 等の固定トークンを含む文書は、
UIレンダリングによりトークンが破壊されるため、
ui_copy の適用対象となる。

### 7.2 安全側選択原則（MUST）

Transport Encoding の選択において、
複数の選択肢が存在し、かつ UIレンダリングによる
構造破壊の可能性を完全に排除できない場合、
LLM は ui_copy を選択しなければならない（MUST）。  
この原則は「既定値」ではなく、
安全性確保のためのフォールバック規則である。

### 7.3 download 選択補足（SHOULD）

UI上での構造保持が困難または不安定な場合は、
ui_copy に代えて download を優先して選択することが望ましい（SHOULD）。  
特に以下の場合は、download の選択を強く推奨する：

- 長文であり、UI表示またはコピー時に途中欠落のリスクがある場合
- 複数成果物を同時に提示する場合
- 高密度構造（コードブロックの多重ネスト、固定トークン大量使用等）を含む場合
- UIレンダリングにより表示崩れまたは回収不能となる可能性が否定できない場合

これらの条件に該当する場合、
ui_copy よりも download の方が回収安定性が高い手段となるため、
優先的に選択することが望ましい（SHOULD）。  
ただし、構造保持が可能な場合は ui_copy を優先してもよい（MAY）。
