# 共通ドキュメント構造

本書は、HLDocS において作成されるすべてのドキュメントに共通する  
**文書構造・配置規則・必須要素**を定義する。

本書は、  
各 document_type 固有の内容や意味論を定義するものではなく、  
**文書の外枠構造（共通構造）**のみを対象とする。

本書は、「HLDocS 前提条件」という仕様が参照可能である場合にのみ適用される。
- 「HLDocS 前提条件」が入力として与えられていない場合、  
または当該仕様に基づく適用可否が確定していない場合、  
本書に基づく判断・生成・再作成・工程実行を行ってはならない。
- この場合、許可されるのは、  
提示された文書の受理および存在確認、  
ならびに前提条件が未参照または未確定である旨の通知のみとする。
- 「HLDocS 前提条件」が入力文書一覧に含まれない場合、生成・再作成・成果物提示を一切行ってはならない。

---

## 1. 基本方針

- HLDocS ドキュメントは Markdown を正規形式とする
- すべてのドキュメントは、本書で定義する共通構造に従う
- 共通構造は **再現可能なテンプレート生成**を目的とする
- 本書で規定される空行・区切り線は、表示装飾ではなく **構造要素**である
- ファイル名・ディレクトリ構成・番号は **意味論を持たない**

---

## 2. 文書全体構造（MUST）

HLDocS ドキュメントは、以下の順序と構成を **必ず**持つ。

1. LLM-MANAGED ブロック  
2. 空行（1行）  
3. 階層リンク行（先頭）  
4. 空行（1行）  
5. タイトル（`# タイトル`）  
6. 空行（1行）  
7. 本文  
8. 空行（1行）  
9. 区切り線（`---`）  
10. 空行（1行）  
11. フッタ階層リンク  

本章で規定される空行および区切り線は、  
**共通ドキュメント構造の一部として必須**であり、  
省略・追加・移動してはならない。

【構造空行規約】

文書全体構造（本章2）における空行は、すべて構造要素として扱う（MUST）。

以下の空行は「構造空行」として定義し、省略してはならない（MUST NOT）。

対象箇所：
1. LLM-MANAGED ブロック直後
2. 先頭階層リンク行直後
3. タイトル直後
4. 本文直前
5. 区切り線（---）直前
6. 区切り線（---）直後
7. フッタ階層リンク直前

定義：
- 空行とは「完全に空の1行」とする（MUST）
- 空白文字（スペース・タブ）のみの行は空行として扱ってはならない（MUST NOT）

制約：
- 各構造空行は必ず1行でなければならない（MUST）
- 構造空行の欠落は禁止する（MUST NOT）
- 構造空行の重複（2行以上）は禁止する（MUST NOT）

【空行数制約】

構造空行以外の箇所において、連続する空行は1行までとする（MUST）。

---

## 3. LLM-MANAGED ブロック

### 3.1 役割

LLM-MANAGED ブロックは、  
ドキュメントの **管理用メタデータ**を定義するためのブロックである。

- 文書内容そのものではない
- 本文とは独立して管理される
- 詳細な規約は [LLM-MANAGED ブロック規約](./04_LLM-MANAGEDブロック規約.md) に従う

本書では、LLM-MANAGED ブロックの内部構造・キー定義は扱わない。

### 3.2 記載位置と形式

- LLM-MANAGED ブロックは、ドキュメントの**先頭行から開始**しなければならない。
  ブロック直前に空行を置いてはならない（MUST NOT）。
- HTML コメント形式で記述する
- 本文からは参照しない

---

## 4. 階層リンク

- 文書の先頭および末尾に配置する
- 階層は `>` 区切りで表現する
- 末尾は必ず当該ドキュメント自身を指す
- 新規作成時の階層は、document_type 値で仮置きする
- 新規作成直後の相対リンク・仮置き階層を実態に合わせる修正は、人間またはツールの責務とする
例：
```
[目次](../目次.md) > spec > ドキュメント名
```

### 4.1 テンプレート固定形式（MUST）

階層リンク行をテンプレートで表現する場合は、  
以下の固定形式（全文一致）を使用しなければならない。

[目次](__TOC_REL_PATH__) > __HIERARCHY_PATH__

---

## 5. タイトル

- 文書の主題を簡潔に示す
- `#` 見出しを用いる
- canonical_title と一致していることが望ましい
- タイトルをテンプレートで表現する場合は、「__TITLE__」を使用する

---

## 6. 本文

- 本文の構造・内容は document_type 別仕様により定義される
- 本書は本文の意味論・詳細構造を規定しない
- 本文をテンプレートで表現する場合は、「__DOCUMENT_BODY__」を使用する

---

### 6.0.1 Markdown表記統一規則（MUST）

HLDocS 文書における Markdown 表記は、差分の安定化および再生成時の表記揺れ防止を目的として統一しなければならない（MUST）。

#### 箇条書き記号（unordered list）

箇条書きには `-` を使用しなければならない（MUST）。

以下は禁止する（MUST NOT）。

- 箇条書き記号の表記を`-`以外に変更する

例：

```markdown
- 項目A
- 項目B
```

#### 箇条書き階層

箇条書きの階層は以下のインデント規則に従わなければならない（MUST）。

```markdown
- 第1階層

  - 第2階層

    - 第3階層
```

箇条書き記号は階層に関係なく `-` を使用しなければならない（MUST）。

### 補足（誤解防止・固定化）

- 本書で規定する空行・区切り線は **共通構造（外枠）**に関するものである
- 本文（document_type 別テンプレートが定義する領域）の内容表現は本書の対象外である
- 本文内における空行や区切り線の使用可否・意味は、本文仕様に従う
- 本文内への空行・区切り線の追加を、本書は **禁止しない**

---

## 6.1 spec / template / prompt の位置づけ補足（固定化）

本章に定義する文書構造は、document_type が `spec` / `template` / `prompt`
のいずれであるかに関わらず、
**すべての HLDocS ドキュメントに共通して適用される外枠構造**である。

ここでいう `template` は、テンプレート断片そのものを意味するのではなく、
**本文領域にテンプレート本文を含む HLDocS 文書として生成される document_type**
を指す。

したがって、`template` 文書であっても
HLDocS 文書構造（LLM-MANAGED ブロック、階層リンク、タイトル、本文、区切り線、フッタ階層リンク）
を必ず備えなければならない（MUST）。

- `spec`  
  - 仕様本文は「本文」領域に記載される  
  - 本文の意味論・章構成は、共通構造ではなく spec 別仕様に属する

- `template`  
  - テンプレート本文は「本文」領域に記載される  
  - テンプレートとして解釈される範囲・マーカー規約は、  
    共通ドキュメント構造ではなく生成プロンプト運用規約・template 別仕様に属する

- `prompt`  
  - プロンプト本文は「本文」領域に記載される  
  - 指示内容・禁止事項・生成制約は、  
    共通ドキュメント構造ではなく prompt 別仕様および生成プロンプト運用規約に属する

本書は、  
これら `spec` / `template` / `prompt` の **意味論的差異や役割分担を定義しない**。

それらの定義は、  
それぞれ対応する仕様書（spec / template / prompt 別仕様）および  
生成プロンプト運用規約に委ねられる。

### 6.1.1 template 文書の成果物境界（MUST）

template 文書はテンプレート断片ではなく、
HLDocS 文書の本文領域にテンプレート本文を含む
document_type として生成される。

したがって template 文書の最終成果物は
HLDocS 文書全体でなければならない（MUST）。

HLDocS 文書構造（本書 2章）に完全に従うこと。

共通テンプレート範囲
（例：`__COMMON_TEMPLATE_BEGIN__` ～ `__COMMON_TEMPLATE_END__`）
は本文内部の構造要素であり、
HLDocS 文書全体と同一視してはならない（MUST NOT）。

テンプレート範囲のみを
最終成果物として出力してはならない（MUST NOT）。

### 6.1.2 template 文書の再作成時成果物境界（MUST）

recreate または patch により template 文書を再作成する場合であっても、
最終成果物は HLDocS 文書全体でなければならない（MUST）。

以下を最終成果物として出力してはならない（MUST NOT）。

- `__COMMON_TEMPLATE_BEGIN__` ～ `__COMMON_TEMPLATE_END__` の範囲のみ
- テンプレート本文のみ
- テンプレート説明とテンプレート断片の混在物
- HLDocS 外枠を欠いた構造断片

再作成時の template 文書は、
新規生成時と同様に、
共通ドキュメント構造および固定プレースホルダ唯一形に適合しなければならない（MUST）。

### 6.1.3 template 文書の説明文必須要件（MUST）

template 文書においては、
本文領域の先頭に、当該テンプレートの用途・適用範囲・使用上の前提を説明する記述を
必ず配置しなければならない（MUST）。

説明文は以下を満たさなければならない（MUST）。

- 通常の Markdown 本文として記述すること
- 構造トークン・プレースホルダを含めないこと
- テンプレート範囲（__COMMON_TEMPLATE_BEGIN__ 等）を含めないこと
- LLM-MANAGED ブロックを含めないこと
- 区切り線（---）を含めないこと

説明文は省略してはならない（MUST NOT）。

説明文は、少なくとも以下の内容を含まなければならない（MUST）。

1. テンプレートの用途
2. 適用対象（document_type または利用場面）
3. 使用上の前提条件または制約

説明文はテンプレート範囲と明確に分離されていなければならない（MUST）。

---

## 6.2 共通テンプレート用プレースホルダ固定（文字列レベル）（MUST）

共通ドキュメントテンプレート（document_type=template、共通テンプレート）において使用するプレースホルダおよび構造トークンは、  
**文字列レベルで完全一致**しなければならない。

### 6.2.1 固定プレースホルダ一覧（全文一致）

以下の文字列のみを使用できる。

- __COMMON_TEMPLATE_BEGIN__
- __COMMON_TEMPLATE_END__
- __DOCUMENT_BODY__
- __TITLE__
- __HIERARCHY_PATH__
- __TOC_REL_PATH__
- <LLM_MANAGED_BLOCK>
- <BLANK_LINE>
- <SECTION_SEPARATOR>

上記以外の表記・別名・別記法は使用してはならない。

### 6.2.2 固定行（全文一致）

共通テンプレート本文内で使用する階層リンク行およびタイトル行は、以下の固定形式（全文一致）とする。

- [目次](__TOC_REL_PATH__) > __HIERARCHY_PATH__
- # __TITLE__

### 6.2.3 配置制約（MUST）

- `__COMMON_TEMPLATE_BEGIN__` の次行は、必ず `<LLM_MANAGED_BLOCK>` としなければならない。
- `__COMMON_TEMPLATE_BEGIN__` と `<LLM_MANAGED_BLOCK>` の間に、空行または他の行を挿入してはならない（MUST NOT）。

### 6.2.4 共通ドキュメントテンプレートの完成形（MUST）

- 文書全体が HLDocS 文書構造を持つこと
- 本文領域には、テンプレートの用途・適用範囲等の説明文を必ず配置しなければならない（MUST）
  説明文は、必ず以下の配置制約および禁止事項に従わなければならない（MUST）
- 説明文の配置位置は、本文領域における `# __TITLE__` の直後の空行の後、`__COMMON_TEMPLATE_BEGIN__` の直前に限ること
- 説明文は通常の Markdown 本文として記述し、構造トークン、プレースホルダ、テンプレート範囲マーカー、LLM-MANAGED ブロック、区切り線を含めてはならないこと
- 説明文は、テンプレートの用途・適用範囲・使用上の前提を明示する内容でなければならず、
  機械的生成においても省略・空文化・抽象化してはならない（MUST）
  曖昧な記述、空文、プレースホルダのみの記述は禁止する（MUST NOT）
- 説明文は、少なくとも以下を含まなければならない（MUST）
  1. テンプレートの用途
  2. 適用対象（document_type または利用場面）
  3. 使用上の前提条件または制約
- 説明文とテンプレート範囲は明確に分離されていなければならない（MUST）
- `__COMMON_TEMPLATE_BEGIN__` ～ `__COMMON_TEMPLATE_END__` の範囲内は、以下の唯一形と一致しなければならないこと
- `doc_id: __AUTO__` や空値は、人間が手動新規作成するときの便宜表現であり、**LLM が生成する canonical_document の成果物では使用してはならない**

テンプレート範囲の唯一形：
- 1行目 `__COMMON_TEMPLATE_BEGIN__`
- 2行目 `<LLM_MANAGED_BLOCK>`
- 3行目 `<BLANK_LINE>`
- 4行目 `[目次](__TOC_REL_PATH__) > __HIERARCHY_PATH__`
- 5行目 `<BLANK_LINE>`
- 6行目 `# __TITLE__`
- 7行目 `<BLANK_LINE>`
- 8行目 `__DOCUMENT_BODY__`
- 9行目 `<BLANK_LINE>`
- 10行目 `<SECTION_SEPARATOR>`
- 11行目 `<BLANK_LINE>`
- 12行目 `[目次](__TOC_REL_PATH__) > __HIERARCHY_PATH__`
- 13行目 `__COMMON_TEMPLATE_END__`

テンプレート範囲の唯一形に含まれる各行は、行内容・行順序・行数を含めて完全一致しなければならない（MUST）。

とくに `<BLANK_LINE>` は、当該位置に実空行が1行存在することを意味する構造要素であり、
省略・追加・移動・他位置との統合をしてはならない（MUST NOT）。

また、実体化後においても、当該空行は文書全体構造（本書2章）における構造空行として
必ず観測可能でなければならない（MUST）。

したがって、テンプレート範囲の唯一形に含まれるいずれの `<BLANK_LINE>` についても、
実体化時または再現時に欠落してはならない（MUST NOT）。

再作成（recreate / patch）においても、
上記唯一形との一致要件は緩和されない（MUST NOT）。

修正前正本未提示、または再作成条件未成立を理由として、
テンプレート断片のみを暫定出力してはならない（MUST NOT）。

文書は Transport Encoding によって外部へ出力されることを前提とする。
出力形式の詳細は Transport Encoding 規約に従う。

本文およびテンプレート範囲に、Markdown構造・固定トークン・HTMLコメント・階層リンクが含まれるため、
当該文書の提示においては Transport Encoding 規約に基づき ui_copy が適用されることがある（MUST）。

## 6.3 生成フェーズ用プレースホルダ定義（07 統合）（MUST）

生成フェーズ実行時に使用されるプレースホルダは、共通ドキュメント構造の一部として以下に統合定義する。  

### 6.3.1 定義

- テンプレート範囲を定義
  - `__COMMON_TEMPLATE_BEGIN__`：共通テンプレート本文開始マーカー
  - `__COMMON_TEMPLATE_END__`：共通テンプレート本文終了マーカー

- テンプレート範囲内のプレースホルダ定義
  - `__DOCUMENT_BODY__`：document_type 別本文差替領域
  - `__TITLE__`：タイトル差替領域
  - `__HIERARCHY_PATH__`：階層リンクのパス部分
  - `__TOC_REL_PATH__`：目次への相対パス部分
  - `<LLM_MANAGED_BLOCK>`：LLM-MANAGED ブロック挿入位置
  - `<BLANK_LINE>`：構造上必須の空行
  - `<SECTION_SEPARATOR>`：区切り線（`---`）挿入位置

テンプレート範囲内のプレースホルダは、テンプレート生成および再作成時には実体化してはならない（MUST）。  
プレースホルダの実体化は、生成フェーズ実行時にのみ行われる。  
実体化例：  
<LLM_MANAGED_BLOCK> → ```<!-- HLDocS:LLM-MANAGED -->```  
<BLANK_LINE> → 実空行  
<SECTION_SEPARATOR> → ---

### 6.3.2 制約（MUST）

- 上記以外のプレースホルダを導入してはならない。
- プレースホルダは **文字列完全一致**でなければならない。
- プレースホルダの意味は、本書定義を超えて拡張してはならない。

### 6.3.3 テンプレート範囲構造制約（MUST）

`__COMMON_TEMPLATE_BEGIN__` および
`__COMMON_TEMPLATE_END__` は、
共通テンプレート本文の範囲を定義する構造マーカーである。

以下を満たさなければならない。

1. `__COMMON_TEMPLATE_BEGIN__` は文書内に **1回のみ**出現する。
2. `__COMMON_TEMPLATE_END__` は文書内に **1回のみ**出現する。
3. `__COMMON_TEMPLATE_BEGIN__` は `__COMMON_TEMPLATE_END__` より前に出現しなければならない。
4. テンプレート範囲は **単一の連続範囲**でなければならない。
5. テンプレート範囲は **入れ子構造を形成してはならない**。
6. テンプレート範囲が複数存在してはならない。

## 7. ドキュメント並べ替え番号規定（MUST）

- ファイル名およびフォルダ名は、  
  ファイルシステム上の並び順を制御する目的に限り、  
  自由に先頭へ番号を付与してよい  
  （番号付与以外の名称変更は行ってはならない）
- 番号は **NN_ 形式**とする  
  - N の桁数は自由である  
  - 末尾は必ず `_` で終わる
- これらの番号は、  
  **意味・役割・仕様上の区別を一切持たない**

### 位置づけ補足（固定化）

本規定は、文書構造や本文仕様とは独立した  
**HLDocS ドキュメント運用上の前提規約**である。

- 並び順制御のための現実的要請と、
- 仕様上の意味論・依存関係

を明確に分離することを目的とし、  
将来にわたって **共通ドキュメント構造に含めるものとする**。

## 6.4 prompt 文書の構造制約（MUST）

document_type = prompt の文書は、
本文領域において以下の構造を持たなければならない（MUST）。

### 6.4.1 説明文（MUST）

本文領域の先頭には、当該プロンプトの用途・適用範囲・前提条件を示す説明文を配置しなければならない（MUST）。

説明文は以下を満たさなければならない（MUST）。

- 通常の Markdown 本文として記述すること
- 構造トークン・プレースホルダを含めないこと
- テンプレート範囲・LLM-MANAGED ブロックを含めないこと

- 以下の内容を必ず含むこと
  1. プロンプトの用途
  2. 適用対象（document_type または利用場面）
  3. 使用上の前提条件または制約

加えて、説明文は以下の意味的要件を満たさなければならない（MUST）。

- 抽象的または空文化した記述を行ってはならない（MUST NOT）
- プレースホルダのみの記述や意味を持たない説明を行ってはならない（MUST NOT）
- 実際の生成・判定に必要な前提条件を具体的に記述しなければならない（MUST）
- 当該プロンプト単体で解釈可能となるように記述しなければならない（MUST）
- 外部仕様への依存を前提とした曖昧な記述を行ってはならない（MUST NOT）

説明文は省略してはならない（MUST NOT）。

---

### 6.4.2 プロンプト範囲マーカー（MUST）

プロンプト本文は、以下のマーカーで囲まれた単一の連続範囲として定義しなければならない（MUST）。

- `__PROMPT_BEGIN__`
- `__PROMPT_END__`

以下を満たさなければならない（MUST）。

1. `__PROMPT_BEGIN__` は文書内に1回のみ出現する
2. `__PROMPT_END__` は文書内に1回のみ出現する
3. `__PROMPT_BEGIN__` は `__PROMPT_END__` より前に出現する
4. プロンプト範囲は単一の連続範囲である
5. 入れ子構造を形成してはならない
6. 複数範囲を持ってはならない

---

### 6.4.3 プロンプト本文の必須要素（MUST）

`__PROMPT_BEGIN__` ～ `__PROMPT_END__` の範囲内には、
以下の要素を含まなければならない（MUST）。

- Phase 定義（Phase 0〜 の処理順序および役割）
- 入力条件（required inputs）
- 成立条件判定ロジック
- FAIL-FAST 条件および出力制約
- 禁止事項（MUST NOT）
- 出力条件（成果物 / FAIL-FAST）
- ENUM 再掲（必要なもの）
- 判定テーブル再掲（必要なもの）

これらの要素は、省略・抽象化・曖昧化してはならない（MUST NOT）。

---

### 6.4.4 構造およびトークンの保持（MUST）

プロンプト範囲内の内容は、以下を満たさなければならない（MUST）。

- Markdown構造・固定トークンを保持すること
- トークンを変形・省略・再解釈してはならない
- UIレンダリングによる構造破壊が発生しない形式で出力可能であること

---

### 6.4.5 Transport Encoding 適用条件（MUST）

以下のいずれかに該当する場合、
prompt 文書の成果物出力には ui_copy を適用しなければならない（MUST）。

- Markdown構造を含む
- 固定トークン（__XXX__）を含む
- ENUM 再掲または判定テーブルを含む
- UIレンダリングにより構造が変形する可能性がある

true_out により構造が破壊される可能性がある場合、
true_out を選択してはならない（MUST NOT）。
