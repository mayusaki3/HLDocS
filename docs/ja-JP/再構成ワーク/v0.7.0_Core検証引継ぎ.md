# v0.7.0 Core検証引継ぎ

## 1. チャット切替方針

現チャットではv0.7.0仕様の構築と検証準備を行う。新しいチャットの目的は**v0.7.0 Coreの独立した再検証**であり、v0.7.0へのリリースまたは通常運転移行を意味しない。新チャットは過去の会話・LLM_WORKSPACEのPASSを根拠にしない。

## 2. 検証対象

- 対象リポジトリ: `mayusaki3/HLDocS`
- 対象ブランチ: `develop`
- 検証開始前の参考SHA: `2e55ca103e23d0f57d2409c6b8a5b6965e4e14fa`。新チャット開始時にHEADを再取得して対象SHAを固定する。
- 正本: `docs/ja-JP/仕様/00_Core/01_HLDocSとは.md`〜`08_Coreセルフ検証仕様.md`の8文書。
- 検証条件: `docs/ja-JP/仕様/00_Core/08_Coreセルフ検証仕様.md`。必要な範囲でState Machine、State、Workflow、Capability、Restriction、Tool、SubFlow仕様を参照する。

## 3. 検証区分

Coreセルフ検証仕様に従い、責務境界、起動・通常運転、Execution Context、Restriction、Canonical Conflict、LLM_WORKSPACE、Fail-closed（10シナリオ）、既知項目外の問題探索を実施する。

各項目の判定はPASS/FAIL/UNDEFINED/BLOCKEDとし、対象SHA、根拠仕様箇所、発見Issue、修正、再検証を記録する。過去のCore結果にあるPASSは現在のPASSへ継承しない。

## 4. 現チャットでの予備確認

Coreの8文書を現在のGitHub正本から取得した。Core基本制限は起動判定から復旧中まで適用され、State Machineへの移譲成功前は通常運転しない規定がある。Core復旧仕様は復旧開始後の責務を分離している。

ただし、これは抜粋照合であり、Core全項目の再検証完了ではない。現チャットの予備確認を新チャットのPASS根拠に使用してはならない。

### 要調査Issue候補

`08_Coreセルフ検証仕様.md`の`doc_id: doc-20261007-CORE-VALIDATION`は、v0.7.0文書共通構造仕様の新規ID形式`doc-YYYYMMDD-HHMMSSZ-XXXX`と異なる。既存doc_idは通常の編集で維持する規則があるため、**形式不一致だけで無断再発行しない**。新チャットでは既存IDの適用・移行境界を確認し、必要なら独立した移行判断とする。

## 5. 新チャットでの作業指示

「HLDocS v0.7.0のCoreを、developの現在HEADと`docs/ja-JP/仕様/00_Core/08_Coreセルフ検証仕様.md`を正本として独立に再検証してください。まずHEADと対象文書を再取得し、Coreの全区分・Fail-closedシナリオを判定してください。問題は根拠を示し、修正時は再検証してください。今回はv0.7.0のリリース判定や通常運転への切替を行いません。」

## 6. 完了境界

Coreの必須項目がすべてPASSし、未解決のCore阻害Issueがない場合は「Core検証PASS」と記録してよい。ただしv0.7.0全体のリリース判定、v0.6.1互換性検証、文書生成DGEN-01〜18の実行系受入検証は別のゲートである。
