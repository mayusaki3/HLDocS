# 文書共通構造仕様

## 1. 目的

HLDocSが生成・更新するMarkdown文書の共通外枠、識別情報、生成時の責務を定義する。文書種別固有の本文構造は各document_type仕様に従う。

## 2. 共通外枠

HLDocS文書の正規形式はMarkdownとする（MUST）。文書は先頭のLLM-MANAGEDコメント、空行、先頭階層リンク、空行、H1タイトル、空行、本文、空行、区切り線、空行、末尾階層リンクの順序を持つ（MUST）。構造空行は完全な空行1行とし、省略・重複しない（MUST）。本文内部の空行・区切り線はdocument_type固有の制約に従う。

先頭と末尾の階層リンクは同一の階層を示す（MUST）。人間向けMarkdownリンクは機械的Traceability参照とは区別する（MUST）。

## 3. LLM-MANAGED

LLM-MANAGEDは文書先頭にHTMLコメント形式で1個のみ配置する（MUST）。最低限、次のキーを保持する（MUST）。

- `doc_id`: 文書の恒久的同一性
- `lang`: 言語コード
- `canonical_title`: 正規タイトル
- `document_type`: 文書の役割
- `canonical_document`: 正規成果物か否かを示す真偽値

既存文書の更新・改名・移動ではdoc_idを維持する（MUST）。翻訳では同一論理文書のdoc_idを維持し、langを翻訳先言語に設定する（MUST）。論理的な新規文書の作成・明示的な分割・統合・置換では新規doc_idを割り当ててよい（MAY）。

doc_id新規生成時は既存仕様の`doc-YYYYMMDD-HHMMSSZ-XXXX`形式（UTC時刻、4桁base36）を使用し、既存IDと衝突してはならない（MUST）。メタデータの拡張キー・値域・Transportとの整合は対応仕様に従う。

## 4. 文書生成と確認用派生成果物

WorkflowはWork Purposeと対象document_typeから適用する正本仕様を取得し、必要な構造と生成指示を組み立てる（MUST）。常設のテンプレートファイルおよび生成プロンプトファイルを実行前提としてはならない（MUST NOT）。

利用者がテンプレート確認または生成指示確認を要求した場合、仕様に基づく派生成果物を提示してよい（MAY）。確認用の断片は正規文書そのものではない。利用者が別途、独立したHLDocS文書として保存・管理するよう要求した場合は、その文書種別と共通外枠の適用を確認する。

## 5. モード廃止

`meta/apply`をHLDocSの実行モードとして使用してはならない（MUST NOT）。`supported_modes`またはmode別の常設テンプレート・生成プロンプト必須判定によって、文書生成の可否を決めてはならない（MUST NOT）。

HLDocS自身の仕様変更と外部成果物の生成・更新は、Work Purpose、Workflow、適用仕様、変更権限およびRestrictionによって区別する（MUST）。

## 6. 正本取得と検証

必要な仕様・既存文書が取得可能なら取得を優先する（MUST）。正本の欠落・矛盾を推測で補完してはならない（MUST NOT）。生成後は共通外枠とdocument_type固有の制約を検査する（MUST）。

Traceability識別子の生成・維持・参照は別途Traceability仕様に従う。文書の生成完了はWork完了やWorkflow完了を自動的に意味しない。
