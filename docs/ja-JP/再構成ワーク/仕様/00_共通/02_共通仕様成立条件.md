# 共通仕様成立条件

## 1. 目的

本書は、HLDocS仕様/規約が利用可能であることを判定し、共通仕様成立状態への遷移条件を定義する。

## 2. 共通仕様未成立状態

HLDocS開始時は、共通仕様未成立状態とする。  
本仕様は、共通仕様未成立状態でのみ利用できる。  
本仕様は、共通仕様成立状態への遷移条件を定義する。  
本仕様に従って共通仕様成立状態へ遷移するまでは、HLDocSに基づく判断・生成・更新・検証を行ってはならない（MUST NOT）。

## 3. 成立条件

共通仕様成立状態へ遷移するためには、以下の条件をすべて満たさなければならない（MUST）。

- HLDocS仕様/規約（正本）が利用可能であること。
- HLDocS仕様/規約（正本）が、本章で定義する仕様要素を満たしていること。

HLDocS仕様/規約（正本）は、共通仕様成立状態を維持するために必要な `3.1 仕様要素` の仕様要素によって構成される。  
仕様要素の成立判定では、仕様要素一覧に定義された仕様要素名と、対応する正本仕様の仕様要素名が完全一致しなければならない（MUST）。  
名称の類推、部分一致、別名、同義語によって成立と判断してはならない（MUST NOT）。

### 3.1 仕様要素一覧

- HLDocSとは
- 共通仕様成立条件
- 状態マシン仕様
- Workflow・SubFlow仕様
- LLM_WORKSPACE仕様
- LLMツール仕様
- 開始Workflow
- 待機Workflow
- Git.userEnv_ls-files
- 前提条件
- 生成プロンプト運用規約
- 共通ドキュメント構造
- LLM-MANAGEDブロック規約
- Transport Encoding 規約
- Traceability（仕様・テスト・コード紐づけ）規約
- 生成フェーズ実行規約
- 再作成時不変条件規約
- prompt成立条件規約
- ENUM 再掲要件規約
- 判定テーブル再掲要件規約
- ドキュメント参照・ナビゲーション規約
- 成果物更新運用規約

本一覧は、HLDocS仕様/規約（正本）の構成概念を示すものであり、並び順・管理番号・ファイル構成・分割単位を規定するものではない。  
成立判定における識別単位は、文書番号・ファイル名・分割単位ではなく、本一覧に列挙された **仕様要素そのもの** である（MUST）。  
したがって成立判定では、各仕様要素に対応する正本仕様が提示されているかを確認しなければならない（MUST）。

文書番号・ファイル分割・番号範囲（例：01-05、06-10 等）を理由として仕様要素が充足していると判断してはならない（MUST NOT）。

### 3.2 正本の情報源原則

本節は、HLDocS仕様/規約（正本）の成立判定にのみ適用する。

HLDocS仕様/規約（正本）の成立判定は、利用者が指定した情報源のみを対象として行わなければならない（MUST）。  
利用者が複数の情報源（全文チャット貼り付け、添付ファイル、URL等）を指定した場合は、次の優先順位で利用しなければならない（MUST）。

1. 全文チャット貼り付け
2. 添付ファイル
3. URL

上位の情報源のみで成立判定が可能な場合は、下位の情報源を参照して成立判定を補完または変更してはならない（MUST NOT）。  
上位の情報源で成立判定ができない場合に限り、次順位の情報源を利用してよい（MAY）。  
複数の情報源間で仕様要素の差異または矛盾を検出した場合は、利用者の指示がない限り統合・補完してはならない（MUST NOT）。

本節は、作業対象正本の取得方法または更新方法を規定するものではない。  
共通仕様成立状態へ遷移した後の作業対象正本の取得・更新は、WorkflowまたはTool仕様に従わなければならない（MUST）。

## 4. 共通仕様成立状態

第3章の成立条件を満たした場合、共通仕様成立状態へ遷移する。  
共通仕様成立状態では、HLDocS仕様/規約を利用して判断・生成・更新・検証を行ってよい。

## 5. 共通仕様未成立

第3章の成立条件を満たさない場合、共通仕様未成立状態を維持する。  
共通仕様未成立状態では、HLDocSに基づく判断・生成・更新・検証を行ってはならない（MUST NOT）。
