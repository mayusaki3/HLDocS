# HLDocSとは

本書は、HLDocS の再構成ワークにおいて、LLM が最初に理解すべき **HLDocS の定義・目的・設計原則・実行モデル上の位置付け**を定義する。

本書は、既存の HLDocS 共通仕様を置き換えるものではない。  
本書は、v0.7.0-preview における検討用仕様であり、既存の正本仕様を破壊せず、HLDocS を状態マシンおよび Workflow として扱うための入口を定義する。

---

## 1. HLDocS の定義

HLDocS とは、LLM がドキュメントを生成・更新・再作成・検証するために参照する、仕様群および実行手順の総称である。

HLDocS は、LLM の内部知識、推測、過去会話の記憶、または利用者の暗黙的意図を正本としない。  
HLDocS における正本は、利用者が提示した仕様文書、または利用者が正本として指定したファイルである。

HLDocS は、LLM に対して次の事項を明確にする。

- 何を正本として扱うか
- どの仕様が成立している場合に処理を開始できるか
- どの順序で処理を実行するか
- どの状態で、どの仕様を参照するか
- どの条件で処理を停止、保留、または次工程へ遷移するか
- 生成物、更新物、検証結果をどのように扱うか

---

## 2. HLDocS の目的

HLDocS の目的は、LLM によるドキュメント作業を、再現可能で検証可能な手順として実行できるようにすることである。

HLDocS は、次の問題を抑制することを目的とする。

- 仕様を読まずに記憶や推測で作業すること
- 途中で新しい改善案を追加し続け、作業が終了しないこと
- 必要でない仕様まで参照し、状態ごとの判断が混線すること
- 仕様の成立条件を満たしていない状態で生成・更新・検証を進めること
- 既存仕様と新規仕様、正本と作業中ドラフトを混同すること
- LLM 固有の挙動に依存した運用を仕様として固定すること

---

## 3. HLDocS の正本原則

HLDocS では、利用者が正本として指定した仕様を最優先する。

LLM は、次の情報を正本として扱ってはならない。

- LLM の学習済み知識
- 以前の会話で読んだ内容の記憶
- 未確認のリポジトリ状態
- 利用者が正本として指定していない添付ファイル
- 作業中の仮説、提案、推測

LLM は、作業に必要な仕様が提示されていない場合、仕様が不足していることを明示しなければならない。

---

## 4. HLDocS の共通仕様成立

HLDocS は、共通仕様が成立している場合にのみ、HLDocS に基づく生成・更新・再作成・検証を開始できる。

共通仕様成立とは、HLDocS を実行するために必要な仕様要素が、利用者から正本として提示され、参照可能である状態を指す。

共通仕様成立の確認では、必要な仕様要素が揃っているかを確認する。  
ただし、v0.7.0-preview 以降の実行モデルでは、成立確認で読んだ内容をその後の個別状態の判断根拠として使い続けないことを前提とする。

成立確認後は、参照境界を設定し、以後の状態では現在状態で指定された仕様のみを根拠として参照する。

---

## 5. 読んだ仕様は保持される前提

HLDocS は、LLM が一度読んだ仕様内容を完全に忘れることを前提としない。

したがって、HLDocS では次の前提で仕様を設計する。

- 読んだ仕様は、以後の会話内でLLMの判断に影響する可能性がある
- 状態が切り替わっても、LLM が過去の内容を完全に忘れるとは限らない
- 「必要な章だけ読む」という挙動は、LLM 共通の保証として扱わない
- 必要な仕様だけを参照させるには、仕様の物理分割または明確な参照境界が必要である

この前提により、HLDocS は特定の LLM の内部挙動に依存しない仕様を目指す。

---

## 6. 参照境界

参照境界とは、以後の判断・生成・更新・検証において、境界以前に読んだ仕様、会話内容、中間判断を根拠として参照しないために設定する論理的な境界である。

参照境界は、LLM が過去情報を完全に忘れることを要求するものではない。  
参照境界は、以後の処理で根拠として採用してよい情報の範囲を制限するための運用上の境界である。

HLDocS では、少なくとも次の時点で参照境界を設定することを想定する。

- 共通仕様成立確認の完了後
- Workflow の主要状態遷移時
- 再構成候補の採択を凍結した後
- 作業フェーズから検証フェーズへ移行する時

参照境界以後の処理では、現在状態で明示された仕様、Supervisor が保持する Core Snapshot、および直近の State Summary のみを根拠として扱う。

---

## 7. Supervisor

Supervisor とは、HLDocS の実行中に、現在の Workflow、現在の State、Core Snapshot、参照境界、State Summary を管理する役割である。

Supervisor は、すべての仕様本文を保持し続ける役割ではない。  
Supervisor は、現在の作業を継続するために必要な最小限の制御情報を保持する。

Supervisor は、次の責務を持つ。

- 現在の Workflow を識別する
- 現在の State を識別する
- 次に参照すべき仕様を決定する
- 参照境界を設定する
- State Summary を受け取り、次状態へ渡す
- Core Snapshot を定期的に再確認する
- Workflow の終了条件を確認する

---

## 8. Core Snapshot

Core Snapshot とは、HLDocS の実行中に常に優先される最小限の中核情報である。

Core Snapshot は、長時間の Workflow において、HLDocS の目的や制御原則の優先度が下がることを抑制するために使用する。

Core Snapshot には、少なくとも次の情報を含める。

- 現在の Workflow
- 現在の State
- 現在の作業対象
- 正本として扱う仕様
- 現在状態で参照可能な仕様
- 参照境界の位置
- 終了条件または凍結条件

Core Snapshot は、仕様本文そのものの代替ではない。  
必要な仕様本文は、現在状態で必要になった時点で参照する。

---

## 9. State Machine

State Machine とは、HLDocS の作業を状態単位に分解し、状態ごとに参照仕様、入力、出力、終了条件、次状態を明確にする実行方式である。

HLDocS における State は、次の情報を持つ。

- State ID
- State 名
- 目的
- 入力
- 参照可能な仕様
- 実行内容
- 出力
- 終了条件
- 次状態

State は、現在状態で指定されていない仕様を根拠として判断してはならない。  
必要な仕様が不足している場合、State は処理を保留し、不足仕様を明示する。

---

## 10. Workflow

Workflow とは、複数の State を目的に応じて並べた作業手順である。

HLDocS における Workflow は、LLM が作業を勝手に拡張し続けることを防止するため、開始条件、状態遷移、凍結条件、終了条件を明示する。

特に再構成作業では、次の分離を必須とする。

- 問題抽出
- 改善候補列挙
- 改善候補の採択
- 採択内容の凍結
- 実施
- 検証

採択内容の凍結後は、新しい改善案を同一 Workflow に追加してはならない。  
新しい改善案は、次 Workflow または次バージョン候補として記録する。

---

## 11. HLDocS と LLM 非依存性

HLDocS は、特定の LLM の内部挙動を前提としない。

HLDocS は、次のような挙動を仕様成立の前提にしてはならない。

- 指定した章だけを厳密に読むこと
- 状態遷移後に過去情報を完全に忘れること
- 長い会話でも最初の指示の優先度が常に保たれること
- モデル固有のコンテキスト圧縮挙動
- モデル固有のツール実行方式

モデル固有の最適化は、仕様ではなく利用ガイドまたは実装ガイドとして扱う。

---

## 12. v0.7.0-preview における位置付け

本書は、v0.7.0-preview における再構成ワークの入口仕様である。

v0.7.0-preview では、既存の HLDocS 共通仕様を破壊的に置き換えることを目的としない。  
主目的は、v0.6.1-preview の安定化に必要な実行モデル、状態管理、Workflow、参照境界、Core Snapshot の考え方を追加・検証することである。

HTML 生成、Lint ツール、可視化、全面的な物理構成変更は、本書の主対象ではない。  
それらは、必要に応じて v0.8.0 以降または v0.9.0 以降の検討対象とする。
