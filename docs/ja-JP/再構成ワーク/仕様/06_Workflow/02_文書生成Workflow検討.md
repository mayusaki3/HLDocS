# 文書生成Workflow検討（未確定）

## 目的

v0.6.1のdocument_type別生成能力を、常設テンプレート・生成プロンプトに依存せずWorkflowから再構成する設計案。正本仕様として未確定であり、実行検証済みではない。

## 共通実行経路案

1. Interactionから文書生成・更新・テンプレート確認・生成指示確認の要求種別を受け取る。
2. Workflowが対象document_typeと正本仕様、共通構造、必要な参照文書を特定する。
3. 取得可能な正本を優先取得し、必須情報の不足を再評価する。取得不能時はCoreの復旧・制限規則に従い推測で補完しない。
4. Workflowが仕様上の必須構造・禁止事項・メタデータ・参照規則を抽出して生成指示を構成する。SubFlowの具体的な分割は未確定。
5. 要求が成果物生成なら文書を、確認要求ならテンプレートまたは説明可能な生成指示を出力する。確認用出力は正本ではない。
6. 対象文書種別の制約を検査し、問題があれば修正・再検査する。正本仕様の変更を伴う場合は変更権限・承認を別途確認する。

## 文書種別ごとの生成制約（既存仕様からの抽出）

| document_type | 生成時に維持する条件 | 生成時の禁止・注意 |
|---|---|---|
| index | リンク・階層主体、目次の参照、既存更新ではdoc_id維持 | 要約や仕様判断を記述しない。ガイド文は利用者の明示指示時のみ |
| spec | 宣言的な概念・不変条件・制約、更新時doc_id維持 | 実装手順、テストケース、検証結果を混入しない |
| testspec | specに従属、ケースごとにsec_id、spec参照はdoc_id#sec_id、テスト番号は表示ラベル | セルフ検証仕様と混同しない。コードそのものを埋め込まない |
| note | 未確定事項・検討案と前提、未決事項を区別 | 確定した仕様の代用としない |
| minutes | 日時・議題・合意事項・未決事項・背景を記録 | 事実記録を仕様の正本としない |
| usage | 実行可能な操作順、前提条件、注意事項 | 仕様の新規宣言やテスト観点を含めない |

## 検証観点

- 6種別それぞれで常設テンプレート・生成プロンプトを参照せず、仕様から必要な指示を構成できること。
- 生成と確認要求で成果物の扱いが変わること。
- 必須仕様の取得不能、矛盾、仕様更新時に旧テンプレートを無条件に優先しないこと。
- testspecのsec_idとspec参照の整合性が確認できること。
- 既存のdocument_type仕様自体が旧版由来であり、v0.7.0の正本として採用する前にCore・Workflow・Traceabilityとの整合性を確認すること。

## 未確定事項

- 共通文書構造、document_type別仕様のv0.7.0での正式な正本位置。
- WorkflowとSubFlowの具体的な責務分割。
- 生成指示の再現性を判定する具体的な入力セットと評価方法。
- 旧仕様の「template」「prompt」というdocument_type言及を新方式に合わせて改訂する範囲。

この文書は仕様設計の検討結果であり、検証結果PASSを意味しない。

## WorkflowとSubFlowの責務分担案

WorkflowはWork Purposeと要求種別を解釈し、適用する正本・処理順序・利用者への確認・成果物の提示・完了判断を管理する。Interaction以外から直接利用者と対話しない。CoreがExecution Contextと変更権限を検証する。

SubFlow候補は次の単一目的単位とする。これらは登録済みSubFlowとして確定したものではない。

| 候補 | 入力 | 出力 | 境界 |
|---|---|---|---|
| 文書種別規則取得 | document_type、正本参照 | 規則集合または取得失敗 | 正本を推測・変更しない |
| 文書構造組立 | 規則集合、要求内容 | 文書構造・生成指示 | WorkflowやStateを変更しない |
| 文書内容生成 | 文書構造、取得済み根拠 | 草稿 | 利用者へ直接提示しない |
| 文書整合性検査 | 草稿、規則集合 | 違反箇所・検査結果 | 修正やPASS確定を独断しない |
| テンプレート確認用生成 | 規則集合 | 派生テンプレート | 正本化しない |

既存のSubFlow登録・呼出し規則との整合を確認してから、正式なSubFlow仕様を作成する。

## 共通文書構造とTraceabilityの照合結果（設計上の発見）

- 既存Traceability規約は `doc_id` による文書同一性、`doc_id#sec_id` による検証単位参照を規定している。生成時は新規・更新を区別し、更新では既存識別子を維持する。
- `sec_id` はtestspecを起点に確定し、spec単体生成時には付与しない。testspecからspecへ参照する際は、参照先識別子が実在することを確認する必要がある。
- note/minutesの根拠アンカー `ref_id` は検証単位 `sec_id` と異なり、仕様化時に後付け可能である。
- 既存Traceability規約は旧「前提条件」「生成プロンプト運用規約」を成立条件として参照するため、v0.7.0 Coreの起動条件・Workflow内での生成指示構成との整合が未確認である。
- 同規約には本文中の機械参照を `doc_id#sec_id` のみに制限する記述と、派生参照 `doc_id#ref_id` を許す記述がある。参照種別ごとの適用範囲を明示する必要がある。
- indexの人間向け相対リンクは機械参照と区別する。旧規約の一般的なURL禁止をナビゲーションや出典取得に無条件適用しないよう整理が必要。
- 共通文書構造、LLM-MANAGED、Transportの規約は旧体系に残っており、v0.7.0の正本採用・更新前に個別照合する。

## 次に必要な確定作業

1. Coreと矛盾しない文書共通構造・メタデータの採用仕様を作成する。
2. Traceabilityの参照種別と正本取得・文書生成との境界を定義する。
3. SubFlowの登録簿・呼出し条件を確定し、上記候補を必要に応じ正式仕様化する。
4. 文書種別別に正常・異常・仕様更新後の生成シナリオを検証する。
