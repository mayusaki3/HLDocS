# Capability(能力)追加ルール

## 1. 目的

本書は、新しいPractical Capability(実務能力)またはExecution Capability(実行能力)をHLDocSへ追加する場合の規則を定義する。

能力追加はHLDocSの正本を変更する作業であり、通常の変更Work(作業)として処理する。

## 2. Workとしての扱い

利用者が新しい能力の追加を明示的に要求した場合、その要求はNEW_WORK_REQUESTとしてWork Candidate(作業候補)を構成できる。

Purposeには少なくとも、追加対象の能力または利用者が求める実務目的を保持する。

能力追加は変更を明示的に目的とするため、通常は変更State(状態)のwork_acceptanceに適合する。

能力追加のためだけに専用Stateまたは専用Workflow Planを生成してはならない（MUST NOT）。

## 3. 変更調査

変更調査Workflow(ワークフロー)は能力追加要求を扱う場合、通常の変更調査に加えて次を確認する。

1. 要求された能力がPractical CapabilityかExecution Capabilityか。
2. 同一または実質的に同一の既存Capabilityが登録されていないか。
3. Capability名、purposeおよび責務境界が一意に理解できるか。
4. Practicalの場合、必要なExecution Capabilityをrequiresとoptionalへ分類できるか。
5. Executionの場合、実在する能力提供手段をprovided_byとして確認できるか。
6. 依存が一方向で循環しないか。
7. 既存Capability、Workflow、Restrictionその他の仕様と矛盾しないか。
8. 個別Capability仕様とCapability Registryの変更対象をTarget List(対処対象リスト)へ含める。

不足するExecution Capability自体の新規追加が必要な場合、それが利用者の能力追加Purposeを成立させるために必要な下位能力であることを確認する。

必要性を説明できない周辺能力を便乗して追加してはならない（MUST NOT）。

## 4. 変更対処

変更対処WorkflowはTarget Listに従い、少なくとも次を整合した一つの能力追加として扱う。

- 個別Capability仕様の作成
- Capability Registryへの登録
- 必要な依存参照の更新
- 能力提供手段側に明示的な宣言追加が必要な場合はその更新

Capability Registryだけ、または個別Capability仕様だけを追加して能力追加を完了してはならない（MUST NOT）。

Practical Capabilityから特定Toolへ直接依存させてはならない（MUST NOT）。

## 5. 変更検証

変更検証Workflowは通常の検証に加えて、少なくとも次を確認する。

- CapabilityがRegistryから一意に発見できる。
- 個別Capability仕様を参照できる。
- typeがPRACTICALまたはEXECUTIONのいずれか一方として成立する。
- Practicalのrequiresおよびoptionalが登録済みExecution Capabilityを参照する。
- Executionのprovided_byが確認可能な能力提供手段を参照する。
- Capability依存に循環がない。
- Capability追加によってRestrictionが緩和されていない。
- 能力確認Workflowが新しいCapabilityを評価できる構造になっている。

必要な下位Execution Capabilityまたは能力提供手段が成立しない場合、上位Practical Capabilityを無条件にAVAILABLEとして扱ってはならない（MUST NOT）。

## 6. 利用者判断

次の場合は推測して能力定義を確定せず、Interaction(対話窓口)を通じて利用者判断を要求する。

- 実務能力と実行能力のどちらとして定義すべきか一意に決まらない。
- 既存Capabilityとの統合または新規追加のどちらが要求に合うか判断できない。
- 能力の責務境界を確定するとWork Purposeを実質的に拡張する。
- requiredとoptionalの違いが実務の成立条件を変えるが、要求から判断できない。

## 7. 実行検証

Capability追加機構は、HLDocSを実際に利用するLLM実行環境でEnd-to-End検証可能でなければならない（MUST）。

現在の再構成ワークにおける基準検証環境は、ChatGPTからGitHub接続を利用し、HLDocS仕様を実行規則としてdevelopブランチ上の対象を参照・変更できる環境とする。

能力追加のE2E検証では、少なくとも次を確認する。

1. 利用者の能力追加要求をNEW_WORK_REQUESTとして扱える。
2. 通常の変更Workとして変更調査、変更対処、変更検証を実行できる。
3. 個別Capability仕様とCapability Registryを実際の正本へ追加できる。
4. 追加後にRegistryから新しいCapabilityを再発見できる。
5. 個別Capability仕様と依存Execution Capabilityを再参照できる。
6. HLDocS能力確認Workflowが現在の実行環境に基づいて追加Capabilityを評価できる。
7. 評価結果をAVAILABLE、DEGRADED、UNAVAILABLEまたはUNKNOWNとして説明できる。

能力追加処理と再発見・能力確認は、同一会話の一時的な文脈だけに依存して成立してはならない（MUST NOT）。正本へ登録された情報から再構成できなければならない（MUST）。

Capability仕様または能力追加ルールを変更した場合、必要に応じてこのE2E検証を再実行する。

## 8. 完了

能力追加Workは、通常の変更Work完了条件に加えて、個別Capability仕様とCapability Registryの整合および能力確認可能性が検証された場合に完了候補となる。

能力が追加されたことと、現在の環境でその能力がAVAILABLEであることを同一視してはならない（MUST NOT）。

能力追加機構そのものの成立確認では、第7章のE2E検証を通過できることを確認する。
