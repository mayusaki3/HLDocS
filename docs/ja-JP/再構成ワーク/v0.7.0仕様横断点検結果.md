## 3. CA-01 Capability ProviderとSubFlow

点検時、次の依存が許可されていた。

```text
Execution Capability
 ↓ provided_by
SubFlow
 ↓
Execution Capability
```

SubFlowはExecution Capabilityを利用して処理を構成する層であるため、Providerとしても扱うと循環依存を形成できる。

修正後:

```text
Practical Capability
 ↓
Execution Capability
 ↓
Capability Provider
 ├─ ENVIRONMENT_TOOL
 └─ HLDOCS_TOOL

Workflow
 ↓
SubFlow
 ↓ uses
Execution Capability
```

SubFlowをExecution CapabilityのCapability Providerから除外した。

これはSubFlowの再利用やPractical Capabilityの実現への利用を禁止するものではない。SubFlowは複数のExecution Capabilityを組み合わせた再利用可能処理を表現でき、その実行可能性は依存Execution Capabilityその他の開始条件から評価する。

## 4. CA-02 旧仕様との正本競合

新再構成仕様の`00_Core/01_HLDocSとは.md`と旧`00_共通/01_HLDocSとは.md`はいずれも`canonical_document: true`である。

旧仕様を比較用に残すことと、旧仕様が正本を名乗ることは別である。

現状のままでは、LLMまたは将来の仕様発見機構が旧仕様を正本として選択する可能性があるため、v0.7.0正本確定前に旧再構成対象群を非正本化する必要がある。

旧仕様は削除せず比較資料として保持できる。

## 5. CA-03〜05 未再構成層

新仕様は次を正式な責務領域として参照しているが、新構造側の個別仕様はまだ存在しない。

- SubFlow(サブフロー)
- Tool(ツール)
- Restriction Set(制限セット)

これは現時点では「循環依存」ではなく、再構成途中の未定義参照として扱う。

旧`00_共通`仕様をそのまま新仕様の不足部分として暗黙利用してはならない。

再構成時は旧仕様から必要事項を調査し、新Core/Capability/Restrictionモデルと整合する形で新仕様へ移す。

## 7. 次の再構成順序

未定義参照を減らすため、次の順序を基本とする。

1. 旧仕様群の正本競合を解消する。
2. Restriction Set共通仕様と登録/参照機構を再構成する。
3. Tool共通仕様をCapability Providerモデルへ合わせて再構成する。
4. SubFlow共通仕様をExecution Capability利用側として再構成する。
5. 上記3層を使う最小E2Eを実施する。
6. 旧仕様との差分を再点検する。

Toolより先にSubFlowを確定すると、Capability利用境界が再び曖昧になる可能性があるため、Provider/Tool側を先に固定する。

## 8. 判定

Core、State Machine、State、Work、Interaction、Workflow、Capabilityの再構成済み範囲は、主要責務境界について基本整合している。

ただしv0.7.0仕様全体としては、旧仕様の正本競合とSubFlow/Tool/Restriction Setの未再構成が残るため、全体再構成完了とは判定しない。
