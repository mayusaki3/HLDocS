生成フェーズ実行規約

本書は、HLDocS において **生成プロンプトおよびテンプレートを用いてドキュメントを生成・再作成する際に、

LLM が内部的に実行しなければならない処理フェーズとその順序を定義する**ための運用規約である。

本規約は、HLDocS の仕様・構造・document_type の意味論や内容そのものを定義するものではない。

あくまで、**生成処理における手続き的拘束条件（どの順序で、何を、どこまで行うか）**を明確化することを目的とする。

本書に定義される生成フェーズは、

共通生成プロンプトおよび document_type 別生成プロンプトにおいて、

**解釈・省略・順序変更されてはならない内部実行順序**として扱われなければならない。

本書は、「HLDocS 前提条件」という仕様が入力文書一覧に含まれ、

かつ当該仕様に基づく適用可否が確定している場合にのみ適用される。

「HLDocS 前提条件」が入力文書一覧に含まれない場合、

または当該仕様に基づく適用可否が確定していない場合、

本書に基づく判断・生成・再作成・工程実行を行ってはならない（MUST NOT）。

この場合に許可されるのは、提示された文書の受理および存在確認、

ならびに前提条件が未参照または未確定である旨の通知のみとする。

本規約における「入力文書一覧」の意味は、

前提条件仕様において定義された用語定義に従う。

---

1. 生成フェーズのプロンプト輸出要件

共通生成プロンプトおよび document_type 別生成プロンプトは、

本規約に定義された生成フェーズ（Phase 0〜Phase 7）を

**通常運用時のプロンプト単体でも実行可能な形で内包しなければならない（MUST）。**

ここでいう通常運用とは、

仕様本文が入力として与えられない状況で

「共通テンプレートを生成して」等の短い指示のみが与えられる状態を指す。

この場合でも LLM は、以下を内部処理として必ず実行しなければならない。

• Phase 0 : 成立条件検証

• Phase 1 : テンプレート抽出

• Phase 2 : テンプレート合成

• Phase 3 : 可変スロット生成

• Phase 4 : 実体化

• Phase 5 : Transport Encoding 適用

• Phase 6 : 構造検証

• Phase 7 : 出力

共通生成プロンプトおよび document_type 別生成プロンプトは、

これらの Phase を **解釈・省略・順序変更してはならない（MUST NOT）。**

また Phase 6 構造検証に失敗した場合、

LLM は出力を行ってはならない。

共通生成プロンプトおよび document_type 別生成プロンプトは、仕様を代替してはならず、仕様と矛盾する解釈・指示・構造定義を含んではならない（MUST NOT）。

---

1.1 document_type 別仕様との接続（MUST）

生成フェーズは、document_type 別仕様により定義された

本文意味論および本文構造に従って実行されなければならない（MUST）。

ここでいう document_type 別仕様とは、

対象 document_type の本文構造・本文意味論・禁止事項・出力境界を

定義した仕様文書を指す。

生成フェーズ実行時、LLM は以下を満たさなければならない（MUST）。

• document_type 別仕様が提示されている場合、

その仕様を本文生成の唯一の意味論根拠として使用すること

• document_type 別仕様に存在しない意味論・章構造・判断規則を

推測または補完してはならない（MUST NOT）

• document_type 別仕様とテンプレートの両方が存在する場合、

テンプレート構造を優先し、意味論は document_type 別仕様に従うこと

document_type 別仕様が提示されていない場合、

LLM は本文意味論を推測してはならない（MUST NOT）。

この場合の振る舞いは Phase 0（FAIL-FAST）の規定に従う。

---

2. 構造トークンと空行の規約

テンプレート範囲（`__COMMON_TEMPLATE_BEGIN__`〜`__COMMON_TEMPLATE_END__`）では、

構造表現として **03_共通ドキュメント構造.md に定義された構造トークンのみを使用しなければならない（MUST）。**

この範囲では、以下の記述を禁止する（MUST NOT）。

• 実際の空行

• `---`

• HTMLコメント

• 未定義トークン

• 構造トークンの前後に挿入された実空行

特に次の構造は許可されない。

<BLANK_LINE>

<BLANK_LINE>

上記は **構造トークン + 実空行** を含むため仕様違反となる。

空行を表現する場合は、必ず次の形式を用いる。

<BLANK_LINE>
<BLANK_LINE>

すなわち、テンプレート範囲内の構造は

**構造トークン列のみで構成されなければならない。**

---

3. 構造検証との関係

Phase 6 構造検証では、以下を必ず確認する。

1. テンプレート範囲内に実空行が存在しないこと

2. 構造トークンの前後に実空行が存在しないこと

3. 未定義トークンが存在しないこと

4. 構造トークン列が 03_共通ドキュメント構造.md の定義に一致すること

いずれかに違反する場合、

LLM は Phase 1 から **1回のみ再試行**を行う。

再試行後も検証に失敗した場合、

生成処理は失敗とし、

LLM は **失敗通知のみを出力しなければならない（MUST）。**

---

4. テンプレート合成規約（MUST）

4.1 共通テンプレート範囲

共通テンプレートは、以下のマーカーで囲まれた範囲のみをテンプレート範囲として扱う。

• `__COMMON_TEMPLATE_BEGIN__`

• `__COMMON_TEMPLATE_END__`

両マーカーは各 1 回ずつ必須とする。

---

4.2 document_type 別本文テンプレート範囲

document_type 別テンプレートは、以下のマーカーで囲まれた範囲のみを本文テンプレート範囲とする。

• `__BODY_TEMPLATE_BEGIN__`

• `__BODY_TEMPLATE_END__`

両マーカーは各 1 回ずつ必須とする。

---

4.3 本文差し込み位置

共通テンプレートには、本文差し込み位置として `__DOCUMENT_BODY__` を 1 箇所のみ定義する。

合成時は、document_type 別テンプレートの本文テンプレート範囲を **無加工で差し込む**。

---

4.4 無改変規則（MUST）

• テンプレート範囲内の内容は一切改変してはならない

• 空行削除・正規化・再構成は禁止する

• 合成処理は機械的操作のみとする

• プレースホルダおよび構造トークンの定義・値域・固定形式は、共通ドキュメント構造に従う

• 合成工程では、プレースホルダまたは構造トークンを解釈・実体化してはならない

---

5. 構造トークン規約（MUST）

本章は、テンプレート範囲内で **具体表現に依存せず文書構造を表現するための構造トークン**を定義する。

5.1 構造トークンの目的

• テンプレート範囲内で Markdown の具体構文（空行、`---`、HTML コメント等）を使用せずに、

論理構造上の区切りや順序を表現する

• テンプレート範囲の無装飾・無加工合成を成立させるための補助規約とする

5.2 既定の構造トークン

既定の構造トークン（値域）は、共通ドキュメント構造に定義されたものに従う。

本書は、構造トークンの値そのものを再定義しない。

5.3 使用規則（MUST）

• テンプレート範囲内で構造上の空行・区切り・LLM-MANAGED ブロックが必要な場合、

**必ず構造トークンを使用する**

• テンプレート範囲内に、

実際の空行、`---`、HTML コメントを直接記述してはならない

5.4 実体化の責務（MUST）

• 構造トークンおよびプレースホルダを具体表現へ変換する責務は、

**最終成果物を出力する直前の生成工程（実体化工程）**に属する

• テンプレート抽出工程およびテンプレート合成工程では、

構造トークンまたはプレースホルダを解釈・変換してはならない（MUST NOT）

• 実体化で許可される操作は、共通ドキュメント構造に定義された **意味等価な置換** のみである

置換以外（正規化、並べ替え、付加、削除、再構成）を行ってはならない（MUST NOT）

5.5 実体化の要件（MUST）

実体化の要件（各トークン／プレースホルダが具体表現として何に置換されるか）は、

共通ドキュメント構造に定義された要件に従う。

5.6 将来拡張（MUST）

• 新たな構造要素・プレースホルダ・構造トークンが必要になった場合、

**共通ドキュメント構造**に対して追記することで対応する

• 共通ドキュメント構造に定義せずに、

本書またはテンプレート範囲へ新しいトークンやプレースホルダを導入してはならない（MUST NOT）

• 本書は、共通ドキュメント構造に未定義の構造トークン／プレースホルダを

例示・仮置きとしても記載してはならない（MUST NOT）

---

6. 生成フェーズ順序（MUST）

本章は、document_type が確定し、

共通テンプレート・document_type 別テンプレート・生成プロンプトがすべて与えられている前提で、

LLM が最終成果物を生成する際の **内部処理順序および各フェーズの作業内容**を定義する。

LLM は、以下に定義する Phase 0 から Phase 7 までを **順序を変更せず** 実行しなければならない。

---

Phase 0: 入力検証（FAIL-FAST）

Phase 0 は、生成工程に入る前の **最終的な実行可否判定フェーズ**である。

本フェーズでは、以下を必ず検証しなければならない（MUST）。

• 適用される成立条件を満たしていると判断可能であること

ここでいう「適用される成立条件」とは、

「HLDocS 前提条件」に定義された成立条件を指す。

• mode / operation / document_type / target が、

利用者の明示指示または 0.2 の定義済みマッピングにより

Phase 0 判定時点で確定していること

• 対応する template / prompt がすべて提示されていること

• 本フェーズ以前の仕様に依存した推測判断を行っていないこと

本章における

「明示されていること」

「未指定でないこと」

とは、

利用者が各項目を逐語指定している場合に限られず、

0.2 の定義済みマッピングにより

Phase 0 判定時点で値が一意に確定している場合を含む（MUST）。

したがって、

0.2 の適用により mode / operation / document_type / target が確定する場合、

それらを未指定として扱ってはならない（MUST NOT）。

いずれかを満たさない場合、

LLM は生成フェーズを開始してはならない（FAIL-FAST）。

FAIL-FAST 時の出力可否および応答内容は、

生成プロンプト運用規約に従う。

Phase 0（FAIL-FAST）では、共通生成プロンプトを生成する場合に限り、

共通ドキュメントテンプレートおよび必要な本文テンプレートが

入力として実体提示されていることを必須条件として検証する。

提示がない場合、

LLM は生成フェーズを開始してはならない（FAIL-FAST）。

0.1 前提条件適用確認（MUST）

以下の場合に限り、

LLM は「HLDocS 前提条件」が入力として提示されていること、

および当該前提条件に基づき HLDocS 共通仕様が成立していることを

確認しなければならない（MUST）。

• 共通テンプレートを生成する場合

• 共通プロンプトを生成する場合

• 共通テンプレートを再作成する場合

• 共通プロンプトを再作成する場合

上記のいずれかに該当し、

かつ以下のいずれかに該当する場合、

LLM は生成フェーズ（Phase1〜Phase7）を開始してはならない（MUST NOT）。

• 「HLDocS 前提条件」が入力として提示されていない

• 前提条件に基づく共通仕様の成立可否が確定していない

この場合、

• 成果物本文を出力してはならない（MUST NOT）

• 停止通知のみを出力する（MUST）

0.2 mode / operation / document_type の定義済みマッピング

以下の単語が指示で与えられた場合、本規約はそれを仕様定義済みマッピングとして解釈する。

• 「共通テンプレート」を含む場合

- mode = meta

- document_type = template

• 「共通プロンプト」を含む場合

- mode = meta

- document_type = prompt

• 「生成」,「作成」または「出力」を含む場合

- operation = new

• 「再作成」,「再生成」または「再出力」を含む場合

- operation = recreate

• 「修正」または「patch」を含む場合

- operation = patch

本確定は推測ではない。本条に基づく仕様定義済みマッピングである。

上記に該当する場合、Phase 0 における

mode / operation / document_type 未明示を理由にFAIL-FAST してはならない（MUST NOT）。

0.2.0 target の定義済みマッピング（MUST）

指示文に以下の語句が含まれる場合、

「共通」

「共通テンプレート」

「共通プロンプト」

target は common と確定しなければならない（MUST）。

この場合、target 未指定を理由に Phase 0 FAIL-FAST としてはならない（MUST NOT）。

上記語句が存在しない場合、target は文脈または document_type 推定により確定する。

確定できない場合のみ Phase 0 FAIL-FAST とする（MUST）。

0.2.0a 定義済みマッピングの Phase 0 一般条文に対する優先（MUST）

0.2、0.2.0、0.2.1 により

mode / operation / document_type / target が確定する場合、

Phase 0 一般条文における

「明示されていること」

の条件は充足済として扱わなければならない（MUST）。

この場合、

利用者入力中に

mode / operation / document_type / target

という語が逐語出現しないことのみを理由に

FAIL-FAST してはならない（MUST NOT）。

0.2.1 短い通常運用指示に対する既定値適用後判定（MUST）

「共通テンプレートを生成して」

「共通プロンプトを生成して」

等の短い通常運用指示が与えられた場合、

LLM はまず 0.2 の定義済みマッピングを適用しなければならない（MUST）。

この適用後は、

mode / operation / document_type が

未指定であることを理由に

FAIL-FAST してはならない（MUST NOT）。

Phase 0 では、

0.2 により確定した値を入力として、

required inputs の充足可否を判定しなければならない（MUST）。

このとき LLM は、

0.2 によって確定した値をそのまま Phase 0 入力として使用しなければならない（MUST）。

追加の mode / operation / document_type / target 明示を利用者へ要求してはならない（MUST NOT）。

0.2.2 共通テンプレート new 生成の required inputs（MUST）

以下の条件をすべて満たす場合、

• mode = meta

• operation = new

• document_type = template

• 対象が common である

当該処理は

「共通テンプレートの新規生成」として扱う（MUST）。

この場合の Phase 0 required inputs は、

共通仕様を構成する正本仕様群そのものとする（MUST）。

この場合、

以下を required input として要求してはならない（MUST NOT）。

• 既存の共通テンプレート

• 既存の共通生成プロンプト

• document_type 別生成プロンプト

• document_type 別テンプレート

共通テンプレート new 生成において

既存の共通生成プロンプトまたは既存テンプレートの未提示を理由に

FAIL-FAST してはならない（MUST NOT）。

0.2.3 共通プロンプト new 生成の required inputs（MUST）

以下の条件をすべて満たす場合、

• mode = meta

• operation = new

• document_type = prompt

• 対象が common である

当該処理は

「共通生成プロンプトの新規生成」として扱う（MUST）。

この場合の Phase 0 required inputs は、

少なくとも以下を含まなければならない（MUST）。

• 共通仕様を構成する正本仕様群

Phase 6: 構造検証（非出力）

Phase 6 は、生成された文書が HLDocS の構造規約およびテンプレート規約に

適合していることを検証するフェーズである。

本フェーズは以下の2段階で構成される。

1. 実体化前検査

- Phase 3 完了後の状態（プレースホルダ・構造トークンが残っている状態）を対象とする

2. 実体化後検査

- Phase 4（実体化）および Phase 5（Transport Encoding 適用）後の

最終成果物実体を対象とする。

1) 成果物完全性検査

最終成果物実体に対して、以下の全文性条件を満たさなければならない（MUST）。

1. 文書末尾が途中語・途中トークンで終了していないこと。

2. HTMLコメント・括弧・引用・コードフェンスなどの対構造が未閉鎖で終わっていないこと。

3. 文書構造が明らかに途中で切断されていないこと。

4. HLDocS構造（LLM-MANAGED / 本文構造）が観測可能であること。

違反がある場合は成果物回収不完全（NG）とする。

2) HLDocS成果物検査

成果物がHLDocS形式である場合、以下の構造を満たしていなければならない（MUST）。

1. 文書先頭に LLM-MANAGED ブロックが存在する。

2. 共通ドキュメント構造に定義された順序に従う。

3. テンプレート成果物は固定トークン・固定行・配置制約を満たす。

4. プロンプト成果物は固定セクション・ENUM再掲・判定表再掲を含む。

5. LLM-MANAGED ブロックおよび階層リンク行は、HLDocS文書構造要素として本文領域に存在しなければならない。

6. HLDocS文書内部のコードフェンス内に、LLM-MANAGED ブロックまたは階層リンク行を配置してはならない（MUST NOT）。

7. ただし、Transport Encoding により HLDocS文書全体が外側コードフェンスで包まれている場合、

当該フェンスは文書外部フェンスとみなし、本検査の対象外とする。

違反した場合、成果物仕様不一致（NG）とする。

3) Transport Encoding 構造検査

最終成果物実体に対して、以下の構造検査を必ず実施しなければならない（MUST）。

1. コードフェンス（ ``` ）の総数は偶数でなければならない。

2. 言語指定フェンス（ ```markdown 等 ）には必ず対応する閉じフェンスが存在しなければならない。

3. フェンス開始後に閉じフェンスなしで別のフェンス開始が出現してはならない。

上記のいずれかに違反した場合、Transport Encoding 構造破壊として NG とする。

Transport Encoding に関する検証不適合は、生成結果不適合として扱う。

LLM は、本フェーズにおいて上記の検証を必ず実行しなければならない（MUST）。

検証結果を出力してはならない（MUST NOT）。

6.0 検証独立性原則（MUST）

Phase 6 における構造検証は、

生成処理の正当性を再確認する工程であり、

生成時の意図・内部判断・未出力状態を

根拠として使用してはならない（MUST NOT）。

LLM は検証時において、

以下のみを判断根拠として使用しなければならない（MUST）。

• Phase 5 完了時点の生成結果（最終成果物実体）

• 入力文書一覧に提示された仕様文書

• 共通仕様に定義された固定構造および固定文字列

以下を検証根拠として使用してはならない（MUST NOT）。

• 生成時の内部推論

• 生成過程で使用した一時的な解釈

• 出力されていない中間生成物

• LLM の意図・説明可能性・意味解釈

Phase 6 の検証は、

生成結果を **独立入力として再解釈した結果のみ**

に基づいて実施しなければならない。

以下の要素が最終成果物実体として観測できなければならない。

• 先頭階層リンク

• タイトル

• 本文領域

• 区切り線

• フッタ階層リンク

6.2.1 HLDocS 文書構造検査（参照検査）

• 本文領域の存在

• 区切り線の存在

6.2.1.1 共通テンプレート成果物完成形検査（MUST）

• 共通テンプレート成果物は

- 文書先頭に実体 LLM-MANAGED ブロック

- 本文冒頭の階層リンク

- タイトル

- 説明文（必須）

- テンプレート範囲

- 区切り線

- フッタ階層リンク

を持つ HLDocS 文書全体でなければならない

• テンプレート範囲のみを出力したものは NG

• 実体 LLM-MANAGED ブロックを `<LLM_MANAGED_BLOCK>` で置き換えたものは NG

• 階層リンク実体を `<HIERARCHICAL_LINK>` 等で置き換えたものは NG

6.2.1.2 本文先頭説明文存在検査（MUST）

説明文は、少なくとも1つ以上の自然言語文（句読点を含む文）で構成されていなければならない（MUST）。

ここでいう説明文とは、以下のいずれかを満たす連続した本文テキストを指す。

• 文書の用途または対象を説明している

• 適用対象または前提条件を説明している

• 文書の使用方法または構造意図を説明している

以下の場合、説明文欠落として NG とする。

• タイトル直後にテンプレート範囲または本文セクションが直ちに開始されている

• 説明文として解釈できる自然文が存在しない

• 説明文の代替として構造トークンまたはプレースホルダのみが存在する

本検査は document_type に依存せず、

「本文構造として説明文が存在すべき位置」に対して適用する（MUST）。

• 各構造空行が「ちょうど1行」であること

• 構造空行が欠落していないこと

• 構造空行が2行以上連続していないこと

LLM は以下の要素について、

個別項目ごとに適合性を確認しなければならない（MUST）。

• LLM-MANAGED ブロック

• 先頭階層リンク

• 本文領域

• 区切り線

• フッタ階層リンク

• 文書要素の順序

• 本文先頭説明文の存在

6.4 再試行規則（MUST）

Phase 6 において不適合が検出された場合、

LLM は **入力欠陥ではなく生成結果の構造不適合であると判断できる場合に限り、

Phase 1 から生成工程を 1 回だけ再実行してよい。**

再実行の対象となるのは、少なくとも以下のような生成結果不適合である。

• 文書要素の順序不一致

• プレースホルダ実体化の不整合

• 構造トークンの置換不整合

• テンプレート範囲構文違反

以下の場合、再試行を行ってはならない（MUST NOT）。

• Phase 0 で検出される成立条件不成立

• Phase 1 で検出されるテンプレートマーカー欠落または多重定義

• 必須入力文書の欠落

再試行は、Phase 6 において

構造不適合の原因が生成結果に起因する場合に限り許可される。

LLM は、同一不適合理由のまま

生成工程を再試行してはならない（MUST NOT）。

再試行を行う場合、

Phase 6 において検出された不適合カテゴリを

内部的に識別した上で、

当該不適合が再発しない形で生成工程を再実行しなければならない（MUST）。

再試行後も Phase 6 において不適合が検出された場合、Phase 7 は実行しない。

この場合に限り、Phase 6 の終了処理として失敗通知のみを外部へ返してよい。

---

6.5 失敗通知の形式（MUST）

Phase 6 において再試行後も不適合が検出された場合、

LLM は失敗通知のみを外部へ返すことができる。

この場合、失敗通知は以下の **失敗カテゴリ識別子のみ**を返してよい。

• `INPUT_ERROR`

必須入力文書不足、成立条件未成立

• `STRUCTURE_ERROR`

HLDocS 文書構造違反

• `TOKEN_ERROR`

未定義プレースホルダまたは未定義構造トークン

• `TEMPLATE_RANGE_ERROR`

テンプレート範囲マーカー違反

• `INVARIANT_ERROR`

不変条件違反

失敗通知では、以下を出力してはならない（MUST NOT）。

• Phase 6 の検証詳細

• 内部生成過程

• 中間生成物

• 修正候補

失敗通知は **カテゴリ識別子のみ**とする。

---

6.6 複数成果物生成規則（MUST）

生成工程において複数の成果物が生成される場合、

生成および構造検証は **成果物単位**で行わなければならない（MUST）。

LLM は各成果物について以下を独立して実行しなければならない（MUST）。

• Phase 1 : テンプレート抽出

• Phase 2 : テンプレート合成

• Phase 3 : 可変スロット生成

• Phase 4 : 実体化

• Phase 5 : Transport Encoding 適用

• Phase 6 : 構造検証

各成果物は Phase 6 において独立して検証され、

適合した成果物のみが Phase 7（出力）対象となる。

複数成果物の存在は、

生成工程の順序・構造・検証条件を変更してはならない（MUST NOT）。

成果物の提示方法および提示順序は

Transport Encoding 規約に従う。

ある成果物が Phase6 において不適合となった場合、

当該成果物のみ出力対象から除外される。

他の成果物の生成・検証・出力には影響を与えてはならない（MUST NOT）。

---

Phase 7: 出力

• 最終成果物を含む応答を出力する

• 中間生成物・検証結果・内部判断過程を出力してはならない

• 出力は Phase 5 の結果に従う

• 出力時に文書内容・構造・識別子を改変してはならない（MUST NOT）

---

7. document_type 検証規則（MUST）

• document_type は **ENUM 定義のみ許可**する

• document_type の正当性は、

[LLM-MANAGED ブロック規約](./04_LLM-MANAGEDブロック規約.md) に定義された ENUM に基づいて検証しなければならない

• 未定義 document_type を推測してはならない

• 必要なテンプレート・生成プロンプトが不足している場合は、

**生成を停止する**
