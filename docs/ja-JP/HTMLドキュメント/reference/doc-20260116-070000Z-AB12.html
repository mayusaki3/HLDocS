前提条件

本書は、HLDocS における **共通仕様の前提条件**を定義するものである。

ここでいう「共通仕様」とは、

HLDocS に基づくドキュメント生成・再作成・検証を行うために必要な

**前提・運用・構造・不変条件を定義した仕様群の総体**を指す。

共通仕様は、複数の仕様文書によって構成されるが、

**いずれか一部のみでは成立しない**。

本書は、

• 共通仕様が成立しているか否かを判断するための基準

• 共通仕様が未成立である場合の入力の扱い

を定義する。

共通仕様を構成する仕様要素（参考）

HLDocS 共通仕様は、以下の仕様要素によって構成される。

• 前提条件

• 生成プロンプト運用規約

• 共通ドキュメント構造

• LLM-MANAGED ブロック規約

• Transport Encoding 規約

• Traceability 規約

• 生成フェーズ実行規約

• 再作成時不変条件規約

• prompt成立条件規約

• ENUM 再掲要件規約

• 判定テーブル再掲要件規約

• 表示名リンク規約

• 表示名リンク成立条件補足

• 共通仕様完全一覧入力規約

• HTMLドキュメント生成規約

• HTML Site Manifest規約

• HTML出力単位規約

• HTMLディレクトリ構成規約

• HTML Traceability可視化規約

• HTML検査成績表規約

本一覧は、共通仕様の構成概念を示すものであり、

並び順・管理番号・ファイル構成・分割単位を規定するものではない。

成立判定における識別単位は、

文書番号・ファイル名・分割単位ではなく、

本一覧に列挙された **仕様要素そのもの** である（MUST）。

したがって成立判定では、

各仕様要素に対応する正本仕様が提示されているかを確認しなければならない（MUST）。

文書番号・ファイル分割・番号範囲

（例：01-05、06-10 等）を理由として

仕様要素が充足していると判断してはならない（MUST NOT）。

本一覧に含まれる仕様要素がすべて揃っている場合にのみ、

HLDocS 共通仕様は成立しているとみなされる。

本一覧を変更する場合、当該変更は共通仕様の変更として扱われ、

一覧自体を同時に更新しなければならない（MUST）。

HLDocS 共通仕様への新規仕様追加・仕様統合・仕様分割・migration・restructuring・HTML visualization 対応は、

単なるファイル追加ではなく、

共通仕様構造そのものの変更として扱わなければならない（MUST）。

したがって、共通仕様へ新規仕様文書を追加する場合、

少なくとも以下を同期更新しなければならない（MUST）。

• 本一覧

• 共通仕様完全一覧

• 目次

• 成立条件関連規約

• 必要に応じた生成プロンプト・検証プロンプト

• 必要に応じた template / prompt / visualization / operational representation

一部のみ更新し、

他の成立条件・一覧・運用表現を未更新のまま残してはならない（MUST NOT）。

Canonical Specification が変更された場合、

対応する Operational Representation も同期更新しなければならない（MUST）。

同期更新されていない Operational Representation は、

Canonical Specification と等価であるとみなしてはならない（MUST NOT）。

共通仕様の成立条件（MUST）

共通仕様は、以下の条件をすべて満たす場合にのみ **成立している** とみなす。

• 共通仕様を構成するすべての仕様要素が提示されていること

• 各仕様要素が、相互参照・前提関係を含めて一体として解釈可能であること

• 未提示の仕様要素に依存した判断を必要としない状態であること

• 「HLDocS 前提条件」が入力文書一覧に含まれていること

上記条件を満たさない場合、当該入力は **共通仕様としては未成立** である。

共通仕様が未成立である場合、

その入力は **検証・確認・差分検討を目的とした入力**としてのみ扱われ、

生成工程の前提とはみなされない。

共通仕様成立判定手順（MUST）

共通仕様の成立は、

生成工程開始前に **必ず明示的に判定されなければならない（MUST）**。

成立判定は、以下の手順をすべて満たす場合にのみ PASS とする。

1. 入力文書一覧を明示的に列挙すること

（判定時点で参照可能な文書のみを対象とする）

2. 本書に定義された

「共通仕様を構成する仕様要素」一覧を列挙すること

3. 上記 1 と 2 を突合し、

未提示の仕様要素が存在しないことを確認すること

4. 未提示の仕様要素が 1 つでも存在する場合、

共通仕様は未成立（FAIL）と判定しなければならない（MUST）

5. FAIL と判定された場合、

以下を行わなければならない（MUST）

- 生成工程を開始してはならない

- 成果物を一切出力してはならない

- 成果物と誤認され得る構造的出力も行ってはならない（MUST NOT）

- 未提示の仕様要素一覧を明示する

部分的に必要十分であるという判断、

生成対象に直接関係する仕様のみが提示されているという理由による

局所的充足判定は、成立判定として扱ってはならない（MUST NOT）。

共通仕様は **総体としてのみ成立する**。

総体成立を確認せずに生成工程へ進んではならない（MUST NOT）。

• 成立判定を外部に出力する場合は、少なくとも次を明示しなければならない

- 今回入力の完全ファイル名一覧

- 今回導出した正規化集合

- 共通仕様構成要素完全一覧

- 各要素の提示 / 未提示突合結果

- PASS / FAIL 最終宣言

• PASS の場合は未提示要素なしを明示

• FAIL の場合は未提示要素一覧を明示

• これらの証跡を欠く場合、成立判定結果は外部検証可能な成立判定として扱ってはならない

共通仕様成立判定アルゴリズム（MUST）

共通仕様成立判定は、以下のアルゴリズムを **順序どおりに機械的に実行**しなければならない（MUST）。

LLM は、本アルゴリズムに含まれない推測・補完・番号解釈・部分充足判定を行ってはならない（MUST NOT）。

1. 入力対象集合の確定

1. 判定時点で参照可能な入力文書本文のみを対象とし、入力文書一覧を確定する。

2. 参照可能性が不明な文書、存在のみ宣言された文書、本文未提示文書は入力文書一覧に含めてはならない（MUST NOT）。

2. 構成要素正本一覧の確定

1. 「共通仕様を構成する仕様要素」一覧を、そのまま正本一覧として採用する。

2. 成立判定の識別単位は、文書番号・ファイル名・添付順・分割単位ではなく、当該一覧に列挙された **仕様要素名そのもの** とする（MUST）。

3. 「HLDocS 前提条件」は、HLDocS 共通仕様成立条件の root document として扱わなければならない（MUST）。

4. 「HLDocS 前提条件」が入力文書一覧に存在しない場合、

共通仕様成立判定は直ちに FAIL としなければならない（MUST）。

3. 対応付け規則

1. 各入力文書は、LLM-MANAGEDブロックに記載された canonical_title から一意に識別できる仕様名に基づいて、構成要素正本一覧のいずれか **1要素にのみ** 対応付けなければならない（MUST）。

canonical_title 以外の情報（本文内容、説明文、章タイトル、キーワード等）を理由として仕様要素を推定してはならない（MUST NOT）。

2. 1つの入力文書を複数の仕様要素に対応付けてはならない（MUST NOT）。

3. 1つの仕様要素を複数の未統合な文書断片の合算で「提示済」とみなしてはならない（MUST NOT）。

4. 文書番号・番号範囲・添付順・チャット上の並び順

（例：01-05、06-10、前半、後半、続き）

を理由として、仕様要素の提示済判定を行ってはならない（MUST NOT）。

4. 要素単位突合

1. 構成要素正本一覧の各要素について、対応付け済み入力文書が存在するかを確認する。

2. 対応付け済み入力文書が存在する要素のみを「提示済」とする。

3. 対応付け済み入力文書が存在しない要素は「未提示」とする。

4. 対応付け不能な入力文書は、成立判定の充足根拠として使用してはならない（MUST NOT）。

5. PASS / FAIL 判定

1. 構成要素正本一覧の全要素が「提示済」の場合に限り PASS とする。

2. 1要素でも「未提示」が存在する場合は FAIL とする。

3. 「大半が提示済」「生成対象に直接必要なものは揃っている」「前段で一度提示された」等の理由により PASS としてはならない（MUST NOT）。

6. 外部出力証跡

成立判定を外部に出力する場合は、少なくとも以下をこの順で明示しなければならない（MUST）。

1. 今回入力の完全ファイル名一覧

2. 今回導出した正規化集合

3. 共通仕様構成要素完全一覧

4. 各要素の提示 / 未提示突合結果

5. PASS / FAIL 最終宣言

PASS の場合は「未提示要素なし」を明示しなければならない（MUST）。

FAIL の場合は未提示要素一覧を明示しなければならない（MUST）。

7. 禁止事項

LLM は、成立判定において以下を行ってはならない（MUST NOT）。

• 未提示文書を補完・推測・内部知識で代替すること

• 文書番号や番号範囲から仕様要素提示を推定すること

• 複数文書を暗黙統合して1仕様要素を提示済とみなすこと

• 仕様要素名ではなく文書数・添付数・番号連続性で充足判定すること

• 外部出力証跡を欠いたまま PASS / FAIL を確定すること

共通生成（テンプレート／プロンプト）開始条件（MUST）

共通テンプレート生成および共通プロンプト生成は、共通仕様が成立していることを条件とする。

すなわち、本書に定義された共通仕様成立条件を満たしていない場合、

共通テンプレート生成および共通プロンプト生成は開始してはならない（MUST NOT）。

用語：提示（provided / presented）（MUST）

生成工程における「提示」とは、

当該文書本文が入力として実体（テキスト）で与えられている状態を指す。

「〜を前提とする」「存在するはずである」等の宣言は、提示を意味しない。

提示されていない仕様・テンプレート・生成プロンプトを、

補完・推測・内部生成によって代替してはならない（MUST NOT）。

用語：入力文書一覧（effective input set）（MUST）

本仕様群における「入力文書一覧」とは、

当該チャットに **提示（provided / presented）** された文書本文（テキスト）の集合を指す。

入力文書一覧は、以下の 2 段階で扱われる（MUST）。

1) 含有（inclusion）

• 文書本文が当該チャットに **提示** された時点で、

当該文書は入力文書一覧に **含まれる**。

• 「提示」の定義は本書の「用語：提示（provided / presented）」に従う。

2) 有効性（effectiveness）

生成・再作成・工程実行の判定（Phase 0 等）においては、

入力文書一覧のうち、**判定時点で LLM が参照可能な状態にある文書**のみを

判断根拠として使用してよい（MUST）。

以下を満たさない文書は、判定時点の判断根拠として使用してはならない（MUST NOT）。

• 過去に提示されたが、判定時点で参照可能であることが保証されない

• 文書の存在が宣言されているだけで、本文テキストが入力として与えられていない

• 未提示要素を補完・推測・内部生成によって代替している

補足（誤読防止）：

• 「過去に一度提示された事実」だけでは、判定時点で参照可能であることを意味しない。

• したがって、生成・再作成・工程実行の可否判定は、

**判定時点で参照可能**であることによってのみ成立する。

3) 実行環境モデル（INFORMATIVE）

HLDocS における入力文書提示の具体的な運用は、

実行環境により次の 2 つのモデルを想定する。

1. 対話型運用（チャット環境）

文書本文は会話中の添付または提示として与えられる。

過去に提示された文書であっても、

判定時点で LLM が参照可能であることが保証されない場合、

当該文書は判断根拠として使用してはならない。

その場合、LLM は参照不可である旨を通知し、

人間が当該文書を再提示することで入力文書一覧に再度含める。

2. API 運用

API 環境では、実行ごとに入力が独立するため、

共通仕様および対象 document_type に必要な仕様文書本文は

リクエスト入力として毎回提示されることを想定する。

いずれの運用モデルにおいても、

生成・再作成・検証の判断根拠として使用できる文書は、

**判定時点で参照可能な文書本文に限られる。**

4) 運用表現モデル（INFORMATIVE）

HLDocS における共通仕様利用は、

少なくとも以下の 2 つの運用形態を想定する。

1. Canonical Specification Mode

正本仕様本文群を入力として利用する。

例：

- GitHub 上の仕様本文参照

- 添付された仕様本文

- file_search により参照される仕様本文

2. Operational Representation Mode

spec から生成された template / prompt / visualization 等の

圧縮運用表現を入力として利用する。

例：

- 共通生成プロンプト

- document_type 別生成プロンプト

- template

- HTML visualization

- viewer 用変換表現

Operational Representation は、

Canonical Specification と意味論的に整合していなければならない（MUST）。

Canonical Specification が変更された場合、

対応する Operational Representation も同期更新しなければならない（MUST）。

同期更新されていない Operational Representation は、

Canonical Specification と等価であるとみなしてはならない（MUST NOT）。

Operational Representation が未完成または未同期である場合、

HLDocS は preview 状態として扱われ得る。

1. 基本前提（MUST）

1.1 LLM の認識前提

• LLM は、本書および各仕様書の本文内容を **事前知識として保持していない**。

• LLM は、過去の会話文脈が保持されていることを前提としてはならない。

• 各ドキュメント生成・再生成は、**単体で完結し、再現可能**でなければならない。

1.1.1 生成結果検証原則（MUST）

LLM が生成した成果物の適合判定は、

生成時の意図または内部推論ではなく、

生成結果として出力された文書実体のみに基づいて行われなければならない（MUST）。

LLM は、

「自ら生成した結果であること」

を理由として適合判定を緩和してはならない（MUST NOT）。

生成結果の適合判定は、

生成を行った LLM 自身の判断に依存してはならない（MUST NOT）。

適合判定は、

生成結果として出力された文書実体に対して

独立した検査主体（人間または検証工程）によって

行われなければならない（MUST）。

1.2 仕様提示モデル

人間は、検討・検証・差分確認などの目的で、

共通仕様を構成する仕様文書の一部のみを提示する場合がある。

このような入力は、

**共通仕様の成立を意図したものではなく、

人間の明示的な指示に基づき、

LLM が提示された仕様と成果物候補との整合性を確認するための工程**

として扱われる。

LLM は、提示された仕様文書のみを判断根拠として使用し、

未提示の仕様要素を補完・推測・前提化してはならない（MUST NOT）。

1.2.1 検証入力時の禁止事項（MUST NOT）

共通仕様が成立していない入力に対して、

LLM は以下を **前提違反として扱わなければならない**。

• 当該入力を生成工程の前提として扱うこと

• 未提示の仕様要素を補完・推測・暗黙前提として扱うこと

• 共通仕様が成立しているかのように判断を進めること

生成工程の開始可否、

生成フェーズの実行条件、

FAIL-FAST の判定および振る舞いについては、

**生成フェーズ実行規約（07）および生成プロンプト運用規約（02）に従う。**

1.2.2 前提未成立時の判断抑止（MUST）

共通仕様が未成立である入力に対して、

LLM は **判断・分類・整理・工程化を行ってはならない**。

ここでいう「判断・分類・整理・工程化」には、

以下を含む（ただしこれらに限定されない）。

• 入力・仕様・添付文書に **存在しない**

工程名・段階名・分類名・ステップ名・記号列

（例：A/B/C、Step1/Step2 等）を、

便宜的であっても **自律的に導入すること**

• 上記のような語彙を、

判断根拠・論点整理軸・作業候補・工程候補として扱うこと

• 共通仕様が成立していない状態にもかかわらず、

成立後を前提とした解釈・整理・構造化を行うこと

前提未成立時に LLM が行ってよいのは、

以下に **厳密に限定**される。

• 提示された入力の受理

• 共通仕様が成立しているか否かの判定

• 提示された仕様文書の内容確認

• 人間から **明示的に指示された** 検証・確認行為

前提条件が満たされない限り、

LLM は生成工程・再作成工程・工程計画・改善提案を

**開始してはならない（MUST NOT）**。

1.2.3 非生成時の出力純度制約（MUST）

共通仕様が未成立である場合、

または本書に基づく生成工程・再作成工程が開始されていない場合、

LLM は HLDocS 管理下ドキュメントと誤認され得る出力を

行ってはならない（MUST NOT）。

ここでいう「誤認され得る出力」には、

以下を含む（ただしこれらに限定されない）。

• LLM-MANAGED ブロック

• 階層リンク行（「目次 > …」形式を含む）

• テンプレート構造トークン

• テンプレート開始／終了マーカー

• プレースホルダ（__XXX__ 形式）

• ENUM 再掲構造

• 判定テーブル断片

• Transport Encoding に該当する構造

• HLDocS 管理下ドキュメントの本文形式に準じる構造

• 成果物本文と区別不能な Markdown 構造

非生成時に LLM が出力してよい内容は、

以下に厳密に限定される。

• 共通仕様の成立／未成立の判定結果

• 判定理由

• 未提示仕様要素の列挙

• 条文番号の参照

• 人間から明示的に指示された確認・検証応答

上記以外の出力は、

成果物そのものではない場合であっても、

構造的に誤認を生じ得る限り、

禁止される（MUST NOT）。

1.3 表現形式に関する前提（MUST）

• 箇条書き・表・コードブロック等の**表現形式自体は制約対象ではない**。

• ただし、LLM は以下を厳守しなければならない。

- 表現形式によって、情報の**意味・役割・責務の層**を変更してはならない。

- 表として記述されていることを理由に、

判定規則・正本情報・再掲要件が

本来属さない位置へ移動したと解釈してはならない。

- 表は、既に仕様で定義された内容を

**逐語で再掲・視覚化する目的にのみ使用され得る**。

- 表現形式は意味論を持たず、

意味は必ず仕様上の定義位置によって決定される。

- 表形式であることを理由に、

内容の編集・正規化・最適化・再構成を行ってはならない（MUST NOT）。

- 表は、中間表現・編集対象・最適化対象として解釈してはならない。

2. HLDocS 不変条件（MUST）

2.1 構造不変条件

• すべての HLDocS 管理下ドキュメントは、共通ドキュメント構造に従う。

• LLM-MANAGED ブロックは、必ずドキュメント先頭に配置される。

• 階層リンク行は、先頭および末尾に **同一内容・同一位置** で再掲される。

• 全文差し替え生成において、階層リンク行を再生成・省略・移動してはならない（MUST NOT）。

2.2 同一性不変条件

• ドキュメントの論理的同一性は `doc_id` によってのみ識別される。

• ファイル名、パス、番号、言語、本文内容、見出し構造は

**同一性の判断材料とならない**。

2.2.1 識別子決定性の維持（MUST）

再作成（recreate）または差し替え（patch）において、

修正前正本が入力として提示されている場合、

LLM は当該正本に記載された `doc_id` を再生成してはならない（MUST NOT）。

`doc_id` / `sec_id` / `ref_id` について、

入力として提示された正本または対応仕様に基づく確定根拠が存在しない場合、

LLM はそれらを推測によって補完してはならない（MUST NOT）。

識別子の確定根拠が不足している場合、

当該識別子を必要とする生成・再作成・検証工程は未成立として扱わなければならない（MUST）。

3. LLM-MANAGED 管理原則（MUST）

3.1 管理責務

• LLM-MANAGED ブロック内の値は、**LLM のみが決定・更新する**。

• 人間による直接編集は、原則としてドキュメント同一性を破壊する行為とみなされる。

例外（MAY）

以下の場合に限り、人間が `doc_id` を削除または無効化する行為を許容する。

• 明示的なドキュメント分割を行い、新規ドキュメントとして再生成する場合

• 明示的な置換・廃止を行い、同一性の継承を行わない場合

これらの場合でも、**既存の doc_id を再利用してはならない**。

4. document_type と役割モデル（MUST）

• document_type は ENUM として扱われる。

• document_type は **処理対象の種別**を示す識別子であり、処理モード・生成フェーズ・運用状態を含意してはならない。

• document_type の変更は、論理的同一性の変更を意味しない。

• document_type は、構造・判断ロジック・生成順序を直接規定しない。

4.1 他仕様との関係

• document_type に関する詳細なキー定義および編集規約は、

[**LLM-MANAGED ブロック規約**](./04_LLM-MANAGEDブロック規約.md) に従う。

• 本章は、それらを束ねる **前提モデルの宣言** であり、

個別仕様の内容を上書きしない。

4.2 document_type: template の責務（MUST）

• template は、HLDocS 管理下ドキュメントの **構造（骨格）** を定義する。

• template は、判断ロジック・条件分岐・検査手順・出力方式の選択規則を

**含めてはならない（MUST NOT）**。

• template は、共通テンプレートおよび document_type 別テンプレートとして提供され得る。

• template の意味・役割は、名称から推測してはならず、

仕様および生成プロンプトにより規定される。

テンプレートに含まれる説明文は、テンプレートマーカー

（例：__COMMON_TEMPLATE_BEGIN__ ～ __COMMON_TEMPLATE_END__）

の外側に配置されなければならない（MUST）。

テンプレートマーカー内部には、

説明文・補足文・注釈を含めてはならない（MUST NOT）。

テンプレートマーカー内部は、

テンプレート構造を定義する構造トークンのみで構成される。

補足：説明文の扱い（MUST）

• template には、テンプレートマーカーで囲まれた範囲とは別に、

**人間向けの説明文・補足文** が含まれていてもよい。

• これらの説明文は **人間の理解・レビューのための補助情報**であり、

LLM は生成・判断・検証の根拠として **解釈してはならない（MUST NOT）**。

• LLM が意味論として解釈してよいのは、

**テンプレートマーカーで明示的に指定された範囲のみ**である。

4.3 document_type: prompt の責務（MUST）

• prompt は、LLM の **判断・振る舞い・内部自己検査** を規定する。

• prompt は、構造（骨格）を規定してはならない（MUST NOT）。

• prompt は、共通生成プロンプトおよび document_type 別生成プロンプトとして提供され得る。

• prompt は、**仕様を代替するものではなく、仕様を機械的に実装するための判断規範**である。

• prompt の意味・役割は、名称や表現から推測してはならず、

仕様および生成プロンプトにより規定される。

仕様の不足・不備・未確定を理由として、

生成プロンプトの修正・改善・再設計を行ってはならない（MUST NOT）。

生成プロンプトは生成対象であり、

検証工程における改善対象・調整対象・提案対象ではない。

生成プロンプトの変更は、

人間が仕様を修正した結果としてのみ行われる。

---

4.4 利用者操作モデル（MUST）

HLDocS に準拠したドキュメント生成において、利用者は以下のみを行えばよい。

• 共通 template を LLM に与える

• 共通 prompt を LLM に与える

• 対象 document_type に対応する template を LLM に与える

• 対象 document_type に対応する prompt を LLM に与える

• 生成したい内容（テーマ・対象・範囲など）を指示する

template および prompt は、

**あらかじめ spec から生成された成果物であることを前提**とし、

利用者がそれらの内部構造や生成規則を理解する必要はない。

ただし、template / prompt / visualization 等の運用表現が、

Canonical Specification と意味論的に一致している保証が存在しない場合、

Canonical Specification を正本仕様として優先しなければならない（MUST）。

運用表現の不足・未同期・再構成途中状態・migration 中状態は、

HLDocS preview 状態として扱われ得る。

---

4.5 document_type 別仕様の必須定義項目（MUST）

document_type 別仕様は、対象 document_type の本文意味論および

本文構造を定義する仕様文書である。

document_type 別仕様は、以下の項目を必ず定義しなければならない（MUST）。

1. 本文意味論

- 当該 document_type が表現する情報の意味

- 本文の目的および役割

2. 本文構造

- 本文の章構成または論理構造

- 本文テンプレートの基本形

3. 出力境界

- 本文に含める情報の範囲

- 本文に含めてはならない情報

4. 禁止事項

- 本文に含めてはならない構造

- 本文に含めてはならない意味要素

5. テンプレート範囲解釈規則

- template 文書に含まれるテンプレート範囲の扱い

- 本文生成に使用するテンプレート範囲

6. 生成プロンプトとの関係

- 対応する document_type 別生成プロンプトが

本仕様を意味論根拠として使用すること

7. document_type 成立条件

- 当該 document_type の生成・再作成・検証を

開始するために満たさなければならない条件

- 当該 document_type に固有の仕様要素

（例：必要テンプレート、必要プロンプト、追加仕様文書等）

- 成立条件が満たされない場合の扱い

（生成工程未成立、FAIL 等）

上記項目のいずれかが定義されていない場合、

当該 document_type の仕様は未成立とみなされる。

この場合、

LLM は当該 document_type の生成意味論・生成条件・成立条件を

推測または補完してはならない（MUST NOT）。

当該 document_type に関する生成・再作成・検証工程は

開始してはならない（MUST NOT）。

---

4.6 document_type 別仕様の成立条件（MUST）

document_type 別生成・再作成・検証を行う場合、

対象 document_type に対応する document_type 別仕様が、

入力文書一覧に提示され、かつ参照可能でなければならない（MUST）。

対象 document_type の仕様が提示されていない場合、

LLM は当該 document_type の本文意味論・本文構造・禁止事項・出力境界を

推測または補完してはならない（MUST NOT）。

この場合、当該 document_type の生成工程は未成立とみなし、

生成・再作成・工程実行を開始してはならない（MUST NOT）。

document_type 別仕様の成立判定は、

共通仕様成立判定とは独立に、

対象 document_type ごとに行われなければならない（MUST）。

4.6.1 document_type 別仕様の構成単位（MUST）

対象 document_type の仕様が複数文書によって構成される場合、

当該 document_type の成立に必要な仕様要素一覧は、

当該 document_type 側の仕様文書内で明示的に列挙されていなければならない（MUST）。

明示的に列挙されていない場合、

LLM は必要仕様要素の範囲を推測してはならない（MUST NOT）。

この場合、当該 document_type の成立可否は未確定とみなし、

生成・再作成・工程実行を開始してはならない（MUST NOT）。

5. 全文差し替え生成に関する前提（再発防止）（MUST）

本書および HLDocS 管理下のすべての仕様において、

「全文差し替え生成」とは、修正前正本に含まれる

すべての構造および本文を、実体として再出力する操作を指す。

全文差し替え生成を行う場合、以下を必ず満たさなければならない（MUST）。

• 修正前正本に存在する章・節・本文を、省略・要約・統合してはならない

• 修正対象外の章・節についても、必ず正規本文を実体出力しなければならない

• 成果物本文中に、以下の表現を含めてはならない（MUST NOT）

- 「修正前正本と同一」

- 「変更なし」「省略」「以下略」

- 編集指示・作業注記・差分説明

それは HLDocS の **世代（generation）が変わること** を意味する。

• 世代情報は、本ドキュメント体系とは独立した

**HLDocS 管理外ファイル** として管理する。
