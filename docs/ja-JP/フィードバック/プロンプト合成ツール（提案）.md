結論：有効。むしろ「prompt仕様策定で行く」なら、プロンプト/テンプレート合成ツールは整合性と再現性の要になる。

---

# 1. 何が解決できるか（目的）

## 1.1 再現性の担保
- 「どのテンプレート」「どのプロンプト」「どの順序」で合成したかを固定できる。
- 会話文脈や人手コピペによる揺れを排除できる。

## 1.2 prompt仕様（PROMPT_BODY抽出）との整合
- document_type: prompt の本文から PROMPT_BODY だけを抽出し、LLM入力に組み込める。
- 「成果物（HLDocS管理下）」と「実行体（LLMに渡す文字列）」の二層モデルを機械的に運用できる。

## 1.3 破壊検査（NG/WARN）を自動化できる
- 合成前（個別ファイル）と合成後（最終入力）の両方に検査をかけられる。
- NGなら「LLMに渡さない」を徹底できる。

---

# 2. あるべきツールの要件（最小）

## 2.1 入力
- 共通テンプレート（template）
- document_type別テンプレート（template）
- 共通プロンプト（prompt成果物からPROMPT_BODY抽出）
- document_type別プロンプト（prompt成果物からPROMPT_BODY抽出）
- 任意：ジョブ定義（どの組み合わせで合成するか）

## 2.2 出力
- 合成済み最終プロンプト（LLMに渡す文字列）
- 合成メタ（trace）
  - 使ったファイル一覧
  - doc_id（prompt成果物のdoc_id）
  - 抽出したPROMPT_BODY範囲（行番号等）
  - 合成順序
- 検査結果（NG/WARN）

## 2.3 重要な動作
- PROMPT_BODYの抽出（prompt仕様で確定した境界記法に従う）
- 合成順序の固定（例：template→promptの順、共通→typeの順）
- NGが1つでもあれば終了コード=1（CIでfail可能）

---

# 3. ツール構成案（リポジトリ内の置き場所）

- HLDocS管理下（docs/）ではなく、管理外の実装領域に置くのが妥当
  - 例：`tools/` または `scripts/`
- 仕様（使い方・I/F）は docs で管理可能（specとして）

---

# 4. あなたの現状方針との整合

- 「テンプレート配下のプロンプトは仕様確定まで保留」
  - OK。先に prompt仕様（PROMPT_BODY）を固める必要がある。
- ツールは、仕様確定後に
  - prompt成果物の抽出
  - 合成
  - 検査
  を一気通貫で実装できる。

---

# 5. 次ステップ（提案：順序固定）

1) document_type: prompt 仕様を確定
   - PROMPT_BODY境界記法（BEGIN/END）を確定
   - PROMPT_BODY内の禁止・検査観点を確定

2) 検証ツール（validate）を先に最小実装
   - HLDocS構造チェック（NG/WARN）
   - PROMPT_BODY抽出チェック（境界欠落＝NG 等）

3) 合成ツール（compose）を実装
   - 合成結果＋trace出力
   - validateを前後で実行（fail-fast）
