# HLDocS 前提条件

本書は、HLDocS における **共通仕様の前提条件**を定義するものである。

ここでいう「共通仕様」とは、  
HLDocS に基づくドキュメント生成・再作成・検証を行うために必要な  
**前提・運用・構造・不変条件を定義した仕様群の総体**を指す。

共通仕様は、複数の仕様文書によって構成されるが、  
**いずれか一部のみでは成立しない**。

本書は、  
- 共通仕様が成立しているか否かを判断するための基準  
- 共通仕様が未成立である場合の入力の扱い  

を定義する。

### 共通仕様を構成する仕様要素（参考）

HLDocS 共通仕様は、以下の仕様要素によって構成される。

- 前提条件
- 生成プロンプトの運用規約
- 共通ドキュメント構造
- LLM-MANAGED ブロック規約
- Transport Encoding 規約
- Traceability 規約
- 生成フェーズ実行規約
- 再作成時の不変条件規約
- 生成プロンプト成立条件規約
- ENUM 再掲要件規約
- 判定テーブル再掲要件規約

本一覧は、共通仕様の構成概念を示すものであり、
並び順・管理番号・ファイル構成・分割単位を規定するものではない。  
本一覧に含まれる仕様要素がすべて揃っている場合にのみ、
HLDocS 共通仕様は成立しているとみなされる。  
本一覧を変更する場合、当該変更は共通仕様の変更として扱われ、
一覧自体を同時に更新しなければならない（MUST）。

### 共通仕様の成立条件（MUST）

共通仕様は、以下の条件をすべて満たす場合にのみ **成立している** とみなす。

- 共通仕様を構成するすべての仕様要素が提示されていること
- 各仕様要素が、相互参照・前提関係を含めて一体として解釈可能であること
- 未提示の仕様要素に依存した判断を必要としない状態であること

上記条件を満たさない場合、当該入力は **共通仕様としては未成立** である。  
共通仕様が未成立である場合、
その入力は **検証・確認・差分検討を目的とした入力**としてのみ扱われ、
生成工程の前提とはみなされない。

### 共通プロンプト生成成立条件（MUST）

共通プロンプト生成成立条件は、共通仕様が成立していることを条件とする。  
すなわち、本書に定義された共通仕様成立条件を満たしていない場合、
共通プロンプト生成は開始してはならない（MUST NOT）。

### 共通テンプレート生成成立条件（MUST）

共通テンプレート生成成立条件は、共通仕様を構成する仕様要素のうち、
テンプレート構造に影響を与える仕様要素が入力文書一覧に含まれていることを条件とする。  
ここでいう「テンプレート構造に影響を与える仕様要素」とは、
少なくとも以下を含まなければならない（MUST）。

- 共通ドキュメント構造
- LLM-MANAGED ブロック規約
- Transport Encoding 規約
- 生成フェーズ実行規約
- 再作成不変条件規約

上記が欠落している場合、
共通テンプレート生成は開始してはならない（MUST NOT）。  
なお、共通テンプレート生成成立条件と共通仕様成立条件は、必ずしも同一ではない。

### 用語：提示（provided / presented）（MUST）

生成工程における「提示」とは、
当該文書本文が入力として実体（テキスト）で与えられている状態を指す。  
「〜を前提とする」「存在するはずである」等の宣言は、提示を意味しない。  
提示されていない仕様・テンプレート・生成プロンプトを、
補完・推測・内部生成によって代替してはならない（MUST NOT）。

### 用語：入力文書一覧（effective input set）（MUST）

本仕様群における「入力文書一覧」とは、
当該チャットに **提示（provided / presented）** された文書本文（テキスト）の集合を指す。  
入力文書一覧は、以下の 2 段階で扱われる（MUST）。

#### 1) 含有（inclusion）

- 文書本文が当該チャットに **提示** された時点で、
  当該文書は入力文書一覧に **含まれる**。
- 「提示」の定義は本書の「用語：提示（provided / presented）」に従う。

#### 2) 有効性（effectiveness）

生成・再作成・工程実行の判定（Phase 0 等）においては、
入力文書一覧のうち、**判定時点で LLM が参照可能な状態にある文書**のみを
判断根拠として使用してよい（MUST）。

以下を満たさない文書は、判定時点の判断根拠として使用してはならない（MUST NOT）。

- 過去に提示されたが、判定時点で参照可能であることが保証されない
- 文書の存在が宣言されているだけで、本文テキストが入力として与えられていない
- 未提示要素を補完・推測・内部生成によって代替している

補足（誤読防止）：
- 「過去に一度提示された事実」だけでは、判定時点で参照可能であることを意味しない。
- したがって、生成・再作成・工程実行の可否判定は、
  **判定時点で参照可能**であることによってのみ成立する。

## 1. 基本前提（MUST）

### 1.1 LLM の認識前提

- LLM は、本書および各仕様書の本文内容を **事前知識として保持していない**。
- LLM は、過去の会話文脈が保持されていることを前提としてはならない。
- 各ドキュメント生成・再生成は、**単体で完結し、再現可能**でなければならない。

### 1.2 仕様提示モデル

人間は、検討・検証・差分確認などの目的で、
共通仕様を構成する仕様文書の一部のみを提示する場合がある。  
このような入力は、
**共通仕様の成立を意図したものではなく、
人間の明示的な指示に基づき、
LLM が提示された仕様と成果物候補との整合性を確認するための工程**
として扱われる。  
LLM は、提示された仕様文書のみを判断根拠として使用し、
未提示の仕様要素を補完・推測・前提化してはならない（MUST NOT）。

#### 1.2.1 検証入力時の禁止事項（MUST NOT）

共通仕様が成立していない入力に対して、
LLM は以下を **前提違反として扱わなければならない**。

- 当該入力を生成工程の前提として扱うこと
- 未提示の仕様要素を補完・推測・暗黙前提として扱うこと
- 共通仕様が成立しているかのように判断を進めること

生成工程の開始可否、
生成フェーズの実行条件、
FAIL-FAST の判定および振る舞いについては、
**生成フェーズ実行規約（07）および生成プロンプト運用規約（02）に従う。**

#### 1.2.2 前提未成立時の判断抑止（MUST）

共通仕様が未成立である入力に対して、
LLM は **判断・分類・整理・工程化を行ってはならない**。  
ここでいう「判断・分類・整理・工程化」には、
以下を含む（ただしこれらに限定されない）。

- 入力・仕様・添付文書に **存在しない**  
  工程名・段階名・分類名・ステップ名・記号列  
  （例：A/B/C、Step1/Step2 等）を、  
  便宜的であっても **自律的に導入すること**
- 上記のような語彙を、  
  判断根拠・論点整理軸・作業候補・工程候補として扱うこと
- 共通仕様が成立していない状態にもかかわらず、  
  成立後を前提とした解釈・整理・構造化を行うこと

前提未成立時に LLM が行ってよいのは、
以下に **厳密に限定**される。

- 提示された入力の受理
- 共通仕様が成立しているか否かの判定
- 提示された仕様文書の内容確認
- 人間から **明示的に指示された** 検証・確認行為

前提条件が満たされない限り、
LLM は生成工程・再作成工程・工程計画・改善提案を
**開始してはならない（MUST NOT）**。

### 1.3 表現形式に関する前提（MUST）

- 箇条書き・表・コードブロック等の**表現形式自体は制約対象ではない**。
- ただし、LLM は以下を厳守しなければならない。

  - 表現形式によって、情報の**意味・役割・責務の層**を変更してはならない。
  - 表として記述されていることを理由に、
    判定規則・正本情報・再掲要件が
    本来属さない位置へ移動したと解釈してはならない。
  - 表は、既に仕様で定義された内容を
    **逐語で再掲・視覚化する目的にのみ使用され得る**。
  - 表現形式は意味論を持たず、
    意味は必ず仕様上の定義位置によって決定される。
  - 表形式であることを理由に、
    内容の編集・正規化・最適化・再構成を行ってはならない（MUST NOT）。
  - 表は、中間表現・編集対象・最適化対象として解釈してはならない。

## 2. HLDocS 不変条件（MUST）

### 2.1 構造不変条件

- すべての HLDocS 管理下ドキュメントは、共通ドキュメント構造に従う。
- LLM-MANAGED ブロックは、必ずドキュメント先頭に配置される。
- 階層リンク行は、先頭および末尾に **同一内容・同一位置** で再掲される。
- 全文差し替え生成において、階層リンク行を再生成・省略・移動してはならない（MUST NOT）。

### 2.2 同一性不変条件

- ドキュメントの論理的同一性は `doc_id` によってのみ識別される。
- ファイル名、パス、番号、言語、本文内容、見出し構造は  
  **同一性の判断材料とならない**。

---

## 3. LLM-MANAGED 管理原則（MUST）

### 3.1 管理責務

- LLM-MANAGED ブロック内の値は、**LLM のみが決定・更新する**。
- 人間による直接編集は、原則としてドキュメント同一性を破壊する行為とみなされる。

#### 例外（MAY）

以下の場合に限り、人間が `doc_id` を削除または無効化する行為を許容する。

- 明示的なドキュメント分割を行い、新規ドキュメントとして再生成する場合
- 明示的な置換・廃止を行い、同一性の継承を行わない場合

これらの場合でも、**既存の doc_id を再利用してはならない**。

## 4. document_type と役割モデル（MUST）

- document_type は ENUM として扱われる。
- document_type は **処理対象の種別**を示す識別子であり、処理モード・生成フェーズ・運用状態を含意してはならない。
- document_type の変更は、論理的同一性の変更を意味しない。
- document_type は、構造・判断ロジック・生成順序を直接規定しない。

### 4.1 他仕様との関係

- document_type に関する詳細なキー定義および編集規約は、  
  [**LLM-MANAGED ブロック規約**](./04_LLM-MANAGEDブロック規約.md) に従う。
- 本章は、それらを束ねる **前提モデルの宣言** であり、  
  個別仕様の内容を上書きしない。

### 4.2 document_type: template の責務（MUST）

- template は、HLDocS 管理下ドキュメントの **構造（骨格）** を定義する。
- template は、判断ロジック・条件分岐・検査手順・出力方式の選択規則を  
  **含めてはならない（MUST NOT）**。
- template は、共通テンプレートおよび document_type 別テンプレートとして提供され得る。
- template の意味・役割は、名称から推測してはならず、  
  仕様および生成プロンプトにより規定される。

#### 補足：説明文の扱い（MUST）

- template には、テンプレートマーカーで囲まれた範囲とは別に、  
  **人間向けの説明文・補足文** が含まれていてもよい。
- これらの説明文は **人間の理解・レビューのための補助情報**であり、  
  LLM は生成・判断・検証の根拠として **解釈してはならない（MUST NOT）**。
- LLM が意味論として解釈してよいのは、  
  **テンプレートマーカーで明示的に指定された範囲のみ**である。

### 4.3 document_type: prompt の責務（MUST）

- prompt は、LLM の **判断・振る舞い・内部自己検査** を規定する。
- prompt は、構造（骨格）を規定してはならない（MUST NOT）。
- prompt は、共通生成プロンプトおよび document_type 別生成プロンプトとして提供され得る。
- prompt は、**仕様を代替するものではなく、仕様を機械的に実装するための判断規範**である。
- prompt の意味・役割は、名称や表現から推測してはならず、  
  仕様および生成プロンプトにより規定される。

仕様の不足・不備・未確定を理由として、
生成プロンプトの修正・改善・再設計を行ってはならない（MUST NOT）。  
生成プロンプトは生成対象であり、
検証工程における改善対象・調整対象・提案対象ではない。  
生成プロンプトの変更は、
人間が仕様を修正した結果としてのみ行われる。

---

## 4.4 利用者操作モデル（MUST）

HLDocS に準拠したドキュメント生成において、利用者は以下のみを行えばよい。

- 共通 template を LLM に与える
- 共通 prompt を LLM に与える
- 対象 document_type に対応する template を LLM に与える
- 対象 document_type に対応する prompt を LLM に与える
- 生成したい内容（テーマ・対象・範囲など）を指示する

template および prompt は、  
**あらかじめ spec から生成された成果物であることを前提**とし、  
利用者がそれらの内部構造や生成規則を理解する必要はない。

---

## 5. 全文差し替え生成に関する前提（再発防止）（MUST）

本書および HLDocS 管理下のすべての仕様において、
「全文差し替え生成」とは、修正前正本に含まれる
すべての構造および本文を、実体として再出力する操作を指す。  
全文差し替え生成を行う場合、以下を必ず満たさなければならない（MUST）。

- 修正前正本に存在する章・節・本文を、省略・要約・統合してはならない
- 修正対象外の章・節についても、必ず正規本文を実体出力しなければならない
- 成果物本文中に、以下の表現を含めてはならない（MUST NOT）
  - 「修正前正本と同一」
  - 「変更なし」「省略」「以下略」
  - 編集指示・作業注記・差分説明

## 6. 前提変更に関する注意（IMPORTANT）

- 本書に記載された前提条件を変更する場合、  
  それは HLDocS の **世代（generation）が変わること** を意味する。
- 世代情報は、本ドキュメント体系とは独立した  
  **HLDocS 管理外ファイル** として管理する。
