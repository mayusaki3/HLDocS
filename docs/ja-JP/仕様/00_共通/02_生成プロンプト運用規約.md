# 生成プロンプト運用規約

本書は、HLDocS において **生成プロンプトおよびテンプレートを設計・生成・再生成・運用する際の運用上の前提条件**を定義する。  
本書は、仕様（spec）・構造・document_type 間の意味論そのものを定義する文書ではない。

本書の目的は、  
各仕様からテンプレートおよび生成プロンプトを作成・更新する際に、  
**どの層で何を判断し、何を判断してはならないか**という  
運用上の境界条件を明示することにある。

生成プロンプトは、  
逐語再掲された ENUM・判定テーブルを含む限りにおいて、  
仕様本文が入力として与えられていない状態でも  
判断規範として単体成立しなければならない。

---

## 1. 本書の位置づけ（MUST）

- 本書は **運用規約（operational rule）** である。
- 本書は、以下の成果物を設計・生成・更新する際の前提条件を規定する。
  - 共通テンプレート
  - document_type 別テンプレート
  - 共通生成プロンプト
  - document_type 別生成プロンプト
- 本書は、生成プロンプトの成立条件そのものを新たに定義するものではなく、
  生成プロンプトの設計・運用における判断境界を規定する。

それらの詳細定義は、以下の共通規約に委譲される。

- 生成フェーズ実行規約
- 再作成不変条件規約
- prompt 成立条件規約
- ENUM 再掲要件規約
- 判定テーブル再掲要件規約
- LLM-MANAGED ブロック規約

---

## 2. 想定する生成利用モデル（前提）

### 2.1 入力モデル（MUST）

生成フェーズにおいて、LLM に与えられる入力は以下に限定される。

- 共通テンプレート
- document_type 別テンプレート
- 共通生成プロンプト
- document_type 別生成プロンプト

以下は、共通仕様が成立している場合に限り、生成フェーズの判断根拠として省略され得る。

- 仕様本文（spec）
- 規約本文
- 説明用ドキュメント

生成プロンプトは、  
**仕様や規約が入力として与えられていない状態でも、単体で判断規範として成立している必要がある。**

ただし、本書における「仕様本文が入力として与えられていない状態」とは、
前提条件により共通仕様が成立していると判断された場合に限り、
生成フェーズにおいて spec を省略する運用形態を指す。

共通仕様の成立可否の最終判断および、
未成立時の取り扱いについては 第9章に従う。

---

### 2.2 生成プロンプトにおける仕様再掲の扱い

生成プロンプトは、  
仕様・構造・識別子・ENUM 値を **再定義してはならない（MUST NOT）**。

ただし、生成フェーズにおける判断材料を与える目的に限り、  
仕様からの **逐語再掲または意味等価再掲** を許可する。

再掲の可否・範囲・形式は、  
ENUM 再掲要件規約および判定テーブル再掲要件規約に従わなければならない。

#### 再掲の基本条件（MUST）

- 再掲は逐語、または意味等価かつ不変でなければならない
- 再掲内容に対し、変更・要約・補足・省略・再解釈を行ってはならない
- 再掲は判断材料としてのみ使用され、  
  仕様の代替・上書き・再定義を目的としてはならない

---

## 3. 生成プロンプト設計における禁止原理（MUST）

生成プロンプトは、以下を行ってはならない。

- 仕様・テンプレート・規約を再解釈・補完・要約すること
- 利用者から与えられていない仕様上の欠落を、推測により補うこと
- LLM-MANAGED ブロックに属するメタデータ領域を侵害すること
- document_type と生成モード等の異なる概念を合成した用語を導入すること

これらの禁止原理は、  
生成フェーズ構成・再作成不変条件・内部自己検査よりも **常に優先** される。

---

## 4. 仕様（spec）と生成プロンプト（prompt）の関係（禁止原理）

本章は、
仕様（spec）が入力として与えられている場合と、
与えられていない場合における prompt の振る舞い差に関する
禁止原理を定義する。

生成プロンプト（prompt）は、  
**生成フェーズにおいて判断規範として単体成立していなければならない**。

ただし、以下の禁止原理を必ず満たさなければならない。

- prompt は、仕様（spec）を上書き・再定義・補完してはならない（MUST NOT）
- 仕様（spec）が入力として与えられている場合、  
  prompt は当該仕様と意味的に矛盾してはならない（MUST）
- 仕様（spec）が入力として与えられていない場合であっても、  
  prompt は新たな判断基準・制約・例外を導入してはならない（MUST NOT）

本章は、  
「prompt が spec の代替として振る舞う」ことを許可するものではない。  
**判断根拠の使用可否に関する禁止原理のみ**を定義する。

---

## 5. 生成対象 prompt 自己参照の禁止（MUST）

本章の規定は、本書における他の規定に優先して適用される。

LLM は、生成対象となっている prompt 本文を、  
判断根拠・仕様補完・制約導出のために参照してはならない。

### 5.1 基本原則（MUST NOT）

LLM は、生成対象となっている prompt 本文そのものを、  
以下の目的で判断根拠として使用してはならない。

- 意味解釈
- 設計判断
- 仕様補完
- 制約導出
- 禁止事項・許可条件の判断
- 再作成時の差分判断

### 5.2 meta モードにおける特則（MUST NOT）

meta モードでは、生成対象 prompt は  
**意味的に判断不能な成果物**として扱われなければならない。

許可される参照は、以下の **不変項目の機械的保持のみ**である。

- doc_id
- canonical_title
- document_type
- 文書全体の構造順序
- 階層リンク行（先頭・末尾）

本文内容は、生成結果に一切影響してはならない。

### 5.3 recreate / patch 時の等価性（MUST）

recreate / patch の生成結果は、  
同一仕様・同一テンプレート・同一規約が与えられた場合、  
**常に new と意味等価**でなければならない。

---

## 6. テンプレートと生成プロンプトの責務分離

### 6.1 テンプレートの責務（MUST）

テンプレートは、以下のみを責務とする。

- 文書の固定構造（骨格）の定義

テンプレートは、以下を含めてはならない。

- 判断基準
- 条件分岐
- 作業手順
- LLM に対する命令文

### 6.2 生成プロンプトの責務（MUST）

生成プロンプトは、以下を責務とする。

- テンプレート構造スロットに対する操作・判断規則の定義

生成プロンプトは、以下を行ってはならない。

- テンプレート構造の変更
- 章構成の追加・削除・並び替え
- テンプレートを成果物の雛形として再解釈すること

---

## 7. 生成モード（meta / apply）の運用前提（MUST）

### 7.1 生成モードの定義

HLDocS における生成利用には、以下の 2 種類の生成モードが存在する。

- **meta**  
  HLDocS 自身（共通仕様・テンプレート・生成プロンプト等）を  
  作成または再作成するための生成。

- **apply**  
  HLDocS を不変の前提として用い、  
  他プロジェクトのドキュメントを生成・再作成するための生成。

### 7.2 モード明示の前提（MUST）

生成プロンプトは、
生成指示において **meta / apply のいずれであるかが明示されていること**を前提として設計されなければならない。

モードが不明確な状態で生成を継続してはならない（MUST NOT）。
- モード未指定の場合は、前提条件未成立として扱う。

---

## 8. 再作成（差し替え）に関する運用前提

再作成（recreate / patch）における  
不変条件・省略禁止・完全性要件は、  
再作成不変条件規約に委ねられる。

生成対象文書の本文状態（存在・欠落・内容差異）は、  
判断根拠として使用してはならない。

---

## 9. 共通仕様未成立時の取り扱い（MUST NOT）

共通仕様が成立していない入力は、  
**人間による検討・確認・差分把握を目的として提示されたもの**  
としてのみ扱われる。

この状態において、LLM は以下を行ってはならない。

- 生成工程を開始すること
- 新規ドキュメントを生成すること
- 既存ドキュメントを修正・再作成・差し替えること
- 次工程・追加作業・改善提案を提示すること

共通仕様が未成立である場合、  
**生成を開始しないこと自体が正しい挙動である。**

本章の規定は、
「前提条件（前提条件 spec）」において
共通仕様が未成立と判断された入力に対して
必ず適用されなければならない。

---

## 10. 世代・バージョン管理に関する前提（運用）

HLDocS の仕様・テンプレート・生成プロンプトは、  
**人間側の管理判断により世代・バージョンを更新される**。

- 世代・バージョン管理は、LLM の判断対象ではない
- 生成フェーズにおいて、世代情報を推測・補完してはならない
- 世代切替の判断は、必ず人間が行う

世代・バージョン管理の詳細は、  
別途定義される管理規約に委ねられる。
