# 生成プロンプト運用規約

本書は、HLDocS において **生成プロンプトおよびテンプレートを設計・生成・運用する際の前提となる利用形**を定義する。  
本規約は、HLDocS の仕様・構造・document_type 間の関係性・意味論そのものを定義するものではない。

本書の目的は、  
各仕様からテンプレートおよび生成プロンプトを作成する際に、  
**実運用においてどのような前提・責務分離・判断境界を置くべきか**を明示することにある。

---

## 1. 本書の位置づけ

本書は、以下を設計・生成・更新する際の **運用上の前提条件**を規定する。

- 共通テンプレート
- document_type 別テンプレート
- 共通生成プロンプト
- document_type 別生成プロンプト

本書は、  
生成プロンプトの **成立条件・不変条件・判定条件そのものを詳細定義する文書ではない**。  
それらの詳細規範は、別途定義される **共通規約群** に委譲される。

委譲対象となる規約の責務例は以下のとおりである。

- 生成フェーズの実行順序および FAIL-FAST 条件
- 再作成（差し替え）時の不変条件および省略禁止
- prompt の成立条件（必須要素セット）
- ENUM の再掲要件
- 判定テーブルの再掲要件

---

## 2. 想定する利用モデル（前提）

HLDocS の生成フェーズでは、以下を前提とする。

- LLM に与えられる入力は以下に限定される  
  - 共通テンプレート  
  - document_type 別テンプレート  
  - 共通生成プロンプト  
  - document_type 別生成プロンプト
- 仕様本文・規約本文・説明文書は、原則として生成フェーズでは LLM に与えない
- 生成プロンプトは、**テンプレートが既に与えられている状況**を前提として設計される

この前提により、生成プロンプトは  
**単体で規範として成立している必要がある**。

生成モード（meta / apply）は、
入力として与えられるテンプレートや生成プロンプトの有無ではなく、
生成対象が HLDocS 構成要素であるか否かによって決定される。

そのため、meta モードにおいても、
共通テンプレートおよび共通生成プロンプトを入力として与える工程が存在し得る。

---

## 2.1 生成プロンプトにおける仕様再掲の扱い

生成プロンプトは、  
仕様・構造・識別子・ENUM 値を **再定義してはならない**。

ただし、生成フェーズにおける判断材料を与える目的に限り、  
仕様からの再掲を行うことを許可する。

再掲の要件・制約・適否判断は、  
ENUM 再掲要件規約および判定テーブル再掲要件規約に従わなければならない。

### 2.1.1 再掲の基本条件（MUST）

- 再掲は逐語、または意味等価かつ不変でなければならない
- 再掲内容に対して、変更・要約・補足・省略・再解釈を行ってはならない
- 再掲は判断材料としてのみ使用され、  
  仕様の代替・上書き・再解釈を目的としてはならない

---

## 2.2 生成プロンプト設計における禁止原理（MUST）

生成プロンプトは、以下を行ってはならない。

- 仕様・テンプレート・規約に含まれる内容を再解釈・補完・要約すること
- 利用者から与えられていない仕様上の欠落を、推測により補うこと
- LLM-MANAGED ブロックに属するメタデータ領域を侵害すること

これらの禁止原理は、  
生成フェーズ構成、再作成不変条件、内部自己検査のすべてに優先して適用される。

---

### 2.3 仕様（spec）と生成プロンプト（prompt）の関係（禁止原理）

本節は、生成フェーズにおける **判断根拠の使用可否** を定義する。

生成プロンプト（prompt）は、  
**生成フェーズにおいて判断規範として単体成立していなければならない**。

ただし、以下の禁止原理を必ず満たさなければならない。

- prompt は、仕様（spec）を **上書き・再定義・補完してはならない（MUST NOT）**
- 仕様（spec）が入力として与えられている場合、  
  prompt は当該仕様と **意味的に矛盾してはならない（MUST）**
- 仕様（spec）が入力として与えられていない場合であっても、  
  prompt は **新たな判断基準・制約・例外を導入してはならない（MUST NOT）**

本節は、  
「prompt が spec の代替として振る舞い得る」という設計思想を定義するものではない。  
生成フェーズにおいて **何を判断根拠として使用してよいか／使用してはならないか**  
という **禁止原理のみ** を定義する。

---

### 2.4 派生（spec → prompt）の成立（MUST）

document_type 別生成プロンプト（prompt）は、以下の入力から作成可能でなければならない。

- 「共通生成プロンプト（prompt）」＋「document_type 別仕様（spec）」

この派生により作成された document_type 別生成プロンプト（prompt）は、  
当該 document_type 別仕様（spec）に定義された MUST / MUST NOT 条件を弱体化してはならない（MUST NOT）。

---

## 2.5 生成対象自己参照の禁止（MUST）

本節は、**document_type = prompt** に適用される  
**絶対的な禁止規範（MUST / MUST NOT）**を定義する。

本節に定義される規範は、設計思想・推奨事項・運用上の注意ではなく、  
**生成フェーズにおいて常に強制される規約**である。

---

### 2.5.1 基本原則（MUST NOT）

LLM は、生成対象となっている **prompt 文書そのもの**を、  
以下の目的で **判断根拠として使用してはならない（MUST NOT）**。

- 意味解釈
- 設計判断
- 仕様補完
- 制約導出
- 禁止事項・許可条件の判断
- 再作成時の差分判断

ここでいう「判断根拠」とは、  
**文言の存在有無に関わらず、生成結果に影響を与える一切の参照行為**を含む。

---

### 2.5.2 meta モードにおける生成対象 prompt 参照禁止（MUST NOT）

mode = meta において、LLM は以下を **行ってはならない（MUST NOT）**。

- 生成対象となっている prompt の本文を、
  判断・解釈・制約導出・正当性評価の根拠として使用すること
- 生成対象 prompt に含まれる文言を用いて、
  再生成結果の内容・粒度・表現を調整すること
- recreate / patch において、
  生成対象 prompt の本文差分を意味的に評価すること

meta モードでは、  
生成対象 prompt は **判断不能な成果物** として扱われなければならない。

生成対象 prompt は、  
doc_id 等の不変項目を保持するための **機械的参照対象** であって、  
**意味的判断の入力として使用してはならない**。

---

### 2.5.3 recreate / patch 時の特則（MUST NOT）

operation = recreate / patch の場合であっても、  
LLM は以下を **行ってはならない（MUST NOT）**。

- 生成対象 prompt の本文内容を用いて、
  - 未変更部分を推定すること
  - 正しさ・妥当性を評価すること
  - 再生成結果を調整すること

recreate / patch において許可される参照は、  
**不変項目（doc_id / canonical_title / document_type / 階層リンク行）の機械的保持のみ**である。

---

### 2.5.4 例外的許容：非生成対象 prompt の参照（MAY）

以下の条件を **すべて満たす場合に限り**、  
LLM は **生成対象ではない prompt** を判断根拠として使用してよい（MAY）。

- 当該 prompt が **生成対象ではない**
- 当該 prompt が **別 doc_id を持つ独立文書**である
- 当該 prompt が、利用者から **明示的に入力として与えられている**
- 当該 prompt の使用が、本節で定義された禁止事項に抵触しない

この例外は、  
**生成対象自己参照の禁止原則を緩和するものではない**。

---

### 2.5.5 規範の優先順位（MUST）

本節（2.5）に定義された禁止事項は、
仕様・テンプレート・生成フェーズ実行規約・設計背景よりも
**常に優先して適用される**。

本節に反する解釈・運用・実装は、  
すべて **HLDocS 規約違反**とみなされる。

---

## 3. テンプレートと生成プロンプトの責務分離

### 3.1 テンプレートの責務（MUST）

テンプレートは、以下を責務とする。

- 文書の固定構造を定義すること

テンプレートは、以下を含めてはならない。

- 書き方の指示
- 判断基準
- 条件分岐
- 作業手順
- LLM に対する命令文

---

### 3.2 生成プロンプトの責務（MUST）

生成プロンプトは、以下を責務とする。

- テンプレート構造スロットに対する操作・判断規則を定義すること

生成プロンプトは、以下を行ってはならない。

- テンプレート構造の変更
- 章構成の追加・削除・並び替え
- テンプレートを成果物の雛形として再解釈すること

---

## 4. 生成フェーズ実行と詳細規約の委譲

生成フェーズの実行順序、FAIL-FAST 条件、Phase 構成は、  
**生成フェーズ実行に関する共通規約**に従わなければならない。

本書は、生成フェーズの詳細な手順・検証条件を重複定義しない。

---

## 5. 再作成（差し替え）に関する運用前提

再作成（差し替え）における  
不変条件・省略禁止・完全性要件は、  
**再作成不変条件に関する共通規約**に従わなければならない。

本書は、不変条件そのものを定義しない。

再作成（recreate / patch）において、
生成に必須となる入力は「修正前正本（同一 doc_id）」のみである。

共通仕様・共通テンプレート・共通生成プロンプトは、
判断根拠として使用する場合に限り入力されていればよく、
それらの欠落を理由として生成を拒否してはならない。

再作成は「同一文書の改版」であり、
新規作成と同一条件で扱われる。

---

## 6. prompt 成立条件の扱い

生成プロンプトが「成立している」か否かの判定条件は、  
**prompt 成立条件に関する共通規約**に委ねられる。

生成プロンプトは、  
当該規約に定義された必須要素セットを満たすことを前提として  
設計・更新されなければならない。

---

## 9. 生成モード切替（MUST）

### 9.1 生成モードの定義

HLDocS による生成利用には、以下の 2 種類の生成モードが存在する。

- **HLDocS メタ生成（meta）**  
  HLDocS 自身（共通仕様、テンプレート、生成プロンプト等）を  
  作成または再作成するための生成。

- **HLDocS 適用生成（apply）**  
  HLDocS を不変の前提として用い、  
  他プロジェクトのドキュメントを作成または再作成するための生成。

---

### 9.2 モード明示を前提とする設計（MUST）

生成プロンプトは、  
生成指示において **meta / apply のいずれのモードであるかが明示されていること**を  
前提として設計されなければならない。

モードが不明確な状態で生成を継続してはならない（MUST NOT）。

---

### 9.3 生成モードと再作成（差し替え）の関係（MUST）

再作成（差し替え）における
正本の保持、不変条件の遵守、推測生成の禁止は、
生成モードに応じて以下のように適用される。

- meta モードでは、生成対象本文を判断根拠として使用してはならない。
- apply モードでは、不変項目の保持を目的とした参照のみが許容される。

生成プロンプトは、モードが meta である場合、  
再作成工程において既存の正本が  
要約・再編集・再構成されることがないよう  
設計されなければならない。

apply モードにおいては、  
HLDocS 自身の仕様・テンプレート・生成プロンプトは  
不変の前提として扱われなければならない。

---

### 9.4 meta モード更新フロー（MUST）

meta モードにおける HLDocS 更新は、以下の順序に従わなければならない。

(1) 共通仕様（spec）の確定  
(2) 共通仕様から共通テンプレート（template）の作成  
(3) 共通仕様と共通テンプレートから共通生成プロンプト（prompt）の作成  

(4) document_type 別仕様（spec）の確定  
(5) document_type 別仕様から document_type 別テンプレート（template）の作成  
(6) document_type 別仕様と document_type 別テンプレートから document_type 別生成プロンプト（prompt）の作成  

上位工程が未確定の状態で、下位工程を実行してはならない（MUST NOT）。
