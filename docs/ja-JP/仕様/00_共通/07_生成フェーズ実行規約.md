# 生成フェーズ実行規約

本書は、HLDocS において **生成プロンプトおよびテンプレートを用いてドキュメントを生成・再作成する際に、  
LLM が内部的に実行しなければならない処理フェーズとその順序を定義する**ための運用規約である。

本規約は、HLDocS の仕様・構造・document_type の意味論や内容そのものを定義するものではない。  
あくまで、**生成処理における手続き的拘束条件（どの順序で、何を、どこまで行うか）**を明確化することを目的とする。

本書に定義される生成フェーズは、  
共通生成プロンプトおよび document_type 別生成プロンプトにおいて、  
**解釈・省略・順序変更されてはならない内部実行順序**として扱われなければならない。

本書は、「HLDocS 前提条件」という仕様が、
入力文書一覧に含まれ、かつ参照可能である場合にのみ適用される。

「HLDocS 前提条件」が入力文書一覧に含まれない場合、
または当該仕様に基づく適用可否が確定していない場合、
本書に基づく判断・生成・再作成・工程実行を行ってはならない。

この場合に許可されるのは、提示された文書の受理および存在確認、
ならびに前提条件が未参照または未確定である旨の通知のみとする。

本規約における「入力文書一覧」の意味は、前提条件仕様において定義された用語定義に従う。

---

## 1. テンプレート合成規約（MUST）

### 1.1 共通テンプレート範囲

共通テンプレートは、以下のマーカーで囲まれた範囲のみをテンプレート範囲として扱う。

- `__COMMON_TEMPLATE_BEGIN__`
- `__COMMON_TEMPLATE_END__`

両マーカーは各 1 回ずつ必須とする。

---

### 1.2 document_type 別本文テンプレート範囲

document_type 別テンプレートは、以下のマーカーで囲まれた範囲のみを本文テンプレート範囲とする。

- `__BODY_TEMPLATE_BEGIN__`
- `__BODY_TEMPLATE_END__`

両マーカーは各 1 回ずつ必須とする。

---

### 1.3 本文差し込み位置

共通テンプレートには、本文差し込み位置として `__DOCUMENT_BODY__` を 1 箇所のみ定義する。  
合成時は、document_type 別テンプレートの本文テンプレート範囲を **無加工で差し込む**。

---

### 1.4 無改変規則（MUST）

- テンプレート範囲内の内容は一切改変してはならない
- 空行削除・正規化・再構成は禁止する
- 合成処理は機械的操作のみとする

---

## 2. 構造トークン規約（MUST）

本章は、テンプレート範囲内で **具体表現に依存せず文書構造を表現するための構造トークン**を定義する。

### 2.1 構造トークンの目的

- テンプレート範囲内で Markdown の具体構文（空行、`---`、HTML コメント等）を使用せずに、  
  論理構造上の区切りや順序を表現する
- テンプレート範囲の無装飾・無加工合成を成立させるための補助規約とする

### 2.2 既定の構造トークン

以下の構造トークンを既定とする。

- `<BLANK_LINE>`  
  構造上の空行（論理的区切り）
- `<SECTION_SEPARATOR>`  
  構造上の区切り線
- `<LLM_MANAGED_BLOCK>`  
  構造上の LLM-MANAGED ブロック

### 2.3 使用規則（MUST）

- テンプレート範囲内で構造上の空行・区切り・LLM-MANAGED ブロックが必要な場合、  
  **必ず構造トークンを使用する**
- テンプレート範囲内に、  
  実際の空行、`---`、HTML コメントを直接記述してはならない

### 2.4 実体化の責務（MUST）

- 構造トークンを具体表現へ変換する責務は、  
  **最終成果物を出力する直前の生成工程（実体化工程）**に属する
- テンプレート合成工程では、  
  構造トークンを解釈・変換してはならない

### 2.5 実体化の要件（MUST）

- `<BLANK_LINE>` は **空行 1 行**として実体化される
- `<SECTION_SEPARATOR>` は **`---` 単独行**として実体化される
- `<LLM_MANAGED_BLOCK>` は  
  **LLM-MANAGED ブロック規約に適合する HTML コメント形式**として実体化される

### 2.6 将来拡張（MUST）

- 新たな構造要素が必要になった場合、  
  **本章に構造トークンを追記することで対応する**
- 構造トークンを定義せずに、  
  テンプレート範囲へ具体表現を直接追加してはならない

---

## 3. 生成フェーズ順序（MUST）

本章は、document_type が確定し、  
共通テンプレート・document_type 別テンプレート・生成プロンプトがすべて与えられている前提で、  
LLM が最終成果物を生成する際の **内部処理順序および各フェーズの作業内容**を定義する。

LLM は、以下に定義する Phase 0 から Phase 7 までを **順序を変更せず** 実行しなければならない。

---

### Phase 0: 入力検証（FAIL-FAST）

Phase 0 は、生成工程に入る前の **最終的な実行可否判定フェーズ**である。

本フェーズでは、以下を必ず検証しなければならない（MUST）。

- 共通仕様が成立していると判断可能であること
- mode / operation / document_type が明示されていること
- 対応する template / prompt がすべて提示されていること
- 本フェーズ以前の仕様に依存した推測判断を行っていないこと

いずれかを満たさない場合、  
LLM は生成フェーズを開始してはならない（FAIL-FAST）。

FAIL-FAST 時の出力可否および応答内容は、  
生成プロンプト運用規約（02）に従う。

Phase 0（FAIL-FAST）では、共通生成プロンプトを生成する場合に限り、
共通ドキュメントテンプレートおよび必要な本文テンプレートが
入力として実体提示されていることを必須条件として検証する。

提示がない場合、
LLM は生成フェーズを開始してはならない（FAIL-FAST）。

---

### Phase 1: テンプレート抽出

- 共通テンプレートから  
  `__COMMON_TEMPLATE_BEGIN__` ～ `__COMMON_TEMPLATE_END__` で囲まれた範囲を抽出する
- document_type 別テンプレートから  
  `__BODY_TEMPLATE_BEGIN__` ～ `__BODY_TEMPLATE_END__` で囲まれた範囲を抽出する

各マーカーが欠落している、または複数存在する場合、  
LLM は生成および合成を行ってはならない（MUST NOT）。

抽出対象外の本文・説明文・コメントを解釈してはならない（MUST NOT）。

---

### Phase 2: テンプレート合成

- 共通テンプレート内の `__DOCUMENT_BODY__` 位置に、  
  Phase 1 で抽出した本文テンプレート範囲を **無加工で差し込む**
- 以下を行ってはならない（MUST NOT）
  - 構造トークンの解釈または変換
  - 空行の削除・追加
  - マーカーや固定構造の変更

---

### Phase 3: 可変スロット生成および Traceability 構築

- 可変スロット（例：文書タイトル、章本文、説明文）を生成する
- Traceability 規約に従い、以下の識別子を構築・配置する  
  - doc_id  
  - sec_id  
  - ref_id（該当する場合）

以下を行ってはならない（MUST NOT）。

- テンプレート構造の改変
- 固定マーカーの削除・移動
- 構造トークンの変更または実体化

---

### Phase 4: 構造トークン実体化

- Phase 3 完了後の文書に含まれる構造トークンを、  
  **意味等価な具体表現**へ置換する
- 置換以外の操作を行ってはならない（MUST NOT）

---

### Phase 5: Transport Encoding 適用

- 指定された Transport Encoding 規約に従い、  
  最終成果物の出力形式を適用する
- 文書の意味内容・構造・識別子を変更してはならない（MUST NOT）

---

### Phase 6: 最終検証（非出力）

- 共通ドキュメント構造規約に違反していないこと
- 不変条件（doc_id、階層リンク、構造順序 等）が保持されていること
- 推測生成を行っていないこと
- Transport Encoding 規約に定める出力制約に適合していること

検証結果を出力してはならない。

---

### Phase 7: 出力

- **最終成果物のみ**を外部へ出力する
- 中間生成物・検証結果・内部判断過程を出力してはならない
- 出力は Phase 5 の結果に従う
- 出力時に文書内容・構造・識別子を改変してはならない（MUST NOT）

---

## 4. document_type 検証規則（MUST）

- document_type は **ENUM 定義のみ許可**する
- document_type の正当性は、  
  LLM-MANAGED ブロック規約に定義された ENUM に基づいて検証しなければならない
- 未定義 document_type を推測してはならない
- 必要なテンプレート・生成プロンプトが不足している場合は、  
  **生成を停止する**
