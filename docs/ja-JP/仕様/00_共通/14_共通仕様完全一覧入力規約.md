# 共通仕様完全一覧入力規約

本書は、HLDocS における「共通仕様完全一覧」と、
生成・検証時の入力成立条件との関係を定義する。

本書は、共通仕様完全一覧を、
物理ディレクトリ構造ではなく、
有効入力集合（effective input set）として扱うことを目的とする。

---

## 1. 基本方針

HLDocS における共通仕様完全一覧は、
物理ディレクトリ配下を自動走査して決定するものではない。

共通仕様完全一覧は、
生成・検証時に利用する共通仕様文書群を明示的に定義した集合である。

したがって、成立条件判定では、
物理ディレクトリ構造ではなく、
実際に参照可能な有効入力集合（effective input set）を基準としなければならない（MUST）。

「HLDocS 前提条件」は、
HLDocS 共通仕様成立条件の root document として扱う。

したがって、
「HLDocS 前提条件」が有効入力集合に含まれない場合、
HLDocS 共通仕様成立条件は成立していないものとして扱う（MUST）。

この場合、
生成・再作成・patch・検証・成果物提示を一切行ってはならない（MUST NOT）。

---

## 2. 有効入力集合

有効入力集合（effective input set）とは、
当該生成・検証時点で、LLM が実際に参照可能な入力集合を指す。

例：

- 添付ファイル
- GitHub URL
- file_search により参照可能なファイル
- チャット内へ貼り付けられた内容
- 外部参照として明示された文書

---

現時点での共通仕様完全一覧は以下とする。

1. 前提条件
2. 生成プロンプト運用規約
3. 共通ドキュメント構造
4. LLM-MANAGEDブロック規約
5. Transport Encoding規約

11. 判定テーブル再掲要件規約

---

## 4. 成立条件

共通仕様成立条件判定では、
共通仕様完全一覧に列挙された文書群が、
有効入力集合に含まれていなければならない（MUST）。

一部が欠落している場合、
共通仕様成立条件は成立していないものとして扱う（MUST）。

---

## 5. 共通仕様更新時の同期更新要件

HLDocS 共通仕様へ新しい共通仕様文書を追加する場合、
以下を同時に更新しなければならない（MUST）。

1. 前提条件に記載された共通仕様構成要素一覧
2. 共通仕様完全一覧
3. 目次
4. 成立条件関連規約
5. 必要に応じた生成プロンプト・検証プロンプト

一部のみ更新し、
他の一覧・成立条件・判定規則を未更新のまま残してはならない（MUST NOT）。

これは、
restructuring・migration・HTML visualization・split / merge・再配置などにおいて、
共通仕様集合の不整合が連鎖的に発生することを防止するためである。

---

## 6. ディレクトリ構造との分離

以下のような判定は禁止する（MUST NOT）。

```text
仕様/00_共通 配下を自動的に共通仕様完全一覧とみなす
```

理由：

- 添付ファイル運用と整合しない
- URL 指定運用と整合しない
- file_search 運用と整合しない
- restructuring / migration 時に成立条件が不安定化する

HLDocS は、物理配置ではなく、
有効入力集合を基準として成立判定を行う。

---

## 7. restructuring との関係

restructuring・migration・再配置時であっても、
成立条件は物理配置ではなく、
有効入力集合を基準とする。

これにより、
ファイル移動・分割・統合・配置変更が行われた場合でも、
論理的な共通仕様集合を安定して扱うことができる。

---

## 8. HTML 可視化との関係

Markdown → HTML visualization においても、
共通仕様集合は物理配置ではなく、
論理的な入力集合として扱う。

そのため、HTML 側では、
物理パスではなく、
canonical_title / doc_id / sec_id を基準とした可視化を推奨する（SHOULD）。
