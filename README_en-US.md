# HLDocS

**Human–LLM Document Roles Specification**

HLDocS is a common specification that defines the roles and rules for collaborative document creation, validation, and reconstruction between Humans and Large Language Models (LLMs).

This repository is designed based on practical operation across multiple projects, including AIChaBo and Project Sansa, but it is not tied to any specific implementation, tool, or framework.

## What is HLDocS?

HLDocS is a document specification based on the following principles:

* The **canonical structure** of documents is guaranteed by the LLM
* Humans do **not** perform exhaustive structural validation
* Humans focus on **meaning, correctness, and design decisions**
* Human readability is treated as supplementary information

HLDocS does not define how documents should be written for humans.
Instead, it defines how documents should be handled through role separation between Humans and LLMs.

---

## Roles

### Human Responsibilities

* Validating requirements, designs, and test content
* Determining scope and direction
* Review and decision making

In HLDocS, humans do **not** verify document structural completeness or consistency.

---

### LLM Responsibilities

* Maintaining document structure
* Preserving IDs, relationships, and structural information accurately
* Assisting reconstruction, generation, and validation
* Generating human-oriented supporting information

In HLDocS, preventing structural corruption is the highest priority requirement for an LLM.

## LLM_WORKSPACE and Workflow

HLDocS supports long-term Human–LLM collaborative work.

The recommended workflow is:

1. Record new requests in Request
2. Record active work status in Worklog
3. Create Handover documents only when chat migration is required

Worklog is the canonical source of work state.

LLM_WORKSPACE is a logical structure.
It may be stored using GitHub, attachments, chat conversations, or other storage mechanisms.

Work must remain resumable even when GitHub is unavailable.

---

## Canonical and Non-Canonical Information

HLDocS classifies document content into the following categories.

### Canonical Information

* Structural definitions
* IDs (Suite, Test, API, etc.)
* Relationships
* Specification declarations

Canonical information is the single source of truth and must not be removed, altered, or made ambiguous.

---

### Non-Canonical Information

* Human notes
* Summaries and supplementary explanations
* Readability enhancements

Non-canonical information:

* May be removed without invalidating the specification
* May be regenerated by an LLM
* Must not affect canonical information

---

## Document Types

HLDocS is intended for document types such as:

* Test specifications
* API specifications
* Design specifications
* Core specification documents

For each document type, HLDocS defines:

* The scope of canonical information
* The role of Human Notes
* The guarantees required from LLMs

---

## Markdown Policy

HLDocS documents are based on Markdown.

Markdown is used not for visual decoration, but for explicitly expressing document structure.

* Tables should generally not be used
* Meaningful symbols and notation are fixed by specification
* Readability enhancements are treated as non-canonical information

---

## What HLDocS Does Not Do

HLDocS is not intended to:

* Produce documents optimized solely for human readability
* Enforce a specific tool or framework
* Provide legally binding regulations

HLDocS is a technical and architectural common specification.
